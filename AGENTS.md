# Meadow PIM — Root DOX Contract

- DOX is a highly performant AGENTS.md hierarchy installed in this repository.
- Agents must follow DOX instructions across any edits.

## Core Contract

- AGENTS.md files are binding work contracts for their subtrees
- Work products, source materials, instructions, records, assets, and durable docs must stay understandable from the nearest applicable AGENTS.md plus every parent AGENTS.md above it

## Read Before Editing

1. Read the root AGENTS.md
2. Identify every file or folder you expect to touch
3. Walk from the repository root to each target path
4. Read every AGENTS.md found along each route
5. If a parent AGENTS.md lists a child AGENTS.md whose scope contains the path, read that child and continue from there
6. Use the nearest AGENTS.md as the local contract and parent docs for repo-wide rules
7. If docs conflict, the closer doc controls local work details, but no child doc may weaken DOX

Do not rely on memory. Re-read the applicable DOX chain in the current session before editing.

## Update After Editing

Every meaningful change requires a DOX pass before the task is done.

Update the closest owning AGENTS.md when a change affects:

- purpose, scope, ownership, or responsibilities
- durable structure, contracts, workflows, or operating rules
- required inputs, outputs, permissions, constraints, side effects, or artifacts
- user preferences about behavior, communication, process, organization, or quality
- AGENTS.md creation, deletion, move, rename, or index contents

Update parent docs when parent-level structure, ownership, workflow, or child index changes. Update child docs when parent changes alter local rules. Remove stale or contradictory text immediately. Small edits that do not change behavior or contracts may leave docs unchanged, but the DOX pass still must happen.

## Hierarchy

- Root AGENTS.md is the DOX rail: project-wide instructions, global preferences, durable workflow rules, and the top-level Child DOX Index
- Child AGENTS.md files own domain-specific instructions and their own Child DOX Index
- Each parent explains what its direct children cover and what stays owned by the parent
- The closer a doc is to the work, the more specific and practical it must be

## Child Doc Shape

- Create a child AGENTS.md when a folder becomes a durable boundary with its own purpose, rules, responsibilities, workflow, materials, or quality standards
- Work Guidance must reflect the current standards of the project or user instructions; if there are no specific standards or instructions yet, leave it empty
- Verification must reflect an existing check; if no verification framework exists yet, leave it empty and update it when one exists

Default section order:
- Purpose
- Ownership
- Local Contracts
- Work Guidance
- Verification
- Child DOX Index

## Style

- Keep docs concise, current, and operational
- Document stable contracts, not diary entries
- Put broad rules in parent docs and concrete details in child docs
- Prefer direct bullets with explicit names
- Do not duplicate rules across many files unless each scope needs a local version
- Delete stale notes instead of explaining history
- Trim obvious statements, repeated rules, misplaced detail, and warnings for risks that no longer exist

## Closeout

1. Re-check changed paths against the DOX chain
2. Update nearest owning docs and any affected parents or children
3. Refresh every affected Child DOX Index
4. Remove stale or contradictory text
5. Run existing verification when relevant
6. Report any docs intentionally left unchanged and why

## Purpose

Meadow PIM is a modern, performant Product Information Management (PIM) system for small and medium-sized enterprises (SMEs/KMUs). The high-performance core is written in Rust; flexible business logic and the user interface are written in Python. Design principles: simple, performant, and maintainable.

## Local Contracts

- `plan/meadow-pim-architektur.md` is the authoritative architecture and technical plan. Implementation decisions must stay consistent with it, or the plan must be updated in the same change.
- Final technology stack (see plan sections 2–3):
  - Core: Rust (Edition 2024), Axum + utoipa (OpenAPI), serde/serde_json, jsonwebtoken + argon2, surrealdb client, async-nats, tokio-cron-scheduler.
  - Data & messaging: SurrealDB (documents + graph), NATS JetStream (queue + event bus), S3-compatible object storage, optional Redis cache.
  - Python: Python 3.14, NiceGUI (frontend), asyncio + nats-py + httpx (worker), Pydantic + RestrictedPython (Business Rules, Abschnitt 8).
  - Operations: Docker + Docker Compose (MVP), optional Kubernetes (k3s).
- SurrealDB server core is BSL 1.1 licensed (change date 2030-01-01 → Apache 2.0). Self-hosted production use for Meadow PIM is allowed; offering SurrealDB as a "Database Service" is not.
- jsonwebtoken v10+/v11 requires a crypto backend feature (`aws_lc_rs` or `rust_crypto`); crate MSRV is 1.88.
- **The composition parent is part of the write:** an object is created *with* its composition parent (`POST /objects` / `POST /objects/batch-upsert`, field `parent`; the import worker writes a document parents-first in breadth-first levels and re-attaches legacy edgeless objects). If the parent is neither written in the document nor present in the system, the object must **not** be created — the job reports an error. The composition edge cannot be deleted via `DELETE /references/{id}`; re-parenting goes through `PATCH /objects/{id}/parent`. Types without a composition edge: `collection`, `saved_search`.
- **A MEF export is a restore artifact, not just a value dump (2026-09-17):** the JSON document carries the objects, their **relations** (`references`, read in bulk via `POST /references/query`), and their **channel releases** (`releases`); the source kind `all` is the complete export, and `options.include_ancestors` (default on) keeps a partial source importable. A full restore is three steps in this order: **MCF** (`GET /config/export` → `POST /config/import`) for the model, **MEF** (`POST /exports` kind `all` → `POST /imports`) for the data, then the MCF section `category_attributes` (the class features of an installed standard) — those reference taxonomy nodes that travel as data, so they can only be applied after the data import. Users/groups, connectors, job definitions and system settings are environment configuration and are not part of either document. Contract details: `docs/integration/mef-and-events.md` §1.6. **Was ein Import tun würde, ohne zu importieren (2026-10-16):** `POST /imports/preview` führt den Schreibpfad selbst aus (`objects::upsert_objects` im Report-Modus — Typregister, Business-Key, Scope, Attributwerte, Regeln) plus die Kompositionsregel des Import-Jobs und antwortet je Objektzeile `create`/`update`/`failed`; geschrieben wird nichts (kein Objekt, keine Kante, kein Event, kein Audit, kein neuer Objekttyp, und die Regelauswertung läuft im Report-Modus, damit ein Vorschau-Lauf keinen Circuit Breaker bewegt). Grenzen: `references` werden gezählt statt aufgelöst, und die Werte-Normalisierung des Import-Workers gehört nicht zur Vorschau.
- **Job lists carry no payload (2026-09-18):** `job_run.result` is also storage — an export keeps its whole document there, an import its per-object report — so listing runs *with* results answers with **tens of megabytes** and then **resets the SurrealDB connection**, which took unrelated endpoints (`/languages`, `/system/logs`) down with it (`500 Connection reset`). Lists and polling therefore pass `include_result=false`, and the core writes a **`result_summary`** (the result's top-level fields, each ≤ 2 KB) with every result, returned in every run answer. Report and download fetch the single run. Contract: `crates/AGENTS.md`, `plan/detail/jobs-scheduler.md`.
- **KI-Assistenz (Stufen 0–2 umgesetzt 2026-09-19/21, `plan/detail/ki-assistenz.md`):** eine Schreibhilfe in den Editoren, **kein** Chat und **kein** Agenten-Framework. Bereiche (`area`): `rule`, `computed_attribute`, `search`, `connector`, `export_profile`, `job`, `import_mapping`, `group_permissions` (Rechte und Scope einer Gruppe, Stufe D des RBAC-Plans, 2026-09-27). Ein Vorschlag landet im Feld, **niemals** automatisch in der Datenbank: der Nutzer prüft und speichert über den normalen Weg. Geprüft wird von dem Baustein, der den Vorschlag ausführt: Skripte durch die AST-Vorprüfung in `meadow/ai/policy.py` **plus** die Compile-Politik der Sandbox (danach optional der Dry-Run im Rule Lab), Suche und JSON-Konfigurationen durch die Validierung des Kerns (`POST /saved-searches/preview`, `/connectors/validate`, `/export-profiles/validate`, `/jobs/validate`, `/groups/validate` — die zwei Prüfungen des Gruppen-Schreibpfads, Katalog **und** Scope), das Import-Spalten-Mapping durch `meadow/tabular.check_mapping` (dasselbe Modul, das das MEF-Dokument baut, das der Import schreibt). Der Modellaufruf passiert im **Worker** (dort sitzen `httpx`, die Sandbox und das Außen-I/O), angesprochen über NATS (`ai.generate`/`ai.test`); der Kern besitzt Konfiguration und Audit und schickt die aufgelöste Konfiguration mit — **der API-Key verlässt den Kern nur in dieser internen Nachricht**, nie Richtung Browser, und er steht **nie** in einem Prompt. Konfiguriert wird in der Oberfläche (`/system-settings`, Gruppe „KI-Assistenz", admin-only, Opt-in über `ai_enabled`; das Schlüsselfeld ist write-only, ein ENV-Wert sperrt es **und** der Knopf „Beispielwerte eintragen" füllt Endpunkt und Modell des gewählten Anbieters **nur in leere Felder** — eine Voreinstellung für die Inbetriebnahme, kein Überschreiben). Der Prompt enthält **Schema und Metadaten, keine Objektwerte**. Jeder Aufruf wird im `ai_generated`-Audit mit Bereich, **Ziel** (`target`: Record-Id, `new` oder Attributname), Modell, Versuchen, Latenz und Tokens festgehalten (ohne Prompt, ohne Skript); `GET /ai/history?area=…&target=…` (`ai.use`) listet diese Einträge, und der Vorschlagsdialog zeigt sie über den Knopf „Verlauf" — **kein zweiter Speicher**. Fail-closed: aus, unkonfiguriert oder Worker weg ⇒ `503` mit klarer Meldung, kein Ersatzweg und kein Einfluss auf Speicherpfade.
- **Job-Parameter haben einen maschinenlesbaren Vertrag (2026-09-21):** `crates/pim-core/src/api/job_schema.rs` beschreibt jeden Jobtyp mit seinen Parametern und `bulk_operation` mit seinen Operationen; `GET /jobs/schema` liefert das Dokument (Job-Formular: Typenliste und Parameterhinweise; dazu die KI-Assistenz), `POST /jobs/validate` prüft eine Definition **ohne zu speichern** (Parameter + Cron). Regel: jeder deklarierte Schlüssel wird von einem Konsumenten gelesen und jeder gelesene ist deklariert — ein neuer Jobparameter gehört in dieses Schema, nicht ins Formular. Der Schreibpfad (`POST`/`PATCH /jobs`) prüft **gegen den Vertrag** (2026-10-16): deklarierte Felder, die fehlen oder die falsche Form haben, werden mit `400` abgelehnt, **unbekannte** Schlüssel dagegen gespeichert und **gemeldet** (`notices` in `POST /jobs/validate` plus `WARN`-Eintrag der Log-Kategorie `job`) — eine Definition darf einen Parameter tragen, den erst ein neuerer Worker liest. Der Prüfaufruf ist damit wie bei Konnektoren und Export-Profilen genau der Schreibpfad; strenger als ein Mensch ist nur die KI-Assistenz, deren Vorschlag keine erfundenen Schlüssel enthalten darf.

- **Das Repository ist öffentlich — keine Defaults für Secrets (2026-10-12):** `JWT_SECRET` (Kern) und `UI_STORAGE_SECRET` (Frontend) haben **keinen** Vorgabewert und müssen mindestens **32 Zeichen** lang sein; sonst verweigern Kern (`crates/pim-core/src/config.rs`) und Frontend (`meadow/frontend/config.py`) den Start mit klarer Meldung. Die Längengrenze schließt den Platzhalter der Vorlage und die früheren Defaults ein, ohne sie zu nennen (und hält zugleich zu kurze Schlüssel fern — `stopslop` verbietet Platzhalterwerte im Quelltext). Lokal setzt man beide vor dem Start (`scripts/run-dev.ps1` erinnert daran), produktiv kommen sie aus `.env.vps` (Preflight in `scripts/deploy-vps-meadow.sh`). Interne Infrastruktur-Angaben (Registry-Host, Domainnamen, Netzname fremder Stacks) gehören **nicht** in getrackte Dateien: die Vorlagen nutzen `example.com`/`traefik-net`, die echten Werte stehen nur in der gitignorierten `.env.vps` — `tests/test_deployment.py` hält die Netz-Variable `TRAEFIK_NETWORK` als Vertrag fest.

Beide Seiten brauchen **denselben** Wert, gelesen als Umgebungsvariable (kein dotenv auf beiden Seiten): `$env:LOG_INGEST_API_KEY = "dev-machine-key"` vor `cargo run -p pim-core` **und** vor `uv run python -m meadow.worker`; der Kern liest ihn beim Start, also den Kern danach neu starten. ## Verification

- All gates in one run: `bash scripts/check.sh` (Linux/CI/VPS) or `powershell -File scripts/check.ps1` (Windows); `rust` / `python` selects a subset. The core must not be running — on Windows a running `pim-core.exe` locks the binary while relinking.
- **Der Deslop-Scan ist bewusst kein Gate (2026-09-18):** `scripts/deslop.ps1`/`deslop.sh` laufen manuell, nicht in `check.*` und nicht in CI — ein Befund ist ein Qualitätssignal, kein Korrektheitsbeweis. Nur Artefaktbefunde der Stufe A lassen den Lauf scheitern; der Bestand ist über `.stopslop-baseline.json` grün. Details: `plan/detail/ai-code-quality.md`.
- **`mypy` ist ein Gate über den gesamten Python-Baum (2026-09-18):** `[tool.mypy]` in `pyproject.toml` prüft 131 Dateien (`meadow/` vollständig inkl. Frontend, `tests/`, `scripts/`) mit `check_untyped_defs = true` und läuft in `scripts/check.*`; nur `tests/fixtures/` ist über `exclude` ausgenommen (der absichtlich kaputte Deslop-Sample). `follow_imports = "silent"` war die Voraussetzung, dass der Scope modulweise wachsen konnte: nur die in `[tool.mypy] files` gelisteten Dateien werden gemeldet, ein noch nicht aufgenommenes Modul bleibt ungeprüft, statt das Gate zu blockieren. `warn_unused_ignores` macht überflüssige `# type: ignore` sichtbar — der Anlass war genau das: 33 Ausweichungen ohne Prüfer, heute sind es 11 (alle notwendig). Achtung: mypy und Pylance widersprechen sich stellenweise (z. B. `lambda n=hit:` — mypy rät, Pylance braucht das Ignore; beim Entfernen beide ansehen, Pylance fand dabei einen echten `await`-Fehler). NiceGUIs Element-Typing wird **geprüft**: Element-Variablen konkret typisieren (`ui.input`, `ui.checkbox`), `ui.element` ist nur der Rahmen; die wiederkehrenden Muster und die zwei Lehren („dieselbe Meldung 86-mal ⇒ Signatur prüfen", „ein Test-Double macht die schmale Schnittstelle sichtbar") stehen in `plan/detail/ai-code-quality.md` §4.7–§4.9.
- **Die Gates bauen kein Binary (2026-09-17):** `check.ps1`/`check.sh` prüfen nur (fmt, clippy, `cargo test`, ruff, pytest) — `target/debug/pim-core.exe` bleibt also **alt**, bis jemand `cargo build -p pim-core` (oder `cargo run`) aufruft. Wer den Kern nach einer Rust-Änderung neu startet, ohne vorher zu bauen, bedient die Oberfläche still mit einem **veralteten** Kern (genau das passierte hier: ein Debug-Binary vom Vortag ignorierte das `parent`-Feld, während der Release-Build es schon konnte). Vor jedem Neustart nach Kern-Änderungen also **bauen, dann starten**.
- Rust: `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test` (workspace root).
- Python: `ruff check`, `ruff format --check`, `mypy`, `pytest` (dev dependencies via uv); die Ruff-Gates prüfen `meadow`, `tests` und `scripts`, der mypy-Scope steht in `[tool.mypy] files` (`pyproject.toml`). **Ein neu extrahiertes Modul gehört in `[tool.mypy] files` — im selben Schritt.** Der Scope listet Frontend-Module einzeln auf (Wachstumsregel §4.6 in `plan/detail/ai-code-quality.md`); steht ein Modul nicht dort, verfolgt `follow_imports = "silent"` es nur still und meldet **keine** Fehler darin (im Umbau der Produktseite übersehen, siehe §4.11).
- **Seitentests (2026-09-18):** `tests/test_products_page.py` bootet die **echte** Frontend-App über NiceGUIs User-Simulation (Plugin im Root-`conftest.py`, NiceGUI-Storage im Temp-Verzeichnis) und prüft Seitenverhalten statt Helfer – das Netz für den `products_page`-Umbau; Regeln in `tests/AGENTS.md`, Details in `plan/detail/ai-code-quality.md` §4.11.

- The translation files must carry the same key set and no empty values — enforced by `tests/test_frontend.py::test_translation_files_share_the_same_keys` (part of the pytest gate).
- **Deployment contracts (2026-09-29):** `tests/test_deployment.py` hält die stillen Verträge der Produktionsdateien fest (jede in `docker-compose.vps.yml` gelesene Variable ist in `.env.vps.example` dokumentiert und umgekehrt, Log-Rotation je Dienst, Nummerierung und Reihenfolge der Migrationen, Migrationen **vor** der Anwendung, kein `curl` auf einen unveröffentlichten Port, kleingeschriebener Registry-Pfad, `.dockerignore`). ## User Preferences

When the user requests a durable behavior change, record it here or in the relevant child AGENTS.md

- **Python-Paketmanager:** `uv` (statt pip). Projekt-venv unter `.venv/`; Abhängigkeiten in `pyproject.toml` pflegen (`uv add`/`uv sync`, Lockfile `uv.lock`).
- **Test-Ablage:** Neue Tests möglichst im `tests/`-Verzeichnis anlegen, um das Wurzelverzeichnis übersichtlich zu halten.
- **Dokumentations-Ablage:** Dokumentation, die nicht zur Planung gehört, (idealerweise hierarchisch) im `docs/`-Verzeichnis anlegen.
- **Keine Fallbacks für Versionsversatz (bis es eine produktive VPS-Umgebung gibt):** Kern und Frontend/Worker laufen immer zusammen, also gibt es keine Kompatibilitätspfade für ältere Kern-Versionen (z. B. „neuer Endpunkt, sonst seitenweise laden", doppelte Payload-Formate, Feature-Detection). Ein neuer Vertrag wird direkt genutzt; fehlt er, ist das ein Fehler und wird sichtbar gemeldet. Das betrifft **nicht** das Degradieren bei fehlenden Daten/Infrastruktur (leere Liste statt Absturz, `RULES_DEGRADE`), und nicht die bewusst doppelt geführten Konventionen (MEF/MCF-Importe mehrerer Versionen).
- **Keine Fremdprodukt-Namen in der Oberfläche (2026-09-17):** UI-Texte — Übersetzungen (`meadow/frontend/locales/*.json`), Handbuchkapitel (`docs/user/`), Tooltips, Hinweise, Meldungen — beschreiben die Funktion in eigenen Worten und nennen **keine** anderen PIM-/Shop-Systeme; die Nennung von Mitbewerbern in Kundentexten ist rechtlich riskant. Marktvergleiche stehen nur in internen Plan-/Vertragsdokumenten (`plan/`, `*/AGENTS.md`). Details: `meadow/AGENTS.md` (Work Guidance).
