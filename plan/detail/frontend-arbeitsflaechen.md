# Arbeitsflächen der Benutzeroberfläche (Grid, Formular, Massendatenpflege)

- **Hauptdokument:** Abschnitt 11 ([Benutzeroberfläche](../meadow-pim-architektur.md#11-benutzeroberfläche-frontend))
- **Relevante Phasen:** Phase 7, 9
- **Stand:** Entwurf

Dieses Dokument spezifiziert die konkreten Arbeitsflächen der Weboberfläche (NiceGUI): das **Grid** als Hauptarbeitsfläche, das **Produkt-Formular** als Drill-down, die **Massendatenpflege** und das **Dashboard**. Es vertieft die Modulübersicht aus [frontend.md](frontend.md) und übersetzt die fachlichen Modelle (Datenmodell, Vererbung, Sprachbaum, Kategorisierung) in eine **menschengerechte Oberfläche** – die UI bildet bewusst nicht das generische Objektmodell ab.

## Leitprinzipien

- **Die UI bildet nicht das generische Objektmodell ab.** Der Anwender sieht eine vertraute Produktsicht: Ein Produkt hat Name, Preis, Beschreibung, technische Daten – gruppiert, geordnet, mit Pflichtfeldern. Der generische Unterbau (Typ, flexible Attribute) bleibt dahinter verborgen.
- **Drei Arbeitsflächen, eine Auswahl:** (1) das **Grid** als Zuhause der Anwender (Suchen, Filtern, Inline-Editing, Bulk-Aktionen), (2) das **Produkt-Formular** als Drill-down für tiefes Anreichern eines einzelnen Objekts, (3) der **Bulk-Wizard** für Massenänderungen. Alle drei teilen sich Filterlogik, Auswahl und Vollständigkeits-Kontext.
- **Template pro Typ:** Welche Attribute, Gruppen und Pflichtfelder ein Objekttyp anzeigt, bestimmt die Produktvorlage (Attributdefinitionen mit `applicable_types`/`required_types`, siehe [datenmodell.md](datenmodell.md)). Nur Gruppen mit mindestens einem für den Typ gültigen Attribut erscheinen.
- **Hinweise als Icons/Marker:** Herkunft (Vererbung), Fallback (Sprache), Warnungen und Status werden als **dezente Icons/Marker mit Tooltip** dargestellt – nicht als beschreibender Text, um die Anzeige schlank zu halten.
- **Grid-Technologie:** Produktives Grid über **`ui.aggrid` (AG Grid, Community-Modul)** – eingebaute Zell-Editoren, Mehrfachauswahl, Spalten-Pinning, bedingte Formatierung und Synchronisation der Client-Edits zurück zum Server. `ui.table` (Quasar) bleibt für einfache Admin-Listen (Jobs, Audit, Benutzer). `nicegui-tabulator` (Tabulator.js, MIT) ist die dokumentierte Alternative, falls ein Baum direkt im Grid benötigt wird.
- **Stand (Schritt 3/3b/4/4b/5):** Das Basis-Grid ist umgesetzt (`/products`, `meadow/frontend/grid.py`): lesbare Objektliste (`ui.aggrid`) mit aufgelöstem Namen (Sprachbaum-Wert), **Status-Badge**, i18n-Spaltenüberschriften und Mehrfachauswahl; Daten aus `GET /objects`. **Inline-Editing & Batch-Save** sind umgesetzt (Abschnitt 1.3): Zell-Editing, Gestaging mit „Ungespeicherte Änderungen“-Zähler, Batch-Save über `POST /objects/batch-update` (max. 500 Zeilen), „Verwerfen“, gültiger JWT erforderlich (abgelaufene Tokens leiten zur Login-Seite um). Der **Spalten-Picker** ist umgesetzt (Abschnitt 1.2): „Spalten“-Button öffnet ein Menü mit Checkboxen je Attributspalte (aus `GET /attribute-definitions`); Attribute sind standardmäßig ausgeblendet, die ID-Spalte ist links gepinnt. **Persönliche Ansichten** sind umgesetzt (Abschnitt 1.2): „Ansichten“-Dialog speichert die aktuelle Spaltenauswahl pro Benutzer (`app.storage.user`), listet gespeicherte Ansichten und stellt sie per Klick wieder her (inkl. Löschen). Der **Strukturbaum** ist umgesetzt und **lazy-geladen** (Abschnitt 1.1): Kompositionsbaum links mit Knoten-Auswahl, die das Grid auf den Teilbaum filtert; Darstellung als `ui.splitter` (resizable) mit Baum-Karte, Filterfeld und Labels „Name · Typ“. Die **Vollständigkeits-Spalte** ist umgesetzt (Abschnitt 4): farbige Badges (grau 0 %, orange 1–99 %, grün 100 %) aus `GET /objects?locale=` (`completeness`-Feld der Arbeitssprache). Der **Kategorien-Baum** ist als Grundansicht umgesetzt (Umschalter Struktur/Kategorien; Auswahl filtert das Grid via `GET /objects?category=`); Zähler/Baum-Auswahl/„Nicht kategorisiert“ folgen. **Seit Phase-8-Review:** ein schlichtes `/products` lädt **keine** Objekte mehr automatisch – es erscheint ein Hinweis (`grid.select_tree_node`), und die Auswahl im Baum lädt den Teilbaum. URL-Filter (`?incomplete`/`?type`/`?ancestor`/`?category`/`?uncategorized`) laden gezielte Objekte; eine Baum-Auswahl setzt die URL via `history.replaceState`, sodass Save/Reload die Ansicht behält.

## 1. Grid (Hauptarbeitsfläche)

Das Grid ist der Ort, an dem Anwender die meiste Zeit verbringen. Es ersetzt die bisherige „Objektliste" als reine Anzeige und wird zur **Arbeitsfläche**.

### 1.1 Linke Navigation: Kategorien & Struktur

Ein linkes Panel bietet einen **Umschalter** zwischen zwei Sichten:

- **Kategorien (Grundansicht implementiert):** Es gibt **beliebig viele unabhängige Kategorie-Bäume**; der Anwender wählt, welcher Baum angezeigt wird. Die Kategorie-Bäume sind `category`-Objekte, deren `depends_on`-Elternteil der **Universal-Root** ist (der Universal-Root identifiziert die Bäume). Im Grid (`meadow/frontend/grid.py`) lässt sich über **zwei Icon-Buttons** (`account_tree` = Struktur, `category` = Kategorien; aktiver Button hervorgehoben, Tooltip) zwischen den Sichten wechseln; die Kategorien-Sicht lädt nur `category`-Knoten (`LazyTree`, Kinder via `GET /objects/{id}/children?count_members=true`, gefiltert auf `category`) und filtert bei Knoten-Auswahl das Grid über **`GET /objects?category=<id>`** (`category_member`, Aggregation – bewusst nicht über `?ancestor=`). Jeder Knoten zeigt einen **Zähler** (`memberCount`: Anzahl zugeordneter Objekte inkl. Unterkategorien). Über ein **Dropdown** (`ui.select` „Alle Bäume“ + einzelne Kategorie-Bäume) wählt der Anwender, **welcher Baum** angezeigt wird; „Alle Bäume“ zeigt alle Roots, ein einzelner Baum nur seinen Root. Ein **„Nicht kategorisiert“**-Eintrag (oben, `uncategorized_node`) listet Objekte **ohne Kategoriezuordnung** (via `GET /objects?uncategorized=true`, ohne `category`/`root`). Zuordnung über `category_member` (Aggregation, [kategorisierung.md](kategorisierung.md)). **Die Verwaltung der Kategorien** (Anlegen, Hierarchisieren, Umbenennen, Löschen) liegt separat auf `/categories` (Modul 6) – dieser Grid-Baum bleibt **reine Navigation**.
- **Struktur (implementiert):** Die **Pflegestruktur** (Kompositionsbaum `depends_on`, Universal-Root → Familien → Produkte → Varianten, [relationen.md](relationen.md)). Sie ist die Navigationsachse für Vererbung und Hierarchie. Im Grid (`meadow/frontend/grid.py`) wird der Baum links als **`LazyTree`** gerendert (lazy-geladen über `GET /objects/{id}/children`, siehe unten); **Auswahl eines Knotens filtert das Grid serverseitig auf den Teilbaum** (Eltern + Nachfahren via `GET /objects?ancestor=<id>`). Der Umschalter **Kategorien/Struktur** ist umgesetzt (siehe Kategorien-Punkt oben).
  - **Darstellung (implementiert):** Das linke Panel sitzt in einem **resizable `ui.splitter`** (`w-full`, Anfangsbreite 25 %, `limits=(0, 60)`, Drag-Handle zum Verstellen), nimmt die volle Hauptbreite **und -höhe** ein (`h-[calc(100vh-210px)]`), sodass das Grid den verfügbaren Bildschirmplatz ausfüllt. Ein **Panel-Toggle** in der Grid-Toolbar (`view_sidebar`, `toggle_panel`) klappt den Baum ganz ein/aus (`splitter.value` 0 bzw. 25); beim Einklappen nutzt das Grid die volle Breite. Der Card-Kopf ist **zweizeilig**: Zeile 1 enthält den **Sicht-Umschalter** als **Icon-Buttons** (`account_tree`/`category` in einem `ui.button_group`, aktiver Button `color=primary`, Tooltips), Zeile 2 das **Filterfeld** + **Button „Alle einklappen“** (`unfold_less`, `collapse_all()` via `tree.collapse()`). Ein „Alle aufklappen“ gibt es bewusst **nicht**: `expandAll()` in einem Lazy-Tree würde bedeuten, alle Nachkommen zu laden (N+1-Calls, Timeouts, riesiger DOM) — der Baum klappt deshalb **pro Knoten on demand** auf (lazy). So lässt sich auch ein **Zwischenzustand** (manuell teilweise zu-/aufgeklappt) eindeutig auflösen. Filterfeld und Buttons sind **ohne Umbruch** aneinander gebunden (`flex-wrap: nowrap`, Buttons `shrink-0`), sodass sie auch bei schmaler Baum-Darstellung auf einer Zeile bleiben. Die Card ist **padding-frei** (`p-0`), sodass der Baum bündig mit der Seitenüberschrift („Products“) ausgerichtet ist (keine weitere Einrückung). Der Baum füllt die Kartenhöhe (`min-height: 0`) und scrollt **intern** (`overflow-y: auto`), damit kein Überlauf über das linke Panel hinaus entsteht. Der **Universal-Root-Knoten wird verborgen** (übliche Darstellung eines reinen Container-Knotens): seine Kinder werden auf Top-Level angehoben (`tree_nodes = root_children`), es gibt also keine „Struktur“-Überschrift und keinen sichtbaren „Structure · root“-Eintrag. Knoten-Labels zeigen **Name + gedimmten Typ** (`tree`-Header-Slot, z. B. „Beispielprodukt · product“); namenlose Objekte zeigen den **Typ** statt der Rohen-ID. Das Filterfeld filtert den Baum serverseitig (`filter_tree_nodes`).
  - **Lazy Loading (implementiert):** Bei **tausenden/zehntausenden** Objekten skaliert der frühere Ein-Call-Endpunkt (`GET /objects/tree`) nicht mehr (große Antwort, langsames Rendern vieler Knoten). Der Baum lädt/rendert deshalb **nur das Nötigste**. Für die datenlastige Seite ist `response_timeout` auf 10 s gesetzt.
    1. **Daten laden — on demand:** Initial werden nur die **Top-Level**-Knoten (Kinder des Universal-Root) über `GET /objects/{id}/children` geladen; beim Aufklappen lädt derselbe Endpunkt die Kinder nach. Knoten tragen ein **`hasChildren`**-Flag (Aufklapp-Pfeil nur bei Kindern; kein Round-Trip für Blätter).
    2. **Viele direkte Kinder — paginieren:** `GET /objects/{id}/children` ist **paginiert** (`?limit`/`?offset`, Default 100); die UI lädt aktuell die erste Seite pro Knoten. *(Zähler/„Mehr laden“ folgt)*
    3. **Rendern — in der Karte scrollen:** LazyTree ist auf die Kartenhöhe begrenzt (`min-height: 0`) und scrollt **intern** (`overflow-y: auto`), sodass kein Inhalt über das linke Panel hinausläuft und keine störende, sich beim Scrollen „verschiebende“ Kante entsteht. `virtual-scroll` wird gesetzt, greift in dieser NiceGUI/Quasar-Version aber nicht (gerendert wird `q-tree--standard`, kein `.q-tree__scroll-area`) — die Sichtbarkeit wird daher über das interne Scrollen begrenzt.
    4. **Konsequenz — serverseitige Teilbaum-Filterung:** Mit Lazy Loading fehlt dem Client der volle Baum → die Grid-Filterung bei Knoten-Auswahl läuft **serverseitig** über `GET /objects?ancestor=<id>` (der Core berechnet den Teilbaum per BFS in `subtree_keys` und filtert `id IN array::map($ancestor_ids, |$k| type::record('object', $k))`).
    5. **NiceGUI-Pfad (Variante a — umgesetzt):** `ui.tree` hat keinen nativen Lazy-Load-Handler; Quasar-`@lazy-load` liefert den `done(children)`-Callback **nur clientseitig**. Lösung mit **`element.on(..., js_handler=...)`** in der **`LazyTree`-Unterklasse** (`meadow/frontend/lazy_tree.py`):
       - Knoten mit `hasChildren` werden mit **`lazy: true`** markiert (kein `children`-Schlüssel).
       - `self.on('lazy-load', py_handler, js_handler=<js>)`: Das JS fängt `args[0].done` ab, legt es global ab (`window.__meadowLazy[node.id] = done`) und sendet nur den Knoten-Key per `emit({ nodeKey })`.
       - `py_handler` lädt die Kinder via Backend und ruft `self.client.run_javascript("window.__meadowLazy[key](children)")` → QTree zeigt sie an.
       - **Kein Einklappen bei Auswahl:** `LazyTree.update()` ist ein **No-op** — NiceGUI sendet bei *jeder* Prop-Änderung (z. B. `selected`) das komplette `nodes`-Prop erneut, was die clientseitig nachgeladenen Kinder verwerfen und den Baum einklappen würde. Knoten-Änderungen (Suchfilter im Baum) laufen daher explizit über **`LazyTree.set_nodes()`** (sendet die (gefilterten) Knoten via `super().update()`).
    > **Verifikation (E2E):** Expandieren eines Knotens lädt seine Kinder nach; Knoten-Auswahl filtert das Grid serverseitig auf den Teilbaum (`?ancestor=` liefert Eltern + Nachfahren); die Auswahl eines **Unterknotens klappt den Baum nicht mehr zu** (das ausgewählte Produkt bleibt dargestellt). `GET /objects/{id}/children` überspringt defekte `depends_on`-Verweise auf nicht existente Objekte, sodass der Baum sauber bleibt.

Auswahl eines Knotens setzt den **Grid-Filter** auf den Teilbaum. Die Anzeige im Grid bleibt **flach** (Zeilen); die Hierarchie wird über eine **„Übergeordnetes Produkt"**-Spalte sowie den Strukturbaum sichtbar. Ein Baum direkt im Grid (Tree/Row-Grouping) ist im MVP bewusst nicht vorgesehen – AG Grid bietet das nur im lizenzierten Enterprise-Modul; Tabulator (`dataTree`) wäre die Open-Source-Alternative, falls das später zwingend wird.

### 1.2 Spalten & Ansichten

- **Konfigurierbare Spalten (implementiert):** Der Anwender wählt über einen **Spalten-Picker** („Spalten“-Button im Grid, `meadow/frontend/grid.py`), welche Attribut-Spalten sichtbar sind; Spalten sind **pinnbar** (ID standardmäßig links), in Breite und Reihenfolge anpassbar (AG-Grid-Standard). Die angebotenen Attributspalten stammen aus `GET /attribute-definitions`; Attribute sind zunächst ausgeblendet. Persönliche gespeicherte Ansichten folgen als nächster Teilschritt. *Seit Phase-8-Review:* Der Picker ist ein **`ui.dialog`** (mit „Schließen“-Button), kein `ui.menu` – Quasar-`QMenu`-Auto-Open öffnet in Firefox/Zen nicht (weder als Geschwister noch verschachtelt im Button), während `ui.dialog` browserübergreifend verlässlich öffnet (gleiches Muster wie der funktionierende „Ansichten“-Dialog).
- **Persönliche gespeicherte Ansichten (implementiert, MVP):** Ein benannter Satz aus `{Baum-Kontext, Filter, Spalten, Sortierung}` wird **pro Benutzer** gespeichert und per Klick wiederhergestellt. MVP: Der „Ansichten“-Dialog speichert die aktuelle **Spaltenauswahl** unter einem Namen in `app.storage.user` (pro Benutzer-Session, über Cookie persistiert), listet gespeicherte Ansichten und stellt sie per Klick wieder her (inkl. Löschen). Filter/Sortierung/Baum-Kontext werden noch nicht erfasst; diese Erweiterung sowie serverseitige Persistenz (Backend) folgen. Abgrenzung: Das ist eine **leichte UI-Ebene**, nicht die `saved_search`-Query-DSL bzw. materialisierte Collections (Phase 9, [gespeicherte-suchen-collections.md](gespeicherte-suchen-collections.md)); später kann die Advanced Search darauf aufsetzen.
- **Zellen-Darstellung:** Menschlich formatiert statt roh: `status` als farbiges **Badge**, `enum` als **farbige Tags**, quantifizierte Werte mit **Einheiten-Symbol** (z. B. `12,5 mm`), Datum **lokalisiert** (babel), Referenzen als **Chips** mit aufgelöstem Label.

### 1.3 Inline-Editing & Batch-Save

- **Direktes Zellen-Editing** für einfache Attributtypen (AG-Grid-Cell-Editors): `text` (Input), `number` (Zahlenfeld), `boolean` (Toggle), `enum` (Select), `date` (Datums-Picker), quantifizierte Werte (Zahlenfeld mit Einheiten-Symbol).
- **Batch-Save statt Einzel-Save:** Edits sammeln sich im Grid (gestaged). Ein **„Speichern"**-Button überträgt alle Änderungen **gesammelt** an den Kern; **„Verwerfen"** verwirft. **Geänderte Zellen werden markiert**, ein **„Ungespeicherte Änderungen"**-Zähler ist sichtbar. Gründe: wenig Requests, konsistente Validierung/Vererbung im Kern, sicheres Rückgängigmachen über mehrere Zellen. **Toolbar-Anordnung:** Der Panel-Toggle (Strukturbaum, `view_sidebar`) sitzt ganz links (andere Funktion), daneben der „Ungespeicherte Änderungen“-Zähler; **Speichern**, **Verwerfen**, **Ansichten** und **Spalten** sind **rechtsbündig** angeordnet, wobei **Verwerfen/Ansichten/Spalten** als **Icon + Tooltip** dargestellt werden („Speichern“ bleibt als primärer Button mit Text).
- **Deckelung des Batch-Saves (verbindlich):** Pro `POST /objects/batch-update`-Aufruf sind max. **500 Zeilen** erlaubt ([api-design.md](api-design.md)); das Grid speichert große, ungespeicherte Änderungsmengen in 500er-Blöcken, größere Auswahlen laufen über den Bulk-Wizard (async).
- **Abgelaufene Sitzung (implementiert):** Meldet der Kern beim Batch-Save einen ungültigen/abgelaufenen JWT (pro Zeile `success: false`), erkennt das Frontend das über `is_session_expired` (Fehlertext `invalid or expired token`), leert die Session und leitet zur Login-Seite um – statt einen fehlgeschlagenen Save anzuzeigen. Taucht die Meldung nur beim Schreiben auf (nicht beim Laden), liegt das an `GET /objects` ohne Auth (bewusste MVP-Vereinfachung).
- **Nicht inline editierbar** (Referenz-Picker, Medien/Assets, lange mehrzeilige Texte): Bearbeitung in einem **Modal-Editor direkt im Grid** – ohne die Grid-Position oder ungespeicherte Änderungen zu verlieren; der Modal-Edit landet wie ein Zellen-Edit im gestagten Batch. Das vollständige Formular bleibt per Zeilen-Aktion (z. B. Doppelklick / „Öffnen") erreichbar.
- **Mehrsprachige Felder im Grid:** standardmäßig wird nur die **Arbeitssprache** inline bearbeitet; zusätzliche Sprach-Spalten folgen später über den Spalten-Picker.
- **Vollständigkeits-Spalte (implementiert) & Filter (offen):** Eine farbige **Vollständigkeits-Spalte** (grau 0 %, orange 1–99 %, grün 100 %), gespeist aus dem Kern (`GET /objects?locale=`, Feld `completeness` der Arbeitssprache). Der Filter „nur unvollständige Produkte“ folgt mit der Filterleiste (siehe Abschnitt 4).

## 2. Produkt-Formular (Drill-down)

Das Formular öffnet ein einzelnes Objekt zur tiefen Bearbeitung und Anreicherung.

> **Stand (Phase 7, umgesetzt):** `<meadow/frontend/form.py>`, Route `/products/{object_id}`, erreichbar per **Doppelklick** auf eine Grid-Zeile (`cellDoubleClicked`). Umgesetzt: scrollbare Seite, **drei Abschnitte** (① **Stammdaten**: Objekt-ID read-only + `name` + Business-Key-/Pflicht-Attribute, ② **Attribute ohne Gruppe**, ③ **Attributgruppen** nach `position`), **einklappbare Abschnitte mit farbigem Header** (`header-class`), **tabellenartige, ausgerichtete Attributzeilen** (Kopfzeile Attribut/Wert + Zeilen `Label | Wert | Sprach-Icon`, `flex-1`-Felder, **gefüllte** Inputs), **Pflichtfeld-Sternchen** (`required_types`), **typspezifische Controls** (text/number/boolean/enum/date), **Hybrid-Mehrsprachigkeit** („Haupteditiersprache“-Selektor **in der Kopfzeile** + **Sprach-Icon-Button** je mehrsprachigem Attribut → breiter **Dialog** `w-[34rem]`, der alle Datensprachen aus `GET /languages` bearbeitet und die **Arbeitskopie** `edited` liest/schreibt, sodass angewendete Werte beim erneuten Öffnen erhalten bleiben), **Vererbungs-Marker** (gedimmt + Icon + Tooltip), **Sprung-Menü** (`ui.select` „Springe zu“, klappt die Zielgruppe auf und scrollt dorthin via `scrollIntoView`), **Umschalter „Nur fehlende Pflichtfelder“** (`ui.switch`, filtert die Abschnitte/Zeilen auf `missing_required` via `ui.refreshable`), **Enum-Option-Creation** (`+`-Button am Enum-Dropdown → Dialog, `update_attribute_definition` via `PATCH /attribute-definitions/{id}`), **Vollständigkeits-Widget** und **Status-Auswahl**; Speichern via `PATCH /objects/{id}` mit **Fehlergrund-Anzeige** (Core-`error`-Meldung, z. B. `validation failed: sku: SKU is required (required)`). *Hinweis:* Attribute als **Zeilen** in `ui.expansion`, nicht über `ui.table`-Zell-Slots (NiceGUI-Tabellen-Slots hosten keine zuverlässig pro Zeile unabhängigen Eingabewidgets). Noch offen: Pinned Attributes. Der **Relationen-Abschnitt** (Graph-Kanten, Abschnitt 2.6) ist implementiert.

### 2.1 Layout

- **Eine scrollbare Seite** mit Attributgruppen als **überschriebene, einklappbare Abschnitte** (Accordion; Standard aufgeklappt). Ein **Sprung-Menü** oben (`ui.select` „Springe zu“) navigiert zu einer Gruppe (und klappt sie ggf. auf, `scrollIntoView`). Keine Tabs pro Gruppe – beim Anreichern arbeitet man über Gruppengrenzen hinweg, alle Gruppen sind gleichzeitig sichtbar.
- **Sichtbarkeit & Reihenfolge** der Abschnitte steuert das **Template** (nur Gruppen mit gültigen Attributen für den Typ; Reihenfolge aus `attribute_group.position` bzw. der Template-Reihenfolge).
- **Objekttyp-Zuordnung (Kernprinzip):** Ein **Attribut** erscheint für einen Typ nur, wenn `applicable_types` ihn enthält (leer = überall) – so erscheinen nicht alle Attribute überall. Eine **Gruppe** erscheint für einen Typ, wenn ihr optionales `applicable_types` ihn enthält bzw. (leer) wenn mindestens ein Mitglied-Attribut für den Typ gilt. **Viele-zu-viele:** Ein Attribut kann in **mehreren** Gruppen erscheinen; am Objekt ist es **ein** Feld (gleiches `edited[attr_name]`), das in mehreren Abschnitten gerendert wird (Änderungen synchronisieren sich über die gemeinsame Arbeitskopie).
- Umschalter **„Nur fehlende Pflichtfelder“** (implementiert): ein `ui.switch` im Formular filtert die Abschnitte/Zeilen auf die **fehlenden Pflichtattribute** (`missing_required` aus `GET /objects/{id}`), Gruppen ohne fehlende Felder werden ausgeblendet; Zustand in `app.storage.user`, Umschaltung via `ui.refreshable`.
- Später (Phase 9): **Pinned Attributes** (immer sichtbare Seitenleiste) und **Attribut-Suchleiste** im Formular.

### 2.2 Sprache (Hybrid-Modell)

- **Header-Sprach-Umschalter** („Haupteditiersprache“; Selektorbasis = Sprachen aus `GET /languages` mit `parent == lang_root`, `edit_lang` in `app.storage.user`) bestimmt den primären Anzeige-/Eingabekontext.
- **Mehrsprachige Felder** zeigen **inline** den Wert der Haupteditiersprache; ein **Sprach-Icon-Button** (ohne Zählertext) öffnet einen **breiten Dialog** zur Bearbeitung **aller Datensprachen** (aus `GET /languages`, inkl. regionaler Varianten). Der Dialog liest/schreibt die **Arbeitskopie** (`edited`), daher bleiben angewendete Werte auch **ohne zwischenzeitliches Speichern** beim erneuten Öffnen erhalten und fließen in das Inline-Feld zurück. *Abweichung vom Entwurf:* statt **einer Spalte pro aktiver Datensprache** (bei vielen Datensprachen unübersichtlich) wird die Editierbarkeit über Haupteditiersprache + Sprach-Icon-Dialog realisiert. Die aktive Datensprach-Menge liefert `GET /languages`; welche Datensprachen angeboten werden, ist jetzt über das Feld **`active`** im Sprachbaum konfigurierbar (Sprachbaum-Administration, Modul 8 – das Produkt-Formular filtert auf `active`-Sprachen). Nicht-mehrsprachige Felder haben nur einen Wert.
- **Fallback-Semantik sichtbar:** Fehlt ein lokaler Wert in der Haupteditiersprache, wird der aufgelöste Wert (z. B. `de` für `de-AT`) **gedimmt mit einem Fallback-Icon/Marker** und Tooltip angezeigt; Tippen setzt einen lokalen Override, Löschen entfernt ihn (zurück zum Fallback). Sprachauflösung gemäß [sprachbaum-mehrsprachigkeit.md](sprachbaum-mehrsprachigkeit.md).
- „Reiter pro Sprache" ist **nicht** vorgesehen; der Reiter-Gedanke bleibt nur als sekundäres Navigationsmittel für Gruppennavigation übrig.

### 2.3 Vererbungs-UX

Entlang der Kompositionskette `depends_on` ([datenwertvererbung.md](datenwertvererbung.md)):

- **Vererbte Werte werden in-place angezeigt**, aber klar als „nicht hier gepflegt" markiert: Wert gedimmt + **Vererbungs-Icon mit Tooltip** („vererbt von [Name/ID]" aus `from_object`).
- **Editieren = Override:** Ändern legt einen lokalen Wert am Objekt an (keine Sonder-Interaktion nötig).
- Auf überschriebenen Feldern erscheint die Aktion **„Zurück auf vererbt"** (Resync), die den lokalen Override entfernt.
- **Unterscheidung „nicht gepflegt" vs. „leer gesetzt"** (Vererbungsunterbrechung) über ein **Feld-Kontextmenü** mit zwei Aktionen: **„Leer setzen"** (explizit leer, unterbricht Vererbung) und **„Auf vererbt zurücksetzen"** (lokalen Wert entfernen, erbt wieder). Ein Marker zeigt den Zustand („leer gesetzt/Unterbrechung" vs. „vererbt").
- Ein **„Warnhinweis bei Konflikten"** entfällt: Im Ein-Eltern-Modell gibt es keine Konflikte.

### 2.4 Wertedarstellung

- **Typspezifische Steuerelemente:** `text` → Input/Textarea, `number` → Zahlenfeld, `boolean` → **Toggle**, `date` → lokalisierter Datums-Picker, `enum` → Select mit **farbigen Tags** in der Anzeige, `reference` → verlinkte **Chips** (Klick → Sprung zum referenzierten Objekt).
- **Einheiten-Umschalter** am Eingabefeld (Darstellung/Eingabe in anderer Einheit derselben Dimension; Speicherung in kanonischer SI-Einheit, [einheiten.md](einheiten.md)).
- **Enum-Option-Creation im Formular (implementiert):** Ein **`+`-Button** am Enum-Dropdown öffnet einen Dialog („Option hinzufügen“ / „Neuer Wert“); der neue Wert wird per `PATCH /attribute-definitions/{id}` in `constraints.enum_values` geschrieben und sofort als Auswahl gesetzt (MVP). Selects/Inputs nutzen den **`filled`-Stil** (Hintergrund statt Unterstreichung).
- **Enum-Optionen pflegen (umgesetzt, Phase 9):** Zentrales Verwalten/Entfernen von Enum-Optionen (`constraints.enum_values`) in der Attributdefinition-Verwaltung mit **Nutzungscheck** — der Editor zeigt die Optionen als Liste (✕ je Option + „Option hinzufügen“); beim Entfernen prüft `GET /attribute-definitions/{id}/enum-usage` die Nutzung: unbenutzt → entfernen, benutzt → **Umhängen/Migration**-Dialog (Ziel wählen oder neuer Wert) und `PATCH /attribute-definitions/{id}` mit `enum_remap` (der Kern migriert die Objekte und entfernt den Wert; ohne Remap 409).
- **Suchbarer Referenz-Picker im Formular (implementiert):** Für `reference`-Attribute zeigt ein Suchfeld Treffer (`GET /objects/picker`, gefiltert nach erlaubten Zieltypen aus `constraints.target_types`); Auswahl **setzt den Attributwert auf die Ziel-Objekt-ID**, Anzeige als **Chip** (Label + Typ, entfernbar). Die Vollständigkeits-Anzeige innerhalb des Pickers folgt später. *Hinweis:* Das ist der **Attribut-`reference`-Typ** – ein **skalarer** Link zu genau einem Zielobjekt (Wert = Ziel-Objekt-ID). Die echten, typisierten **Graph-Kanten** (Relationen) werden separat in Abschnitt [§2.6](#26-relationen-graph-kanten) behandelt.
- **Referenz-Picker im Grid (Phase 7, umgesetzt):** eigene Spalte **`_refs` (🔗)**; Klick öffnet ein **Modal** mit dem Objektnamen, den vorhandenen Referenzen **gruppiert und sortiert nach Relationstyp** (Komposition `rel_depends_on` zuerst, danach Aggregationen nach Label; Typ-Label aus `GET /relation-definitions`), als **Chips** (aufgelöste Labels, Entfernen-Button mit Ausnahme der Komposition `rel_depends_on`), mit **Leerzustand** (`grid.ref_empty`) ohne Referenzen, einem **Relationstyp-Dropdown** (aus `GET /relation-definitions`, gefiltert auf `kind == 'aggregation'`) und einem **Suchfeld** (→ `GET /objects/picker`); ein Treffer wird per Klick als Referenz angelegt (`POST /references`).

### 2.5 Kopfzeile & Status

- **Vollständigkeits-Widget im Formular-Header** (farbig; Klick → Aufschlüsselung nach Sprache + Liste fehlender Pflichtfelder → Sprung zum Feld).
- **Status-Badge** + **erlaubte Übergänge** (geliefert vom Kern, Statusmaschine im Python-Service, [workflow-freigaben.md](workflow-freigaben.md)) als Aktionen; Statuswechsel wird im Audit-Log protokolliert.
- Referenzen/Kategorien des Objekts (Graph-Kanten) sind editierbar – siehe Abschnitt [2.6](#26-relationen-graph-kanten).

### 2.6 Relationen (Graph-Kanten)

Beschreibt die **typisierten Relationen** zwischen Objekten (`reference`-RELATION + `relation_definition`: Komposition `depends_on`, Aggregationen `category_member`/`collection_member`/`related`) im Produkt-Formular. Abgrenzung zu Abschnitt 2.4: Dort das **skalare** Attribut `reference`; hier echte **Graph-Kanten** mit eigener Semantik (Vererbung/Löschkaskade vs. lose Verknüpfung).

> **Nicht verhandelbar – Graph/Performanz-USP:** Relationen sind bewusst als **SurrealDB-Graph** modelliert (native RELATION-Kante, Edge-Queries `->reference->object`, Indizes auf `reference`/`definition_id`/`in`), um gegenüber klassischen PIMs (denormalisierte Beziehungstabellen) einen **Performanzvorteil** zu erzielen. Das Frontend ist ein **dünner View über den Graphen** und darf diese Semantik **nicht** durch eine „UI-getriebene“ Implementierung verlieren:
  - Alle Zugriffe laufen über die **Kern-Endpunkte** (`GET /objects/{id}/references?locale=`, `POST /references`, `DELETE /references/{id}`, `PATCH /objects/{id}/parent`, `GET /objects/picker`, `GET /relation-definitions`) – nie über client-seitige Joins oder eine Materialisierung des Graphen im Browser.
  - Die **Treffer-/Label-Suche** nutzt die **server-seitige Suche** des Kerns (`picker`, Volltext + Typfilter) – kein client-seitiges Filtern großer Mengen.
  - Der Kern liefert je Relation bereits aufgelöste `in_object`/`out_object`-Summaries (`{id, type, label, status}`); das Frontend darf **nicht** nachladen bzw. objektweise joinen.

**Umsetzung (MVP, implementiert):**
- **Eigener Akkordeon-Abschnitt „Relationen“** (`build_relations_section` in `meadow/frontend/form.py`; gleicher farbiger Header wie die übrigen Abschnitte, `flex-1`), **intern nach Relationstyp gruppiert** aus `GET /relation-definitions`: Komposition `depends_on` zuerst, danach Aggregationen nach Label (Sortierung wie im Grid-Modal). **Zähler am Abschnitts-Header** (Anzahl Relationen) für Übersicht.
- Pro Typ eine **farbige Karte** (orange = Komposition, hellblau = Aggregation) mit **Kopf aus Label + „Komposition“/„Aggregation“-Badge** + Zähler + „Hinzufügen“ (Aggregation) und Kurzhinweis („Vererbung & Löschkaskade“ bzw. „lose Verknüpfung“) → macht die Semantik des Angelegten sofort sichtbar. Beim `depends_on` den **einen** Elternteil (1:n) mit „Umhängen“ (`PATCH /objects/{id}/parent`). *Hinweis:* Der Inhalt des Expansions wird **innerhalb** des Kontexts erzeugt (`with expansion:` → `content`), sonst liegt er als Geschwister-Element außerhalb und bleibt beim Einklappen sichtbar.
- Pro Typ **tabellarisch ausgerichtete Zeilen** (Ziel-Label | Typ | Aktionen) als `ui.row`/`ui.expansion`; bei Kanten mit Metadaten (Menge/Position) später als echtes Grid. **„Hinzufügen“-Picker** (gefiltert nach erlaubten Zieltypen), Entfernen per Kreuz; Klick auf ein Ziel öffnet das Zielobjekt.
- **Integration in bestehende Muster:** Das **Sprung-Menü** listet den Abschnitt; der **„Nur fehlende Pflichtfelder“**-Umschalter berücksichtigt fehlende Pflicht-Beziehungen (z. B. Komposition). Kein neues Klick-Muster, wenige Klicks.

**Kategorien (produktzentriert, umgesetzt):** Ein eigener Abschnitt **„Kategorien“** im Formular (`form.py`, `build_categories_section`) zeigt den/den Kategorie-Baum/Bäume als **anhaktbaren `ui.tree`** (`tick_strategy='strict'`), **vorbelegt** mit den `category_member`-Kategorien des Objekts (aus `GET /objects/{id}/references`). An-/Abhaken legt/entfernt die `category_member`-Kante sofort (via `POST`/`DELETE /references`) – Analogie: Ticken = Klassifizieren wie in Akeneo. Die generische `rel_category_member`-Karte im **Relationen-Abschnitt** wird dort bewusst **ausgeblendet** (`build_relations_section` überspringt `rel_category_member`), um eine Dopplung zu vermeiden; die Objekt-Navigation nach Kategorie bleibt der Kategorien-Baum im Grid.

**Später (Phase 9):**
- **Baum-Auswahl für Zielobjekte** (Zielobjekt über Kompositions-/Kategorien-Baum wählen, nicht erlaubte Zieltypen **ausgegraut**/gefiltert) – nutzt `GET /objects/tree`/`/objects/{id}/children` bzw. den Kategorien-Baum; Alternativ ein erweitertes Grid im Picker (Stil Akeneo/Pimcore).
- **Kanten-Metadaten-Editor (umgesetzt, Phase 9):** Liefert ein Relationstyp `attributes` (siehe `relationen.md`), öffnet „Hinzufügen“ bzw. ein **Bearbeiten**-Stift je Aggregations-Kante einen **typspezifischen Dialog** (`open_edge_editor` in `form.py`, `rel_def_by_key`/`rel_attr_defs`): pro deklariertem `attribute_definition` ein Feld passenden Typs (Text/Eingabe, Zahl, Schalter, Enum-Select; ein vorhandener Enum-Wert wird in die Optionen aufgenommen, damit er nicht verloren geht). Werte werden in `reference.attributes[name]` gespeichert (`create_reference(attributes=…)` bzw. `PATCH /references/{id}` → `client.update_reference`); die Zeile zeigt die Kanten-Werte als Kurzfassung (`key=value, …`). Eine Relationstyp-Admin-Seite `/relation-definitions` pflegt die Typen (inkl. `attributes`/Restriktionen).

## 3. Massendatenpflege

### 3.1 Bulk-Edit-Wizard (MVP)

- **Auswahl:** „Alle Treffer des aktuellen Filters" / „alle auf dieser Seite" / angehakte Zeilen (Mehrfachauswahl des Grids).
- **Ablauf:** Operation wählen → konfigurieren → **Bestätigen** → Ausführung als **Hintergrundjob** mit Fortschritt und **Report** (Benachrichtigung; Anwender arbeitet weiter).
- **Job-Status per Polling (verbindlich):** Solange ein Bulk-Job läuft, pollt das Frontend den `job_run` per REST (`GET /jobs/runs?ids=…`, [api-design.md](api-design.md)) und zeigt Status/Fortschritt an; nach Abschluss erscheint der **Report** (Erfolg/Fehler pro Objekt) aus `job_run.result` (Benachrichtigung).
- **Operationssatz (passend zum Datenmodell):**
  - **Attributwert setzen** (ersetzt; für Text/Zahl/Boolean/Datum/Enum),
  - **Attributwert leeren** (auf „nicht gepflegt" zurücksetzen – beachtet die Vererbung: erbende Kinder fallen auf den vererbten Wert zurück),
  - **Status ändern** (Workflow-Übergang),
  - **Kategorie hinzufügen / entfernen** (Kategoriebaum-Auswahl),
  - **Elternobjekt ändern** (Re-Parenting in Bulk, mit Zyklenschutz und Typrestriktionsprüfung; bewusste Kaskadenwirkung),
  - **Massen-Löschen** (Soft-Delete-Kaskade über den Teilbaum; Warnung „irreversibel").
- **Validierung:** Der Kern prüft pro Objekt (Typrestriktionen, Eindeutigkeit, Workflow); Verstöße erscheinen im Report.

> **Stand (Bulk-Wizard, Phase 7, umgesetzt):** Der `fact_check`-Button in der Grid-Toolbar (`meadow/frontend/grid.py`) öffnet den Bulk-Dialog: Auswahl-Scope (**„Alle Treffer des Filters“** (aktuelle `all_rows`), **„Alle auf dieser Seite“** (aktuelle AG-Grid-Pagination-Seite über `paginationGetCurrentPage`/`paginationGetPageSize`; bewusst ohne `getDisplayedRowAtIndex`, da RowNodes zirkuläre Referenzen enthalten und die Socketio-Serialisierung mit „Maximum call stack“ crasht) und **„Ausgewählte Zeilen“** (via `grid.get_selected_rows()`)), Operations-Select (7 Operationen) und eine **dynamische Konfigurationsfläche** (Attribut+Wert, Status, Kategorie, Elternobjekt, Lösch-Warnung). `POST /objects/bulk` (`crates/pim-core/src/api/objects.rs`) validiert Editor-Rolle/Operation und reiht einen `bulk_operation`-Job ein; der Worker (`meadow/worker/bulk.py`) wendet die Operation pro Objekt an und liefert `job_run.result` (`op`, `processed`, `succeeded`, `failed`, `results[]`). Das Frontend pollt `GET /jobs/runs?ids=…` und zeigt den Report (Erfolg/Fail pro Objekt). Die Auswahl wird über die Grid-API `get_selected_rows()` gelesen (der NiceGUI-`selectionChanged`-Event überträgt **kein** `selectedRows`). **Seit Phase-8-Review:** Kategorie- und Eltern-Picker werden **lazy** geladen (`load_category_options`/`load_parent_options` in `grid.py`) – nur wenn die entsprechende Operation gewählt wird, nicht bei jedem Seitenaufbau (behebt das „alle Objekte laden“-Problem des Wizards).

## 4. Vollständigkeit (Completeness)

- **Berechnung im Rust-Kern** (nicht im Frontend): Prozent der **Pflichtattribute des Typs** (aus `required_types`), die gesetzt sind – inklusive **vererbter Werte** (ein vererbtes Pflichtfeld gilt als gesetzt). Granularität im MVP: **pro (Objekttyp × Sprache)**. Kanäle (per-Kanal-Vollständigkeit) folgen mit den kanalspezifischen Freigaben (später).
- **Anzeige überall:**
  - **Grid-Spalte (implementiert)** (farbig: grau 0 %, orange 1–99 %, grün 100 %) mit Filter „nur unvollständige Produkte“ (Filter folgt; Spalte liefert das Kern-Feld `completeness` der Arbeitssprache).
  - **Formular-Widget** im Header (farbig; Klick → Sprachaufschlüsselung + Liste fehlender Pflichtfelder → Sprung ins Feld) und Umschalter „nur fehlende Pflichtfelder".
  - **Dashboard-Kacheln** als Aufgaben-Shortcuts (Abschnitt 5).
- MVP bewusst **ohne** „Improvable/empfohlen"-Stufe; diese folgt später.

## 5. Dashboard (Arbeitsübersicht)

> **Stand (Phase 7, umgesetzt):** `meadow/frontend/views.py` (`views.home`, `GET /`, `response_timeout=15`) lädt `GET /objects?limit=1000&locale=`, `GET /system/logs` und `GET /jobs/runs` und rendert Kacheln/Listen. Kein Audit-Read-Endpoint ist vorhanden, daher zeigt „Letzte Aktivität“ aktuell die **System-Logs** (`GET /system/logs`, admin) als Proxy statt eines Audit-Auszugs.

- **Kacheln:** Anzahl Objekte pro Typ/Status (aus `GET /objects`, farblich abgesetzte Kacheln je Typ; Status als Badges mit Zähler).
- **Vollständigkeits-Kacheln als Aufgaben-Shortcuts (implementiert):** z. B. „23 unvollständig (product)“ – Klick öffnet das **Grid mit voreingestelltem Filter** `/products?incomplete=1&type=<typ>` (das Grid filtert client-seitig auf `completeness < 100` der Arbeitssprache und optional den Typ). Das Dashboard wird damit zum **Einstieg in die Pflegearbeit** („Was fehlt?“), ohne eine eigene Aufgabenmaschine.
- **Letzte Aktivität** (System-Logs) und **laufende/letzte Jobs** (Status aus `GET /jobs/runs`, [jobs-scheduler.md](jobs-scheduler.md)).
- Bewusst **nicht im MVP** (später, Phase 9): Starred-Entitäten, Work Areas/Aufgabenwarteschlangen, Kanäle.

> **Performanz-Beobachtung (behalten, Phase 7/8):** Das Dashboard aggregiert client-seitig aus `GET /objects?limit=1000` (alle Objekte inkl. `completeness` der Arbeitssprache) die Kacheln (Anzahl pro Typ/Status, unvollständige je Typ). Bei **großen Datenmengen** wird der Aufbau dadurch langsam – teils werden Daten geladen/analysiert, die gar nicht gebraucht werden, weil die API aktuell keine gezieltere Möglichkeit bietet. **Haltung:**
> - Im Zweifel solche Kacheln **nicht anzeigen** oder auf das Nötigste begrenzen (z. B. nur die Standard-Typen, `limit` reduziert, spätes/gestertes Laden).
> - Falls sinnvoll, stellt der **Kern** eine effiziente Aggregation bereit (z. B. `GET /dashboard/stats` bzw. `GET /objects/stats`): nur die wenigen benötigten Zahlen (Anzahl pro Typ/Status, unvollständige je Typ für eine Sprache) **server-seitig** berechnet – ohne dass die UI alle Objekte ziehen muss.
> - **Nicht verhandelbar:** Nur weil die UI etwas braucht, wird die **Performanz des Kerns nicht gefährdet** – ein Stats-Endpunkt muss dem Graph-/Performanz-USP genügen (Indizes, Edge-Queries; keine Vollscans/teuren Traversierungen allein fürs Dashboard). Follow-up in Phase 8 (Performance/Benchmarks) bzw. Phase 9.

> **Stand (Phase 8, umgesetzt):** Das Dashboard nutzt jetzt **`GET /objects/stats?locale=<code>`** server-seitig (kein client-seitiges `GET /objects?limit=1000` mehr, kein 1000-Cap/Payload-Transfer). Der Stats-Endpunkt wurde im Phase-8-**Load-Testing** weiter optimiert: `completeness::compute_batch` berechnet die Unvollständigkeits-Zählung mit **einer** `depends_on`-Edge-Query + In-Memory-Walk (`resolve_missing_in_memory`) statt einer Query pro Ebene/Objekt, plus Fast-Path in `compute_with_required`. Messung: `GET /objects/stats` ~175 ms isoliert → **~45–64 ms** isoliert / ~109 ms p50 unter Last (bei 57 Objekten), identische Aggregationswerte. Load-Test-Tool: `scripts/load_test.py`.
