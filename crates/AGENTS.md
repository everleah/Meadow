# crates — Rust Source Code

## Purpose

Owns the Rust workspace (root `Cargo.toml`) and all Rust crates. The core service `pim-core` is the headless REST API (Axum + utoipa OpenAPI): sole write access to SurrealDB, JWT authentication/authorization, scheduler, and CRUD-event publishing to NATS JetStream.

## Ownership

- Root `Cargo.toml` (workspace) and every crate under `crates/`.
- `crates/pim-core/` — the PIM core service.

## Local Contracts

- Implementation stays consistent with `plan/meadow-pim-architektur.md` (sections 4–7, 9) and its detail documents; otherwise the plan is updated in the same change.
- Rust Edition 2024; MSRV 1.90 (`surrealdb` → `roaring`). `jsonwebtoken` requires a crypto backend feature (`rust_crypto` is used; `aws_lc_rs` is faster but needs NASM + CMake on Windows).
- `pim-core` module layout: `src/lib.rs` + `src/main.rs` (thin entry); top-level modules `config`, `db`, `error`, `event`, `audit`, `auth`, `cache`, `language`, `log_cleanup`, `inheritance`, `completeness`, `jobqueue`, `rate_limit`, `rules`, `scheduler`, `schema`, `seed`; API handlers in `src/api/{health, auth, objects, attribute_definitions, attribute_groups, jobs, keys, languages, references, rules, search, system, users, groups, imports, connectors, units}`.
- `cache::MetaCache` (in-memory) caches the multilingual/inheritable attribute names and the language fallback chains; attribute-definition writes invalidate it. Redis remains optional for multi-instance (plan Phase 3).
- JWT auth (`auth.rs`): HS256 via `jsonwebtoken`; config through `JWT_SECRET`/`JWT_TTL_SECONDS`. Roles: `superadmin`, `admin`, `editor`, `viewer`. A default `superadmin` (`admin`/`admin`) is seeded in dev when no `user:admin` exists. `Claims` carries an optional `impersonator: Option<Impersonator>` (`{sub, username}`) set for impersonation sessions.
- **Impersonation** (`src/api/auth.rs`, `POST /auth/impersonate/{user_id}`, **superadmin only**): issues a normal JWT for the target `user` (`sub`, `username`, `roles`, `token_version`, `exp`) plus an `impersonator` claim (acting superadmin). Rejects self-impersonation (400) and non-active targets (400); `GET /auth/me` returns the `impersonator` claim so the UI can show a banner. Audited as `user_impersonated`. This is a test/support aid, not a privilege-escalation path — the token adopts the target's roles.
- `POST /system/logs` accepts a machine-to-machine `X-Api-Key` (`LOG_INGEST_API_KEY`) or, as a dev fallback, an admin JWT. Full-text search (`POST /search`) uses analyzer `meadow_std` and index `idx_object_attributes_fulltext` over `object.attributes`. `GET /system/settings` also accepts the API key (machine-to-machine config read for the worker). Curated log categories are `app|job|rule|auth|integration`; the core's own rule logs use `rule` (singular). `GET /system/settings` returns a flat `{key: value}` map; with **`?include_source=true`** it returns `{key: {value, source}}` (`default`|`env`|`db`) for the admin UI (the worker keeps using the flat form). Settings: `log_persist_level` (DEBUG|INFO|WARN|ERROR|CRITICAL), `log_persist_categories` (array), `log_retention_days` (7–90), `log_rate_limit` (>0); `PUT /system/settings/{key}` persists + audits, `DELETE /system/settings/{key}` resets to default.
- Synchronous rule evaluation (`rules.rs`): the core loads `active` `business_rule` records, builds the candidate view, and calls the Python worker over NATS request/reply (subject `rules.evaluate`) in the object write path. Fail-closed: validation errors reject with 400, a rule that fails (exception/timeout) rejects with 500, an unreachable worker rejects with 503; `RULES_DEGRADE=true` degrades to "skip rules" on transport failure. Circuit breaker: a `failure_count` on the rule auto-disables it after `RULES_BREAKER_THRESHOLD` (default 3) consecutive failures and writes an audit entry + system log; success resets the counter. Config: `RULES_NATS_URL`, `RULES_SUBJECT`, `RULES_COMPILE_SUBJECT`, `RULES_TIMEOUT_MS`, `RULES_DEGRADE`, `RULES_BREAKER_THRESHOLD`.
- Business-rule CRUD (`src/api/rules.rs`, endpoints `/rules`): list/get are open to all authenticated roles; create/update/activate/disable require `admin`/`superadmin`. Create/update/activate compile-check the script via the worker (subject `rules.compile`); invalid scripts reject with 400, an unreachable worker with 503. New rules start as `draft`; `name` is unique (409); every change bumps `version` and is audited. `POST /rules/{id}/dry-run` (admin/superadmin) evaluates a single rule against a real object (`object_id`) or a constructed `object`, read-only and audited. `POST /rules/{id}/test-batch` (admin/superadmin, Rule Lab) evaluates a rule against a selection of real objects (`TestBatch { object_ids }`), read-only, one NATS evaluation per object, audited as `rule_test_batch`; `RuleSpec` is `Clone` so the spec can be reused across the batch. `POST /rules/{id}/recompute` (admin/superadmin) queues a `business_rule` recompute job over the rule's object set (only `active` `computed`/`bulk` rules; see job management).
- Computed-attribute enforcement (`rules.rs::resolve_computed`): the write path validates that every value a `computed` rule produces is declared as `computed: true` in `attribute_definition`; undeclared or non-computed writes reject the save with 400 (fail-closed).
- Attribute catalog (`src/api/attribute_definitions.rs` + `src/api/attribute_groups.rs`, tables `attribute_definition`/`attribute_group`): `attribute_definition.group_ids` is `TYPE option<array>` of full group record-ids (`attribute_group:<key>`), an inline many-to-many (no `attribute_group_member` join table) — **option** because records created before group enforcement may lack the field (the code guards with `group_ids ?? []`); the create handler always writes `[]` when none. `attribute_group.applicable_types` (`TYPE array`) restricts the object types a group shows (empty = derived from members). `DELETE /attribute-definitions/{id}` (admin) loads the definition via `LET $obj = type::record('attribute_definition', $key)` (record-key, **not** `WHERE id = $id`), counts objects carrying a value with `attributes.<name> IS NOT NONE` (`IS DEFINED` is unreliable for the `object.attributes` map — it returns true for absent keys), rejects with 409 when in use unless `?force=true`, which deletes and queues a `bulk_operation` run with `op=clear_attribute`. `DELETE /attribute-groups/{id}` (admin) also strips the group id from matching definitions' `group_ids` via `array::difference(group_ids ?? [], [$gid])` (`??` guards `NONE`; `array::contains` is **not** a valid function in the embedded SurrealDB — use the `IN`/`CONTAINS` operator).
- Resolved view in the write path: `create_object`/`update_object` evaluate rules against own + inherited (`resolve_inheritance`) + language-resolved (`resolve_attributes`) values via `?locale=`; only own + computed values are persisted (inherited values never become own values).
- Inherited-computed recompute cascade (`rules.rs::inherited_computed_rules` + `rules.rs::queue_inherited_cascade`): after an attribute update (`apply_object_update`), the write path schedules a `business_rule` recompute job per affected rule whose `attribute_definition` has `computed_reads_inherited: true` (query `attribute_definition WHERE computed AND computed_reads_inherited`, join to `business_rule` by `name` for `type='computed' AND state='active'`). Descendants are taken from `references::subtree_keys` (expects the **full** `object:` id), filtered by the rule's `applies_to`, and each `business_rule` job carries the affected objects as **full** `object:` ids (`object_ids`), `trigger: cascade`, and an optional `locale`. Best-effort — a queue hiccup never fails the save. The worker (`meadow/worker/business_rules.py`) loads these objects with `?resolve_inheritance=true[&locale=…]` so computed rules see inherited values.
- Object deletion (`src/api/objects.rs::delete_object`, `DELETE /objects/{id}`, editor+): **soft delete** with cascade over the composition subtree (`subtree_keys`, BFS over `rel_depends_on`). Sets `deleted_at`/`deleted_by` on the object and every `depends_on` descendant, removes all reference edges touching a deleted object (`DELETE reference WHERE in IN $recs OR out IN $recs`), writes one `object.deleted` outbox event (`changes.cascade`/`object_ids`), and audits `object_deleted`. The universal root (`object:object_root`) is undeletable (400). Soft-deleted objects are hidden by the `deleted_at IS NONE` filter added to the object queries (`GET /objects`, `GET /objects/{id}`, `GET /objects/by-source`, `GET /objects/picker`, `GET /objects/by-key`, `GET /objects/{id}/children`). Aggregation edges never cascade — they are removed for the deleted objects, but the connected objects stay intact.
- Rule warnings and `log()` output from evaluations are persisted as curated `log_entry` rows (`service: pim-core`, `category: rule`; warnings as WARN, `log()` with its script-provided level), best-effort.
- Eventsystem (`event.rs`, table `outbox_event`): CRUD operations write an event **atomically** with the change into the outbox (`CREATE outbox_event CONTENT $outbox;` inside the CRUD transaction; `object_id` via `type::string($obj.id)` for newly-created records) and a background relay (`event.rs::run_relay`) publishes `pending` events to NATS JetStream `events.crud` (stream `EVENTS`, WorkQueue retention with `max_age`/`max_bytes`), marking each `published` (`published_at`). Event types `object.created|updated`, `reference.created|deleted`, `attribute_definition.created|updated`; `object.deleted` follows with soft delete (Phase 7). Config: `EVENTS_NATS_URL`, `EVENTS_STREAM_MAX_AGE_DAYS`, `EVENTS_STREAM_MAX_BYTES`, `EVENT_RELAY_INTERVAL_S`. **Outage behavior (verified Phase 8):** if NATS is unreachable the relay logs `WARN ... event relay cycle failed` and events stay `pending`; writes still succeed (transactional outbox — the outbox is the source, NATS only the transport) and events are re-delivered once NATS returns.
- Job management (`src/api/jobs.rs`, tables `job_definition`/`job_run`): admin-only CRUD for definitions (`GET/POST /jobs`, `GET/PATCH /jobs/{id}`), editor+ read of runs (`GET /jobs/{id}/runs`, `GET /jobs/runs?ids=&status=`), and `PATCH /jobs/runs/{run_id}` (worker status update; `X-Api-Key` or admin). Job types `outbound_export|inbound_import|business_rule|bulk_operation`; run statuses `pending|running|success|failed|retry`. `job_run.job_definition_id` is `option<string>`: `None` for ad-hoc jobs (rule recompute). `running`/`retry` clear a stale `error`/`result`; `success` clears `error`.
- Manual job run (`src/api/jobs.rs::run_job`, `POST /jobs/{id}/run`, editor+): creates a `pending` `job_run` (`trigger: manual`) and publishes it to NATS JetStream via `src/jobqueue.rs` (`JOBS` stream, subjects `jobs.*`, WorkQueue retention, `max_age` from `JOBS_STREAM_MAX_AGE_MINUTES`). On queue failure the run is marked `failed` and the call returns 503. Config: `JOBS_NATS_URL`, `JOBS_STREAM_MAX_AGE_MINUTES`.
- MEF import (`src/api/imports.rs`, table `import_document`, endpoints `POST /imports` + `GET /imports/{document_id}` + `POST /imports/{document_id}/complete`): `POST /imports` accepts the MEF document as a JSON body **or** as a `multipart/form-data` file upload (field `file`, parsed via `multer` in `extract_mef_document`), validates it superficially (`objects`/`references` array), stores it in `import_document` (`document`, `format_version`, `source`, `created_by`), and queues an ad-hoc `inbound_import` `job_run` via `queue_run`; the response is `202 { job_run_id }`. The route is capped by `DefaultBodyLimit::max(100 * 1024 * 1024)` (100 MB). `GET /imports/{document_id}` returns the stored document to the worker (X-Api-Key or admin). `POST /imports/{document_id}/complete` writes the `import.completed` summary event (`event.rs::EVENT_IMPORT_COMPLETED`) to the outbox.
- `emit_events` (bulk imports): `POST /objects`, `PATCH /objects/{id}`, and `POST /references` accept `?emit_events=false` to skip the outbox write (no per-object CRUD event); the import worker passes it when the job has `emit_events: false` and instead emits one `import.completed` summary event.
- Unit catalog & conversion (`src/api/units.rs`, endpoints `GET /units` + `GET /units/convert`): read-only views over the seeded `unit` table. Conversion is the linear-affine function `canonical = value * factor + offset`; `GET /units/convert?value=&from=&to=` (with `to` optional, defaulting to the source dimension's canonical unit) validates same-dimension and returns `{ value, unit }`. Quantified MEF values are normalized by the import worker through this endpoint.
- Language tree (`src/api/languages.rs`, table `language_tree`): `GET /languages` returns all nodes (`code`, `parent` as record key `lang_<code>` or NONE, `label`, `fallback_order`, `active`, `is_ui`); `POST /languages` + `PATCH /languages/{code}` + `DELETE /languages/{code}` are admin/superadmin only. `fallback_order = [parent.code] + parent.fallback_order`; on a parent change `recompute_subtree` re-derives it for the node and its descendants (BFS, cycle guard via `subtree_codes`). `parent` is an `option<string>` field — SurrealDB rejects JSON `null`, so the root case omits it (`CREATE ... CONTENT $content`) / uses `parent = NONE`. `root` is undeletable; a node with child languages is undeletable. Writes invalidate the cached fallback chains (`cache.invalidate_language_tree()`). `active` controls data-maintenance visibility (product form), `is_ui` the drawer UI switch.
- Machine-to-machine auth (`auth.rs::api_key_or_role`): a shared helper that accepts the `X-Api-Key` (`LOG_INGEST_API_KEY`) as a `system` actor or a JWT with at least the required role (hierarchical: `viewer` < `editor` < `admin`/`superadmin`). Worker-facing endpoints use it: `POST /objects`, `PATCH /objects/{id}`, `POST /references` (editor+), `POST /imports` (editor+), `GET /imports/{document_id}` (admin), `POST /imports/{document_id}/complete` (admin), and `GET /rules` (viewer+, so the import worker can read active `normalization` rules).
- Connector configuration (`src/api/connectors.rs`, table `connector`, endpoints `GET/POST /connectors` + `GET/PATCH/DELETE /connectors/{id}`): persisted inbound/outbound connector config — the database is the durable source of truth; environment variables only seed the initial value. `name` is unique; `type` is `webhook|json_import|json_export`; `parameters` is a free-form JSON object (URL, method, headers, filter, coalesce, …). Writes require admin; `GET` list/get also accept the machine-to-machine `X-Api-Key` (the worker loads its connectors here).
- Source reference (`objects.rs`, endpoint `GET /objects/by-source?source=&source_id=`): `POST /objects` accepts optional `source_id`/`source` and stores them on the object (fields + index `idx_object_source`). The lookup returns the unique object for the `(source, source_id)` pair; the import worker uses it for idempotent dedup of objects without a business key.
- Composition tree & children (`references.rs`, editor+): `GET /objects/tree` returns the composition tree rooted at the Universal-Root as nested `{ id, children: [...] }` nodes in one call (query `SELECT in AS child, out AS parent FROM reference WHERE definition_id = 'rel_depends_on'`, then a recursive build with cycle protection); used by the grid's structure navigation, names resolved client-side. `GET /objects/{id}/children` (paginated `?limit`/`?offset`, `ChildrenListParams`) returns the direct `rel_depends_on` children **paginated**, each as its object plus a **`hasChildren`** flag (so the tree shows the expand arrow without loading the whole subtree, for lazy loading); it fetches the child objects in one `SELECT * FROM object WHERE id IN $recs` and **skips children whose object record is missing** (broken/dangling `depends_on` references stay out of the tree). With `?count_members=true`, each `category` child also carries a **`memberCount`** (objects assigned via `category_member` to its composition subtree, via `category_member_keys`) for the category tree's counter. `subtree_keys(db, root_id)` (BFS over `rel_depends_on`, returns **bare object keys**, with cycle protection) backs the server-side subtree filter in `GET /objects?ancestor=<id>` (`objects.rs::list_objects`): the condition is `id IN array::map($ancestor_ids, |$k| type::record('object', $k))`, replacing the former client-side `collect_subtree` traversal once the structure tree is lazy-loaded. `category_member_keys(db, category_id)` (also in `references.rs`) backs `GET /objects?category=<id>`: it computes the category's composition subtree keys (`subtree_keys`) and returns the bare keys of every object assigned via `category_member` (`rel_category_member`, aggregation) to that subtree — used by the grid's category tree (selection filters via aggregation, not composition). `GET /objects?uncategorized=true` (`objects.rs::list_objects`) filters `id NOT IN (SELECT VALUE in FROM reference WHERE definition_id = 'rel_category_member') AND type NOT IN ['category', 'root']` — the grid's „Nicht kategorisiert“ entry.
- Reference picker & relation definitions (`references.rs`, editor+): `GET /objects/picker?q=&types=&locale=&limit=` (compact full-text object search for the reference picker, returning `{id, type, label, status}` with label resolved via `resolve_label`); `GET /objects/{id}/references?locale=` (list an object's references with resolved `in_object`/`out_object` summaries); `DELETE /references/{id}` (editor+, 204); `GET /relation-definitions` (editor+, all `relation_definition` rows for the picker's relation-type dropdown). `create_reference` expects the relation definition's **short record key** (e.g. `rel_category_member`, derived from `relation_definition:rel_category_member`) as `definition_id` — not the full record id nor the display `name` (e.g. `category_member`). `list_object_references`/`picker` resolve labels against the locale fallback chain via `language::resolve_label`.
- Completeness (`src/completeness.rs`): computes an object's **Vollständigkeit** as the percentage of its type's required attributes (`required_types` on `attribute_definition`) that are set. `compute(cache, db, object_id, object_type, locale, own_attributes)` resolves inheritance (`inheritance::resolve_inheritance`) and splits required names into set/missing via `split_set` (pure, unit-tested): a name is *set* when its key is present in `own` attributes (even an explicit empty/null value, which breaks inheritance) or when it was inherited as a non-null value; 100 when the type has no required attributes. `compute_with_required` has a **fast path**: if every required name is already present in `own` it returns 100% without resolving inheritance. The `required_names`/`compute_with_required` are `pub(crate)` so aggregators can reuse required names per type. **`compute_batch`** (Phase 8, used by `GET /objects/stats`) resolves completeness for many objects in one pass: a single `load_parent_map` edge query (`SELECT in, out FROM reference WHERE definition_id='rel_depends_on'`) builds a child→parent map, `inheritable_names` from the cache gates which required names may be inherited, and the chain walk (`resolve_missing_in_memory`, pure + unit-tested) fills values in-memory — avoiding one DB query per ancestor per object. Wired into `objects.rs`: `GET /objects?locale=<code>` adds `completeness: { "<code>": <0–100> }` per object; `GET /objects/{id}?locale=<code>` adds `completeness` and `missing_required` (list of missing required attribute names, for the form widget); `GET /objects/stats?locale=<code>` returns the dashboard aggregation `{total, by_type, by_status, incomplete_by_type}` (object counts by type/status via a single `GROUP`-free scan plus per-type incomplete counts via `compute_batch`). The `?completeness_lt` / `?missing_required` filters are not implemented yet.
- Batch update (`objects.rs`, endpoint `POST /objects/batch-update`, editor+): applies a list of partial changes (`[{id, attributes, status, …}]`) in one call; shared per-object logic with `PATCH /objects/{id}` via `apply_object_update` (rules/computed/workflow guard, outbox event, audit). Capped (verbindlich) at `MAX_BATCH_UPDATE_ROWS` (500) per call, returning `413 Payload Too Large` (`error::payload_too_large`) above the limit. The result is a per-item list (`{id, success, status?, error?}`); an invalid/expired JWT is reported per item as `error: "invalid or expired token"` (HTTP 200, `success: false`).
- Bulk operations (`objects.rs`, endpoint `POST /objects/bulk`, editor+): queues a `bulk_operation` `job_run` for a mass operation. Payload `BulkObjectRequest {op, object_ids, parameters}`; `BULK_OPS` = `set_attribute|clear_attribute|change_status|add_category|remove_category|change_parent|delete`. Validates the editor role, a known `op`, and a non-empty `object_ids`, then calls `jobs::queue_run(..., "bulk_operation", parameters, "manual", &claims.sub)` with `parameters = {op, object_ids, parameters}` and returns `202` with the `job_run`. The worker (`meadow/worker/bulk.py`) applies the operation per object and stores `{op, processed, succeeded, failed, results[]}` in `job_run.result`.
- Rule recompute (`src/api/rules.rs::recompute_rule`, `POST /rules/{id}/recompute`, admin/superadmin): queues a `business_rule` `job_run` (no definition) whose parameters embed the rule `{name, type, script}`, `applies_to`, and optional `object_ids`. The worker executes and reports per object.
- Computed write-back (`src/api/objects.rs::update_computed`, `PATCH /objects/{id}/computed`, `X-Api-Key` or admin): machine-to-machine path that merges only declared-`computed` values (`rules.rs::resolve_computed`) into an object without re-running rules (used by the recompute worker).
- Cron scheduler (`src/scheduler.rs`): a background task (`tokio::spawn` in `run()`) keeps `tokio_cron_scheduler` in sync with enabled scheduled `job_definition` records (6-field seconds-first cron) and, on each fire, creates a `job_run` (`trigger: schedule`) and publishes it to JetStream via `queue_run`. Sync interval from `SCHEDULER_INTERVAL_S` (default 60).
- Dead-letter monitor (`src/jobqueue.rs::monitor_dlq`, background task): ensures the `JOBS_DLQ` stream (`jobs.dlq.*`, Limits retention, manual cleanup) and, for each dead-lettered message, marks the corresponding `job_run` as finally `failed` via `jobs::fail_run` („dead lettered after N attempts“).
- Log-retention cleanup (`src/log_cleanup.rs`, background task): deletes `log_entry` rows older than `log_retention_days` (resolved from system settings via `system::resolve_retention_days`; default 30, validated 7–90) every `LOG_CLEANUP_INTERVAL_S` seconds (default 3600). The ingest rate-limit (`log_rate_limit`) is not yet enforced (deferred per api-design).
- Request limits (`src/app.rs` + `src/rate_limit.rs` + config fields `max_body_bytes`/`rate_limit_per_minute`): a global axum `DefaultBodyLimit` (env `PIM_MAX_BODY_BYTES`, default 10 MiB) caps request bodies; routes with a larger need re-declare their own `DefaultBodyLimit` (e.g. `/imports` at 100 MiB), which — as the innermost layer — overrides the global one. `RateLimiter` (env `PIM_RATE_LIMIT_PER_MINUTE`, default **0 = disabled**) is a per-IP fixed-window limiter (in-memory `HashMap<IpAddr, (Instant, u64)>`, 60 s window) applied as the outermost router layer and returns `429` when exceeded. It reads the peer IP from `ConnectInfo<SocketAddr>`, so the server is served via `into_make_service_with_connect_info::<SocketAddr>()`; it does **not** honor `X-Forwarded-For`, so behind a reverse proxy all clients share the proxy IP (acceptable for direct/LAN deployments; revisit if a proxy terminator is introduced). Defaults keep dev unaffected (2 MiB body, no rate limit).
- SurrealDB `option<T>` fields reject JSON `null` (the distinct `NULL` value, not `NONE`): omit `None` option fields when building `CREATE ... CONTENT`, and clear them with `UPDATE ... SET field = NONE;`.
- The SurrealDB `Surreal<Client>` is shared behind `Arc` (`db.rs`): cloning `Db` (once per request via `AppState`) must reuse the **same** session, because cloning `Surreal<Client>` directly creates a fresh session whose namespace/database replay is asynchronous and intermittently fails with "Specify a namespace to use" under concurrency.
