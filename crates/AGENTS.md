# crates — Rust Source Code

## Purpose

Owns the Rust workspace (root `Cargo.toml`) and all Rust crates. The core service `pim-core` is the headless REST API (Axum + utoipa OpenAPI): sole write access to SurrealDB, JWT authentication/authorization, scheduler, and CRUD-event publishing to NATS JetStream.

## Ownership

- Root `Cargo.toml` (workspace) and every crate under `crates/`.
- `crates/pim-core/` — the PIM core service.

## Local Contracts

- Implementation stays consistent with `plan/meadow-pim-architektur.md` (sections 4–7, 9) and its detail documents; otherwise the plan is updated in the same change.
- Rust Edition 2024; MSRV **1.97** (`Cargo.toml`; `docker/Dockerfile.core` pins `rust:1.97-bookworm`). 1.90 does not compile `diskann` 0.54, which `surrealdb` pulls in (11 × E0311 — found by the first production image build). `jsonwebtoken` requires a crypto backend feature (`rust_crypto` is used; `aws_lc_rs` is faster but needs NASM + CMake on Windows).
- `pim-core` module layout: `src/lib.rs` + `src/main.rs` (thin entry); top-level modules `config`, `db`, `error`, `event`, `audit`, `auth`, `cache`, `language`, `log_cleanup`, `inheritance`, `completeness`, `jobqueue`, `rate_limit`, `rules`, `scheduler`, `schema`, `seed`, `attribute_values`, `attribute_definition_types`; API handlers in `src/api/{health, auth, config, exports, export_profiles, objects, object_types, channels, attribute_definitions, attribute_groups, jobs, job_schema, keys, languages, references, rules, search, system, users, groups, imports, connectors, connector_schema, units, saved_searches, search_schema, enum_sets}`.
- Error mapping (`src/error.rs`): `ApiError` renders as `{"error": <message>}` with 400/401/403/404/409/413/503/500. Every database failure passes `from_db_message`, which turns a SurrealDB **transaction conflict** into `409 "concurrent write conflict, please retry: …"` — two writers on the same record are a caller-side race, not a server fault, and retrying the write is the fix (the import worker's retry pass collects exactly those entries; measured live: 10 parallel writers on one variant produced 6 × `500 "The query was not executed due to a failed transaction"` before the mapping, `0 × 500` after). Everything else keeps its `500` and its message. Clients that read `409` as "already exists" (import worker, bulk relations) must match the message, because a conflict shares the status.
- **Channels & channel-specific releases** (`src/api/channels.rs`, `schema.rs`, Phase 9): `channel` is a configuration catalog keyed by its stable **`code`** (record key, immutable; multilingual `label`, `description`, `active`, `position`); `release` holds the channel state of an object as **one row per `(object_id, channel)`** (unique index, `object_id` is a native `record<object>`, `channel` is the code, `status` uses the object-status vocabulary). Endpoints: `GET /channels` (`object.read`), `GET/POST/PATCH/DELETE /channels…` (`channel.manage`; delete → 409 while releases use the channel), `GET/PUT /objects/{id}/releases` and `DELETE /objects/{id}/releases/{channel}` (`object.read` to list, `object.publish` to write — the machine key still passes, like every other worker write). `PUT` replaces the row (delete + create in one transaction) and both release writes run the **`workflow_guard` rules in `transition` mode** with `EvaluationContext { channel, release_status }` (`RulesClient::evaluate` sends them as `channel`/`release_status`; the Python contract exposes `ctx.channel`/`ctx.release_status`, `withdrawn` marks a withdrawal, `obj.status` stays the *global* status, the rule view carries own + **inherited** values, no language resolution). Audit `object_released`/`object_release_withdrawn`, outbox `object.released`/`object.unreleased`; `DELETE /objects/{id}` deletes the releases of the cascade with the object (per record via `FOR … DELETE release WHERE object_id = $r` — `object_id IN $recs` does **not** match the typed record field). `GET /objects` gained `released_for=<code>` (+ `release_status`, default `published`), `releases=true` (**one bulk query for the page since 2026-09-22**, see the read-path rules below) and the bulk ops `release_for_channel`/`withdraw_from_channel`. MCF: section `channels` directly after `languages` (releases are data, not configuration); the `json_export` profile gained `channel`, which fills a `channel` export source without a code.
- `cache::MetaCache` (in-memory) caches the multilingual/inheritable attribute names, the `url` attributes (`name` + `multilingual`), the language fallback chains, the per-type required names, the feature-code bindings and the serialized attribute vocabulary; attribute-definition writes and object-type writes invalidate it, the MCF import clears it. **Hot-write lookups (2026-09-16):** `active_rules` (per rule types + object type), `inherited_computed_rules` and `category_relation_keys` are cached too — the blocking write path needs all three on **every** save, and they only change in the rules/relation-definition administration (`invalidate_rules()` / `invalidate_relation_definitions()`, both also called by the MCF import). Measured together with the two items below: `POST /objects` 203 → 107 ms, `PATCH /objects/{id}` 372 → **100 ms**. The vocabulary projection (`VOCABULARY_FIELDS`) carries exactly what its consumers render — the export wizard joined by the attribute catalog and the product grid's column picker, which is why that is 11 fields (`id, name, label, type, group_ids, multilingual, applicable_types, reference_data, is_key, inheritable, required_types`; body 5.83 MB → ~6 MB). **Decision (2026-09-15, do not re-open without a trigger):** this in-process cache with explicit invalidation **is** our caching strategy — no HTTP cache layer (`ETag`/`Cache-Control`/conditional requests), no shared/proxy cache, no Redis while a single core instance runs. Redis becomes relevant only with **more than one** core instance (each instance would otherwise warm its own vocabulary and queries and invalidation would have to cross instances); the cheapest real upgrade then is a **generation counter in `MetaCache` served as `ETag`** on the bulk endpoints, not a general cache layer. Measured reasons: bulk reads are milliseconds warm (vocabulary 9 ms), the core↔frontend link is an internal Docker network, every data answer is authenticated and user/locale dependent, and the frontend renders server-side. See `plan/meadow-pim-architektur.md`, Nachtrag 15.
- JWT auth (`auth.rs`): HS256 via `jsonwebtoken`; config through `JWT_SECRET`/`JWT_TTL_SECONDS` — `JWT_SECRET` has **no default** and must be at least 32 characters, otherwise `Config::load()` refuses to start (`scripts/run-dev.ps1` prints a dev value; `.env.vps`'s preflight rejects the template placeholder). Roles: `superadmin`, `admin`, `editor`, `viewer`. A default `superadmin` (`admin`/`admin`) is seeded in dev when no `user:admin` exists. `Claims` carries `groups` (group record ids, direct and inherited), `perms` (the effective permissions as bit words, see the catalog bullet), `auth_version` (the session version, see the access-version bullet), `token_version` and an optional `impersonator: Option<Impersonator>` (`{sub, username}`) set for impersonation sessions. `Claims::can(key)` is the permission check (`permissions()` rebuilds the bit set) and `Claims::require(key)` is the handler-side form (403 `missing permission `<key>`` ); `auth::require_permission(state, headers, key)` is the one entry point for handlers that carry the headers (machine call ⇒ allowed, session ⇒ access-version check + `require`), `auth::require_caller` returns the identity as well (the ABAC scope). The role helpers `has_role`/`is_admin`/`is_editor` stay for the call sites stage B has not moved yet. `auth::validate_new_password(current, new)` enforces the password policy (`MIN_PASSWORD_LENGTH` = 8 characters, must differ from `current`; `current` empty skips the comparison for admin paths) and is used by `POST /auth/password`, `POST /users` and `PATCH /users/{id}`.
- **Access model: membership, claims and the access version** (`src/rbac.rs`, `schema.rs`, `auth.rs`, 2026-09-25): `member_of` (`in` = user, `out` = group) and `child_of` (`in` = child group, `out` = parent) are SurrealDB **RELATION** tables with explicit indexes in both directions (`idx_member_of_in`/`_out`, `idx_child_of_in`/`_out`). `rbac::resolve` answers the groups (direct memberships plus their parents, walked level-wise with record list literals — never `array::map`) and the effective permissions (role defaults + all grants − all denies; **deny wins whichever group states it**, so the order of the groups cannot matter; `superadmin` holds everything and cannot be denied). It runs **once per login**, never per request. Edges are written through `POST /groups/{id}/members`, `DELETE /groups/{id}/members/{user_id}`, `POST /groups/{id}/children`, `DELETE /groups/{id}/children/{child_id}`: idempotent (existing edge → `200 {created: false}`, absent edge → `204`), cycle-checked on the hierarchy (`400`), audited, and `GET /memberships` answers both edge lists in one call so the group dialog needs no N+1. `POST`/`PATCH /groups` **validate `grant_permissions`/`deny_permissions` against the catalog** (`400` with the unknown keys): the read path ignores an unknown key, so a stored typo would be a permission that looks set and does nothing. The check runs before the access-version bump, so a rejected list ends no session. Group changes are audited (`group_created`/`_updated`/`_deleted`, the update naming the changed fields instead of a second copy of the values). **`RELATE type::record(…) -> edge -> type::record(…)` does not parse** ("Unexpected token `::`") — bind both endpoints in `LET` first, like every other edge write.
- **ABAC data scopes** (`src/scope.rs`, `POST`/`PATCH /groups` + the object read paths, 2026-09-25): a group carries `scope: {rules: […]}`; `scope::parse` reads it (fields `type`/`status` only, `operator: in`, and `reference` rules naming a **relation key** — `rel_category_member` — plus one or more target record ids), `scope::validate` checks relation and targets against the database on the **write** path (`400`), and `scope::for_caller` compiles the caller's groups into **one** condition that `build_object_filter` appends to the same chain as every other filter (so page, total and column sample cannot disagree, and it is part of `ObjectFilter::view_key`). Semantics: rules within a group are **ANDed**, groups with rules are **ORed**, a group **without** rules restricts nothing and an unrestricted caller (worker, or a user without groups) adds **no condition at all** — the query stays byte-identical. **A superadmin is never scoped**, even inside a group that carries rules (`scope::needs_scope`): the role bypasses every check, and a scope is a check on data — measured 2026-09-25, before that branch existed, as 69 of 2000 products with a complete permission set; the membership stays possible and is then inert. An `admin` **is** scoped (the plan exempts the superadmin, not the admin). **The clause shape is measured:** `id IN (SELECT VALUE in FROM reference …)` costs 28 918 ms on the dev data against 896 ms for a literal key list (unscoped count: 33 ms), so the member keys are resolved in Rust, rendered as a record literal and cached — bindings on `auth_version` for the group documents, on `stats_version` for the resolved keys. **`/objects`, `/objects/count`, `/objects/attribute-usage`, the single object, `/objects/stats`, `/objects/by-key`, `/objects/by-source` and `/search` require an identity and `object.read`** (they answered `200` without a token before); the picker asks for `reference.read`: `auth::require_caller` accepts the worker API key (unrestricted) or a bearer token whose access version is current, and **every one of those reads carries the scope as one more condition** — a foreign object answers `404` on the single read (`GET /objects/{id}`, `/by-key`, `/by-source`: the id is not an oracle), **The write paths carry the same clause:** the single `PATCH`/`DELETE`/`PATCH …/computed` loads inside the scope (a foreign object is `404`, and the write below never runs), and a batch (`batch-delete`, `bulk`, `batch-upsert`) that names a foreign object is refused **as a whole** (`403`, `api::objects::reject_out_of_scope_objects`) — one query per batch, none for an unrestricted caller (rule R7). `bulk` checks at queue time (the run itself executes in the worker, which is the machine); `batch-upsert` checks the **matched** objects, so an invented business key does not open a foreign row. The structural edge views follow it as well: `GET /objects/{id}/children` and `…/ancestors` check the **anchor** (`404` for a foreign object, like the single read), and the tree keeps the visible nodes **plus the path to them** — the taxonomy above a product is not inside the scope, so without the path a restricted caller would look at an empty tree (measured: 69 visible products → 111 of 11 618 nodes). `scope::for_caller_on(state, caller, "in.")` renders the same clause against the edge's object side instead of the object itself; the compiler stayed one, only the field references move. **The promises are unit-tested** (`scope::needs_scope`, `scope::restricts`, `scope::apply(None, …)` changes nothing) and checked against a live instance by `scripts/scope_bench.py`.
- **The group editor's scope preview, the group write and the write-path dry run** (`src/api/groups.rs`, 2026-09-26/27): `POST /groups/preview-scope` (`group.read`) compiles the scope document that is on screen with the **same** parser, the same `scope::validate` and the same compiler the write uses, and answers `{count, total}` — what the document shows and what the caller sees without it. The editing admin is normally **not** a member of the group, so the counter cannot come from their own session; the caller's own clause is ANDed in, and `scope::clause_of(…, base_index)` keeps the two clauses' bind names apart (a bind name carries the group index — two clauses in one query would feed one set of values to both conditions, a wrong number that looks right). **`POST /groups/validate`** (`group.manage`, machine key allowed) is the same check **without** a document: it runs `reject_unknown_permissions` and `check_scope` (`scope::parse` + `scope::validate`) — exactly what a save runs, with the same messages verbatim — and answers `200 {ok, errors}` (always a question, never a write; a wrong request *shape* is still a `400`). It exists because the AI assistance has to judge a suggestion with the component that would refuse the save (`plan/detail/ki-assistenz.md`); it calls the write path's functions instead of copying their rules. `PATCH /groups/{id}` writes its fields with explicit `SET` assignments instead of `MERGE`: SurrealDB merges **nested** objects field by field, so `MERGE {"scope": {}}` left the stored rules in force while the editor, the API answer and the document all looked cleared — the exact write the group editor sends when the last block is removed (found 2026-09-26).
- **Effective rights of a user, with their sources** (`src/api/users.rs`, `GET /users/{id}/effective`, `user.read`, 2026-09-26): runs the same resolution the login performs (`rbac::resolve`) and adds **where** every permission comes from (`rbac::grants_of`, which now carries the group `name` too, so naming a source needs no second lookup). Per permission: `state` (`role` = the role default, `granted`/`denied` = a group says so, `superadmin` = the role holds everything), `effective`, and `granted_by`/`denied_by` as `{id, name}` lists — a deny is named as well as the grant, and **a deny wins**. A group that does not mention a permission is not a "no": the lists are empty and `effective` answers. `unknown` reports keys in group lists the catalog does not know. The user editor renders this instead of recomputing it: a panel that explains rights must not have its own opinion about them.
- **The caller keeps their session through an access change** (`src/api/auth.rs`, middleware `renew_after_access_change`, 2026-09-26): `auth_version` ends **every** session, including the one that asked for the change — right for the others, wrong for this one (an admin would land on the login page after every membership change). The layer compares the counter before and after the handler (one atomic load, no query) and, **only when it moved**, re-reads the user, re-resolves roles and permissions (`claims_for`) and attaches the fresh token as `x-access-token`. `None` for a deleted or suspended user or a raised `token_version`: that `401` stays. An impersonation session keeps its `impersonator` claim. The frontend adopts the header in one place (`meadow/frontend/api.py`) and sends the token from the session **per request** (`auth.session_token`), because a page reads its token once while it renders. This was pulled forward from stage C5 into C3: without it the members tab would log the admin out on every added member.
- **The access version ends issued sessions** (`access_state:state`, `cache::MetaCache::auth_version`, 2026-09-25): the extractor compares `Claims::auth_version` against the in-memory counter (one atomic load, no query) and answers `401 invalid or expired token` when they differ — the message the frontend already maps to "session expired → log in again". Every write that changes the access model raises the **persisted** counter (permissions, groups, memberships, hierarchy, roles, status, password, user deletion; **not** creating a user and not a removal that finds no edge), before the write it protects, and publishes it to the cache. `0` is never a valid version, so a token from before this contract fails closed. The counter is persisted on purpose: an in-memory one would restart on every deployment and log everyone out. **Consequence:** the caller's own session ends with the change — **closed in stage C (2026-09-26):** the very request that raised the counter gets its own session back, re-derived (see the renewal bullet below). **Closed (stage B, 2026-09-26):** every endpoint now authorizes through the catalog — `auth::require_permission` (or `Claims::require`) checks the permission **and** the access version, so a token that a permission change invalidated is refused on the worker paths as well. The role helper `auth::api_key_or_role` is gone; the role constants and `Claims::has_role` stay for the impersonation exception (`superadmin`) and the scope.
- **Self-service password change** (`src/api/auth.rs`, `POST /auth/password`, any authenticated role): body `{current_password, new_password}`; verifies the current password against the stored argon2 hash (400 on mismatch), applies the password policy (400), stores a new hash, sets `password_changed_at`, clears `must_change_password`, bumps `token_version` and returns `200 {token, token_type}` — a **fresh JWT** so the caller's session continues (the token version is not enforced per request yet, see the plan). Rejected with 403 for impersonated sessions (`impersonator` claim). Audited as `password_changed`. `GET /auth/me` returns `must_change_password` (whether the UI should ask the user to set their own password; a **missing field counts as `true`**) plus `password_changed_at` (informational). `POST /users` takes `must_change_password` (default `true`) and validates the password; `PATCH /users/{id}` accepts `must_change_password` **independently** of `password` (clear/re-arm the hint) and, when it sets a password, defaults the flag to `true` (an explicit value wins), **unsets** `password_changed_at` (`UPDATE … UNSET` — `MERGE` cannot write `null` into an `option<datetime>`) and bumps `token_version`, audited as `user_password_reset`.
- **Impersonation** (`src/api/auth.rs`, `POST /auth/impersonate/{user_id}`, **superadmin only**): issues a normal JWT for the target `user` (`sub`, `username`, `roles`, `token_version`, `exp`) plus an `impersonator` claim (acting superadmin). Rejects self-impersonation (400) and non-active targets (400); `GET /auth/me` returns the `impersonator` claim so the UI can show a banner. Audited as `user_impersonated`. This is a test/support aid, not a privilege-escalation path — the token adopts the target's roles.
- **Permission catalog** (`src/permissions.rs`, `GET /permissions`, 2026-09-25): the one source of truth for the 26 permissions of `plan/detail/benutzer-gruppen-rechte.md` (area, action, role default, `label_key`, English description). `GET /permissions` (`group.read`: the catalog is the input of the group editor, and a session's own rights are in `/auth/me`; the worker's API key still reads it) serves the document — areas in order, the four roles, and per permission the **expanded** roles, so the UI matrix can render "inherited from the role" without knowing the hierarchy. **The bit indices are append-only:** `index` is the permission's bit position in `PermissionSet` (`[u64; WORDS]`, `Copy`, no allocation) and that bit set is what travels in the JWT — reordering would silently give an old token a different meaning, so a removed permission keeps its bit and a new one takes the next. Authorization must therefore stay a **bit test without I/O**: resolve the effective set once at login, never per request (this is the invariant the whole RBAC work is measured against; the `auth_version` decision is in the detail doc). `can()` on an unknown key is `false` (fail-closed); unknown keys are reported by the **write** path only. Role defaults come from `min_role` plus the role hierarchy (`admin` is a special form of `editor`), which is exactly what `auth::Claims::is_admin`/`is_editor` express today — stage B replaces those call sites with `can(...)`, so each replaced site must be checked against this mapping to keep the behaviour of users without groups identical.
- `POST /system/logs` accepts a machine-to-machine `X-Api-Key` (`LOG_INGEST_API_KEY`) or, as a dev fallback, an admin JWT. Full-text search (`POST /search`, `object.read` + scope) uses analyzer `meadow_std` and index `idx_object_attributes_fulltext` over `object.attributes`. `GET /system/settings` also accepts the API key (machine-to-machine config read for the worker). Curated log categories are `app|job|rule|auth|integration`; the core's own rule logs use `rule` (singular). `GET /system/settings` returns a flat `{key: value}` map; with **`?include_source=true`** it returns `{key: {value, source}}` (`default`|`env`|`db`) for the admin UI (the worker keeps using the flat form). Settings: `log_persist_level` (DEBUG|INFO|WARN|ERROR|CRITICAL), `log_persist_categories` (array), `log_retention_days` (7–90), `log_rate_limit` (>0), plus **rule knobs** `rules_degrade` (bool), `rules_breaker_threshold` (>0), `rules_timeout_ms` (100–60000); `PUT /system/settings/{key}` persists + audits, `DELETE /system/settings/{key}` resets to default. A resolved settings snapshot lives in **`AppState.settings`** (`Arc<RwLock<Map>>`, precedence default < env < db, seeded by `system::initial_settings` + `refresh_settings_snapshot`); `RulesClient` reads `degrade`/`breaker_threshold`/`timeout` from it at runtime, so the rule settings take effect on the settings page **without a restart**.
- **AI settings and the secret rule (2026-09-19, `plan/detail/ki-assistenz.md` §4):** the registry gained `ai_enabled` (bool), `ai_provider` (`generic|openai|azure_openai|ollama`), `ai_endpoint`, `ai_model`, `ai_api_key`, `ai_temperature` (0–2), `ai_max_output_tokens` (1–32768), `ai_timeout_ms` (1000–300000), `ai_max_requests_per_hour` (≥0), each with an `AI_*` environment override that wins over the database. **`ai_api_key` is a secret**: `secret_setting()` marks it, and no settings response carries its value — the detailed form answers `{value: null, configured, secret: true, source}`, the flat form `null`. The real value leaves the core **only** inside the NATS request to the worker (`AiClient`, `src/ai.rs`), never towards a browser. `PUT /system/settings/{key}` now writes its record in **one** statement (`UPSERT … SET … RETURN AFTER`): the former `BEGIN; UPSERT … CONTENT; UPDATE … SET …; SELECT …; COMMIT` wrote the same record twice per transaction, so the **second** save of *any* setting answered `409 concurrent write conflict` (found 2026-09-19 while verifying the AI page, which saves nine values one after another).
- **AI endpoints (`src/api/ai.rs`, `src/ai.rs`, 2026-09-19):** `POST /ai/generate` (`ai.use`) validates area/mode/description/current-script, forwards the task **plus the resolved configuration (including the key)** to the worker over NATS (`AI_GENERATE_SUBJECT`, default `ai.generate`), records one `ai_generated` audit entry (area, mode, target, object type, ok, model, attempts, latency, total token count — never the prompt, never the script) and returns the worker's JSON unchanged; `GET /ai/history?area=&target=` (`ai.use`) lists exactly those entries for one target, newest first (`limit`, default 20, capped at 100) — the audit entry is the store, there is no second table; `POST /ai/test` (admin) does the same for the connection test (`ai.test`). Fail-closed: `ai_enabled = false`, an incomplete configuration or an unreachable worker answer `503` with an actionable message, while a refused suggestion is a `200` with `{ok: false, errors}` (a normal outcome, not a transport error). The NATS timeout is the provider timeout plus 5 s, so the worker's own error message wins over a transport timeout. **Areas (`validate`)**: `rule`, `computed_attribute`, `search`, `connector`, `export_profile`, `job`, `import_mapping`, `group_permissions` — `config_kind` is required for `connector` (the connector type) and `job` (the job type, checked against `VALID_JOB_TYPES`), and `columns` (`ColumnSpec {name, hint}`) for `import_mapping`; both are checked **before** the model call, so a request the worker could not serve costs nothing. The column hints are value-free descriptions of the cells (`text, 6 characters, all values different`) — the file itself never leaves the browser. `group_permissions` (2026-09-27) carries the editor's own workflow states in `statuses` (`Option<Vec<String>>`, like `declared_computed`: the list the scope card offers, so a suggestion can never name a state the card cannot show) and its current state (`JSON` of the matrix and the scope) in `current_script`; the check is `POST /groups/validate` above.
- Synchronous rule evaluation (`rules.rs`): the core loads `active` `business_rule` records **through `MetaCache::active_rules`** (cached per rule types + object type, invalidated by every rule write — the write path needs them on every save), builds the candidate view, and calls the Python worker over NATS request/reply (subject `rules.evaluate`) in the object write path. Fail-closed: validation errors reject with 400, a rule that fails (exception/timeout) rejects with 500, an unreachable worker rejects with 503; `RULES_DEGRADE=true` degrades to "skip rules" on transport failure. Circuit breaker: a `failure_count` on the rule auto-disables it after `RULES_BREAKER_THRESHOLD` (default 3) consecutive failures and writes an audit entry + system log; success resets the counter. Config: `RULES_NATS_URL`, `RULES_SUBJECT`, `RULES_COMPILE_SUBJECT`, `RULES_TIMEOUT_MS`, `RULES_DEGRADE`, `RULES_BREAKER_THRESHOLD`. **The request payload is the worker's Pydantic contract** (`meadow/worker/protocol.py`, built by `rules::evaluation_payload`): list fields are **always arrays** — serialising `missing_features: None` as `null` made the worker reject the whole request (`Input should be a valid array`), which broke every Rule Lab run (`dry-run`/`test-batch` pass `EvaluationContext::default()`) while the write path kept working, because that one always supplies a list. `rules::tests::the_evaluation_payload_*` pins the shape and the field names. The phase timing of the write path (including this evaluation) is logged at `debug` level: `RUST_LOG=info,pim_core::api::objects=debug` (the `env-filter` feature of `tracing-subscriber` is enabled for that; the default filter stays `info`).
- Business-rule CRUD (`src/api/rules.rs`, endpoints `/rules`): list/get need `business_rule.read`; create/update/activate/disable **and `DELETE /rules/{id}`** need `business_rule.manage`. Create/update/activate compile-check the script via the worker (subject `rules.compile`); invalid scripts reject with 400, an unreachable worker with 503. New rules start as `draft`; `name` is unique (409); every change bumps `version` and is audited. `DELETE /rules/{id}` returns 204 and is audited `rule_deleted` (no cascade — deleting an `active` computed rule means the matching `attribute_definition` loses its rule, so the UI warns). `POST /rules/{id}/dry-run` (admin/superadmin) evaluates a single rule against a real object (`object_id`) or a constructed `object`, read-only and audited. `POST /rules/{id}/test-batch` (admin/superadmin, Rule Lab) evaluates a rule against a selection of real objects (`TestBatch { object_ids }`), read-only, one NATS evaluation per object, audited as `rule_test_batch`; `RuleSpec` is `Clone` so the spec can be reused across the batch. `POST /rules/{id}/recompute` (admin/superadmin) queues a `business_rule` recompute job over the rule's object set (only `active` `computed`/`bulk` rules; see job management).
- Computed-attribute enforcement (`rules.rs::resolve_computed`): the write path validates that every value a `computed` rule produces is declared as `computed: true` in `attribute_definition`; undeclared or non-computed writes reject the save with 400 (fail-closed).

- Saved searches & collections (`src/api/saved_searches.rs`, Phase 9): `saved_search`/`collection` are generic objects (`object` table) — **not** attached to the composition tree. **Saved searches**: `GET/POST /saved-searches` + `GET/PATCH/DELETE /saved-searches/{id}` (CRUD; read `object.read`, write `search.manage`) and `POST /saved-searches/{id}/execute` which runs the query DSL (stored in `attributes.query`) and returns `{count, ids}`. The DSL is a **recursive condition tree**: `where = {op: and|or, conditions: [<group>|<leaf>]}` with leaves `{field, operator, value}` (the flat `filters` list is gone; a stored legacy `filters` is rejected with a clear message), plus `fulltext` (`attributes @@ $q`; `fields`/`language` accepted but unused), `references` (`rel_<type>`, `out` container, `incoming`/`outgoing`), `sort`, `start`, `limit`. `execute_query(db, query, catalog)` loads the catalog, normalizes/validates the query and renders it through `search_schema::render_query` (shared with `GET /objects?where=…`), then projects every sort field (`<field> AS _sort_N`, `ORDER BY _sort_N`) — SurrealDB rejects `ORDER BY` idioms that are missing from the selection (`Missing order idiom`). - **The OpenAPI document must build — a recursive schema crashes the process (fixed 2026-09-21).** `GET /api-docs/openapi.json` (a handler that calls `ApiDoc::openapi()`) killed the core with `thread 'tokio-rt-worker' has overflowed its stack`; the endpoint had simply never been called. Cause: utoipa **inlines** a nested type into its parent's schema, so `QueryCondition.conditions: Option<Vec<QueryCondition>>` (the recursive search-DSL condition tree) recursed without bound — reproduced in a plain unit test, and even a 32 MiB thread stack did not survive it (so it is unbounded, not just deep). The field carries `#[schema(no_recursion)]` (`src/api/saved_searches.rs`); `api::tests::the_openapi_document_builds_and_serialises` builds and serialises the whole document at the **default** stack size and asserts the paths are present, so the next recursive type fails a gate instead of taking the process down.
- Object type registry (`src/api/object_types.rs`, Phase 9): `saved_search`/`collection` are generic objects; **object types** are the managed business types (`object_type` table, STIBO STEP / Akeneo family model, **flat** — no type inheritance). `GET/POST /object-types` + `GET/PATCH/DELETE /object-types/{name}` (read `attribute_definition.read`, write `attribute_definition.manage`). Each type has `name` (unique code), `label` (multilingual), `description`, `key_attributes` (the unique + **mandatory** business-key attribute names for that type; empty = no key), optional `label_attribute` (display-name attribute), and a **`system`** flag (`bool`, default `false`; the seeded/default types are `system: true`). `key_attributes`/`label_attribute` must reference `text` + non-multilingual attribute definitions (forward references allowed). Deletion is rejected with **400** for `system` types and **409** while objects use the type. `ensure_registered` auto-registers unknown types on `POST /objects` (best-effort, `system: false`). **Business-key enforcement moved per type:** `keys.rs::normalize_key_attributes` now reads the type's `key_attributes` from the registry (was a global `is_key` scan — which also enforced keys for types the attribute did not apply to); the duplicate check filters `deleted_at IS NONE` (soft-deleted objects no longer block). **Completeness (`completeness.rs::required_names`) now includes the type's `key_attributes`** in addition to `required_types`, so a declared key counts as mandatory. **Check and write form one critical section per key** (`src/key_lock.rs`, `AppState::key_locks`): `create_object`/`update_object` fetch the type's key names, lock the requested key values (sharded in-process mutexes, sorted shard order, no global serialisation) and only then run `normalize_key_attributes` plus the write. Without it two parallel writers both read "no conflict" and either collide with a `409` or leave **two live rows** with the same business key — a state that then blocks every later `PATCH` on that key (`plan/detail/demodaten-generator.md` §4.4). This holds for **one core process per database** (dev and the VPS compose); a multi-instance deployment would need a database-level guard. **The uniqueness lookup is index-backed (2026-09-16):** `keys::ensure_key_indexes` defines `idx_object_key_<attribute>` on `object FIELDS attributes.<name>` for every declared key attribute (idempotent; called at startup for the whole registry and after an object-type write that declares keys), and `key_value_exists` renders the **static** field path plus `LIMIT`-free collection with the **type filtered in Rust**. Both details are load-bearing, measured against the live instance: the dynamic `attributes[$key]` form cannot use the index (~1 000 ms for the same lookup), and with `type = $type` in the predicate the planner prefers `idx_object_type` and scans every object of the type (~615 ms) instead of answering from the key index (~71 ms). Attribute names that are not plain identifiers are not indexable and keep the dynamic form (correct, slower). On an existing dataset the first `DEFINE INDEX` builds the index once (~5 s per attribute at 11.7 k objects); later starts are no-ops. **The registry is read, not assumed (2026-09-16):** the indexes are ensured from `registered_key_attributes(db)` — after the **MCF/config import** (`config.rs` calls `keys::ensure_key_indexes` once the document is applied, because the import writes `object_type` records directly and never went through the handler), after an object-type write, and at startup. Without the import call a freshly imported model kept doing the index-less scan (~150 ms per create at demo scale, worse with every object) until the next restart — measured: a `perf` chunk imported at **2,2 obj/s** that way, **30 obj/s** with the indexes in place.

References are resolved to stable keys: `attribute_definition.group_ids` → group names, `unit_id`/`display_unit_id` → unit symbols, `enum_set_id` → set name; `language_tree.parent` → parent language code; `unit.canonical_unit_id` → canonical symbol; `enum_set.options` → `{code, labels, position, active}`. Helper maps (`unit_symbol_maps`, `group_name_map`, `enum_set_name_map`) resolve record-id references. `created_at` is a Rust-side UTC RFC3339 string (`utc_now_iso`, no chrono). Detail: `plan/detail/konfiguration-export-import.md`.** Import-side detail: `normalise_entry_maps()` runs once per section before the apply functions and turns `null` in the map fields `label`/`labels` into `{}` — the export writes `null` for an empty label map, but the object-typed fields reject `NULL` (`plan/detail/bmecat-export.md` §11.4, found in the ETIM spike).**Import** is `POST /config/import` (`integration.manage`; the machine key passes, a restore may run scripted): `?mode=dry_run|merge|replace` (default merge). It applies each section in dependency order (`languages` → `channels` → `units` → `attribute_groups` → `enum_sets` → `object_types` → `classification_standards` → `attribute_definitions` → `relation_definitions` → `business_rules` → `export_profiles` → `category_attributes`), resolving references to existing target records via a preloaded `Resolve` map (stable key → target record key) and falling back to creating missing referenced records. `system`-flagged entries and `system=default` units are skipped (seeded rows must already exist, existence is required). Existing records are merged with `UPDATE ... MERGE`; `would_change(existing, content, VOLATILE)` reports re-imports of an unchanged document as `skipped` (idempotent report) instead of `updated` — `VOLATILE` ignores `version|updated_by|updated_at|created_at|failure_count`. Response is a `ConfigReport` (`mode`, `summary {created,updated,skipped,deleted,errors}`, per-section lists). **`replace`** first deletes target-only (non-system) records per section present in the document (reverse dependency order; `system` records and records still in use are kept, the latter reported as errors), then applies the document — so the applied section matches the document exactly; absent sections are left untouched and a full round-trip replace is a no-op. **Async import (`?async=true`):** stores the document in `import_document` (with `kind = "mcf"`) and queues a `config_import` job (`VALID_JOB_TYPES`), returning `202 {job_run_id}`; the worker (`meadow/worker/config_import.py`) fetches it via `GET /imports/{document_id}` and re-applies it through the sync endpoint, storing the report in `job_run.result`. Both the sync and async paths accept `X-Api-Key` (worker machine-to-machine) or an admin JWT via `api_key_or_role(..., ROLE_ADMIN)`. **A document that names an empty `class_id` is reported, not failed (2026-10-09):** a class feature entry is resolved over the stable key first and its local id second, and an empty `class_id` used to reach `type::record('object','')` - SurrealDB answers `Found  for the Record ID but this is not a valid id`, so the import answered `500` where the module promises a report entry. `category_attributes::local_class_key` drops an empty value (and the space around a value), so the entry now lands in `errors` with *class not found in the target; import the taxonomy data first*. Found with the first artifact of SketchGround's MCF profile, which wrote the empty id. **SurrealDB quirks:** `option<T>` fields reject JSON `null` so nullable fields are omitted from `CONTENT`/`MERGE`; `array::contains` is invalid (use `array::distinct(array::append(...))`); a trailing `SELECT * FROM $r` after `UPDATE` returns no rows (so `update_keyed` runs only the UPDATE); `response.take(idx)` depends on the statement count (`take(2)` after `LET $r = …; CREATE/UPDATE …`); `enum_option.code` is globally unique (options are found by code then re-linked).

- Attribute value validation (`src/attribute_values.rs`, Phase 9): the **only** value-level check of the core so far, for the `url` data type. `is_valid_url()` accepts an absolute `http(s)` URL with a host only (WHATWG parser via the `url` crate, surrounding whitespace tolerated) — `example.com`, `ftp:`/`mailto:`/`javascript:`/`data:` and `https://` are rejected; `validate_attribute_values()` is called by `create_object` and `apply_object_update` (hence also by `batch_update_objects` and every worker write path) and returns `400` with one message per offending value, naming the attribute (`` `attributes.homepage`: must be an absolute http(s) URL ``, multilingual per language: `` `attributes.homepage.de`: … ``). `null` and empty/whitespace strings mean "no value" and stay valid; non-string values (numbers, arrays, a language map for a scalar attribute) are rejected. The attribute list comes from `MetaCache::url_attributes` (no query per write). **Rule:** a new data type that needs validation gets its check here, not in the handlers. The `range` type (two numeric bounds `{"from", "to"}`, added Phase 9 for ETIM/BMEcat range features) is checked nowhere on write, like `number`; its rules live in `attribute_definition_types.rs` (`is_range`, `is_numeric`, `range_value` orders the bounds, `parse_range`/`format_range` for the canonical `from..to` text form) and are applied on the type-change path — units are kept when moving between the numeric types.
- Attribute definitions (`src/api/attribute_definitions.rs`, Phase 9): `DELETE /attribute-definitions/{id}` counts the objects that carry a value for the attribute (409 with `?force=true` to remove the values as a bulk job) — the check filters `deleted_at IS NONE`, like every other usage/visibility query (`count_enum_usage`, object lists, `object_types` deletion), so **soft-deleted objects never block** a deletion. **Data-type change (`POST /attribute-definitions/{id}/type-change`, admin):** the type is mutable through a dedicated endpoint because every existing value must be migrated. Preconditions: not `computed` (the rule owns the value), a business key may only stay `text` (`409` each), the target must be allowed by the compatibility matrix and a target `enum` needs an existing `enum_set_id` (`400`). `?dry_run=true` returns the report (`{name, from, to, checked, convertible, incompatible, samples[], dropped, dry_run}`) without writing; applying converts each value (a value that does not fit blocks the change with `409`, `drop_incompatible: true` removes those values instead), updates the definition (leaving `enum` clears `enum_set_id`/`constraints`, leaving `number` clears the units) and writes both in **one transaction** (`FOR $row IN $rows { UPDATE … SET attributes[$name] = $row.value; }`). Audited as `attribute_definition_type_changed`, event `attribute_definition.updated`, caches invalidated. `PATCH /attribute-definitions/{id}` rejects a `type` field with a pointer to this endpoint (silently ignoring it would look like a successful type change). `standard_codes` is normalised and validated by `validate_standard_codes`: an object of `{standard: code}` with non-empty codes, and a code may be claimed by exactly one definition (a second claim is `409` naming the other attribute). Clearing goes through `SET standard_codes = NONE`, **not** an empty `{}` — the update runs `UPDATE … MERGE`, and SurrealDB `MERGE` merges nested objects key-wise, so `{}` would silently keep the old binding. The same reason drives the `enum_set_id` clear. **`reference_data` (bool, 2026-09-13)** marks an attribute as the vocabulary of a classification standard (set by the standard import, 380 definitions in the shipped ETIM 10.0 bundle): the frontend hides it wherever an attribute is *chosen* and shows a **Standard** column/filter plus an adopt action that clears the flag. Accepted in `POST` (default `false`) and `PATCH`; both `standard_codes` and `reference_data` travel in the MCF `attribute_definitions` section, so an exported configuration keeps the binding and the adopted state (`plan/detail/kategorisierung.md`, "Referenzdaten").
- Search field catalog, validation & filter rendering (`src/api/search_schema.rs`, Phase 9): the **server contract** behind `GET /search-fields`, the validation of every saved-search query (write, execute, preview, collection refresh) **and** the SurrealQL rendering shared by saved searches and the grid: `Catalog {groups, operators, fields, languages, references, limits}` is built by `load(db)` from `attribute_definition`/`object_type`/`object`-status/`enum_set`+`enum_option`/`unit`/`language_tree`/`relation_definition`, where `build_catalog(&CatalogSources)` is the pure, unit-tested part. A field also carries **`reference_data`** (from `attribute_definition.reference_data`, part of the catalog query since 2026-09-13): such a field stays **filterable** — a stored search must keep validating — and only tells the client to keep the standard's vocabulary out of the *offered* field/sort lists (the search form has a switch for that, `meadow/frontend/search_form.py`). the handler stores that canonical form. **Shared renderer** (`RenderedFilter {clauses, params}`, `sanitize_field`, `render_condition`, `render_filter`, `render_query`): groups become parenthesized `AND`/`OR` clauses, parameters are numbered recursively (`f0`, `f1`, …), composite clauses are parenthesized (`AND` binds tighter), `created_at`/`updated_at` operands are wrapped in `type::datetime(…)`, sort fields are projected as `_sort_N`, and **ordering/negative operators are guarded with `field IS NOT NONE AND field != NULL`** — in SurrealDB `NONE < 0` is true (missing values sort before numbers) and `NONE != 'x'` is true as well, so without the guard `not_between [0, 200]` matched every object without a value; - Composition tree & children (`references.rs`, `reference.read`, scoped: the anchor is checked and the tree keeps the visible nodes plus their paths): `GET /objects/tree` returns the composition tree rooted at the Universal-Root as nested `{ id, children: [...] }` nodes in one call (query `SELECT in AS child, out AS parent FROM reference WHERE definition_id = 'rel_depends_on'`, then a recursive build with cycle protection); used by the grid's structure navigation, names resolved client-side. `GET /objects/{id}/ancestors` returns the path from the outermost composition ancestor down to the object (root-most first, the object last; each entry = object document + `hasChildren`, the universal root is not part of the path) — the tree panels use it to show a **search hit in its hierarchy** instead of a flat hit list; the walk is one query per level (taxonomy depth) plus two batched queries and refuses to loop on broken data. `GET /objects/{id}/children` (paginated `?limit`/`?offset`, `ChildrenListParams`) returns the direct `rel_depends_on` children **paginated**, each as its object plus a **`hasChildren`** flag (so the tree shows the expand arrow without loading the whole subtree, for lazy loading); it fetches the child objects in one `SELECT * FROM object WHERE id IN $recs` and **skips children whose object record is missing** (broken/dangling `depends_on` references stay out of the tree). **`?scope=all|composition|taxonomy` (default `all`) and `?type=<object type>` filter in the core** — `composition` excludes the taxonomy types (`object_type.taxonomy`), `taxonomy` keeps only them; an unknown scope is a `400`. Why it must be server-side: with a classification standard installed the universal root carries **5648 taxonomy nodes** next to 46 structure objects, so a client-side filter silently truncates a `LIMIT`ed page and makes `count_members` count subtrees nobody renders. **The filter must use the record-link traversal `in.type`, never `in IN (SELECT VALUE id FROM object WHERE …)`**: measured at the root the subquery shape needs **31.7 s** (evaluated per candidate row), `in.type …` answers the same page in **0.12 s** (still driven by `idx_ref_out_def`). `?count_members=true` adds a `memberCount` to every taxonomy child (`?definition_id=` selects the category relation type, default: the primary one; unknown/non-category ⇒ `400`), computed for the whole page in **one pass** by `category_member_counts` (reads the composition edges and the assignments once, then `subtree_member_counts` — pure and unit-tested — sums the subtrees in memory; the earlier per-child variant re-read every edge per node: ~8 s for 100 children). The endpoint needs `reference.read`; the machine key passes, so the bulk worker (service account, `X-Api-Key`) can walk the tree for `consolidate_inheritance`. `subtree_keys(db, root_id)` (BFS over `rel_depends_on`, returns **bare object keys**, with cycle protection) backs the server-side subtree filter in `GET /objects?ancestor=<id>` (`objects.rs::list_objects`): the condition is `id IN array::map($ancestor_ids, |$k| type::record('object', $k))`, replacing the former client-side `collect_subtree` traversal once the structure tree is lazy-loaded. `category_member_keys(db, category_id, definition)` (also in `references.rs`) backs `GET /objects?category=<id>[&definition_id=<rel_…>]`: it computes the category's composition subtree keys (`subtree_keys`) and returns the bare keys of every object assigned via `category_member` (`rel_category_member`, aggregation) to that subtree — used by the grid's category tree (selection filters via aggregation, not composition). `collection_member_keys(db, collection_id)` (also in `references.rs`) backs `GET /objects?collection=<id>`: it returns the bare keys of every object assigned via `collection_member` (`rel_collection_member`, aggregation) to that collection — used by the grid's flat **Collections** view (selection filters via aggregation, no hierarchy). It binds `$col` to `key_of(collection_id)` and reads the result with `take(0)` (a single-statement query, unlike `category_member_keys` which has a `LET` prefix and uses `take(1)`). `GET /objects?uncategorized=true` (`objects.rs::list_objects`) filters `id NOT IN (SELECT VALUE in FROM reference WHERE definition_id = 'rel_category_member') AND type NOT IN ['category', 'root']` — the grid's „Nicht kategorisiert“ entry.

The picker uses it to decide whether a target type is **reachable** in the composition tree: products hang below a part group, and the composition scope hides taxonomy nodes, so the tree can never reach them (every row was a greyed-out vehicle) — such targets are listed flat instead. - Reference picker & relation definitions (`references.rs`, read `reference.read` / `attribute_definition.read`, definitions written with `attribute_definition.manage`): `GET /objects/picker?q=&types=&locale=&limit=` (compact full-text object search for the reference picker, returning `{id, type, label, status}` with the label resolved via `language::resolve_object_label` — `name` first, then `code`, then the object type, so a taxonomy class shows `EC012373` instead of `etim_class`; with `?locale=` each hit also carries **`completeness: {"<locale>": <0–100>}`** so the form's pickers can badge the target — computed per hit via `completeness::compute`, because the picker's hit list has no ancestors for `compute_batch`). **Two opt-in parameters (2026-09-14, additive — the taxonomy tree's search uses them):** `?code_prefix=true` adds a **second** query for a partial `code` (`EC0123` → every class `EC0123…`) as the range `attributes.code >= <prefix> AND < <prefix+1>` (`prefix_upper_bound`, pure + 2 unit tests; matched as typed *and* upper-cased, since the full-text search is case-insensitive), its hits merged into the result (prefix hits first, then the full-text hits by `score`, deduped by id); `?completeness=false` skips the per-hit badge, which costs **~0.3 s per hit** (measured: 5 hits with `?locale=` = 1.4 s, without = 9 ms). The import worker maps that to `existing` (`meadow/worker/imports.py`) and the bulk `add_relation` to "unchanged", so a repeated MEF import is idempotent for edges too (`plan/detail/demodaten-generator.md` §4.2/§9). **Edge metadata (`PATCH /references/{id}`, editor+):** updates a reference's `attributes`; keys must be declared in the definition's `attributes` template when non-empty (`validate_edge_attributes`), and `create_reference` applies the same check. A SurrealDB RELATION-table quirk: a trailing `SELECT * FROM $r` in the same statement as `UPDATE $r SET …` returns no rows, so `update_reference` re-fetches in a separate statement.
- **Completeness fast path must ask the object's own attributes (2026-09-17):** both `compute_with_required` (single) and `compute_batch` (list, `stats`) may answer 100 % early — but only when `own` carries **every** required name (`all_required_present`, unit-tested). The batch version asked the *inheritable* subset instead, so an object whose only deficits were **non-inheritable** class features counted as complete: `GET /objects` said 100 % for variants that `GET /objects/{id}` scored 40 % and whose `category-attributes` listed three missing mandatory features (2 376 variants affected — only the 212 that happened to miss an inheritable name were flagged). Rule: single and batch path share the predicate; a difference between them shows up as a dashboard contradicting the detail view.
- Completeness (`src/completeness.rs`): computes an object's **Vollständigkeit** as the percentage of its type's required attributes (`required_types` on `attribute_definition`) that are set. `compute(cache, db, object_id, object_type, locale, own_attributes)` resolves inheritance (`inheritance::resolve_inheritance`) and splits required names into set/missing via `split_set` (pure, unit-tested): a name is *set* when its key is present in `own` attributes (even an explicit empty/null value, which breaks inheritance) or when it was inherited as a non-null value; 100 when the type has no required attributes. `compute_with_required` has a **fast path**: if every required name is already present in `own` it returns 100% without resolving inheritance. The `required_names`/`compute_with_required` are `pub(crate)` so aggregators can reuse required names per type. **`compute_batch`** (Phase 8, used by `GET /objects/stats`) resolves completeness for many objects in one pass: a single `load_parent_map` edge query (`SELECT in, out FROM reference WHERE definition_id='rel_depends_on'`) builds a child→parent map, `inheritable_names` from the cache gates which required names may be inherited, and the chain walk (`resolve_missing_in_memory`, pure + unit-tested) fills values in-memory — avoiding one DB query per ancestor per object. Wired into `objects.rs`: `GET /objects?locale=<code>` adds `completeness: { "<code>": <0–100> }` per object; `GET /objects/{id}?locale=<code>` adds `completeness` and `missing_required` (list of missing required attribute names, for the form widget); `GET /objects/stats?locale=<code>` returns the dashboard aggregation `{total, references, by_type, by_status, incomplete_by_type}` (object counts by type/status from a **`GROUP BY type, status` aggregation** — 33 rows instead of loading every object — plus per-type incomplete counts via `compute_batch`, which now only loads the attributes of the types that *can* be incomplete, `completeness::incomplete_candidates` ↔ `MetaCache::types_with_required`; measured 2026-09-16: ~1.0 s cold in a release build / ~2.0 s in the debug build at 11 678 objects — dominated by the object/edge payload. **The whole payload is cached per working language** and bound to `MetaCache::stats_version`, a monotonic counter every write path bumps via `invalidate_stats()` (objects create/update/delete/batch/computed, references create/update/delete/reparent, relation definitions, object types, attribute definitions, class features, language tree); a payload whose version is stale is never served, the next call recomputes it. Warm calls answer in 1–2 ms instead of ~2 s (`plan/detail/demodaten-generator.md` §4.3/§9). **A cache miss is single-flight** (`MetaCache::stats_lock`, per cache key): the caller that missed computes while the other waiters of the same key block and then read the stored payload. Without it every concurrent miss recomputed the whole aggregation in parallel — measured 2026-09-16 (release build, 16 167 objects): 1.8 s for a single cold call, but 8.2 s **mean** for ten waiters (min 5.4 s, max 8.9 s) and ten times the database work; with the lock all ten waiters finish in ~2.1 s (load test `stats` p99: 11 216 ms → 69 ms). **`GET /objects` completeness filters (Phase 9):** `?completeness_lt=<n>` (keep objects strictly below `n` %) and `?missing_required=true` (keep objects that still miss a required attribute) — applied in `list_objects` via the pure helper `passes_completeness_filter` (unit-tested) after the per-object `compute` (which resolves inheritance, so a page is filtered correctly even when the ancestors are not part of the page; `compute_batch` is only exact over a whole dataset). The filter cannot be expressed in SQL, so it is applied to a scanned window of up to 1000 rows and `start`/`limit` then slice the **filtered** result; `locale` may be omitted (default values).
- Batch update (`objects.rs`, endpoint `POST /objects/batch-update`, `object.update`): applies a list of partial changes (`[{id, attributes, status, …}]`) in one call; shared per-object logic with `PATCH /objects/{id}` via `apply_object_update` (rules/computed/workflow guard, outbox event, audit). Capped (verbindlich) at `MAX_BATCH_UPDATE_ROWS` (500) per call, returning `413 Payload Too Large` (`error::payload_too_large`) above the limit. The result is a per-item list (`{id, success, status?, error?}`); an invalid/expired JWT is reported per item as `error: "invalid or expired token"` (HTTP 200, `success: false`).
- Batch delete (`objects.rs`, endpoint `POST /objects/batch-delete`, `object.delete`, `?emit_events`): `{ids: [...]}` (record ids or bare keys, duplicates dropped, `object_root` refused, `MAX_BATCH_DELETE_ROWS` = 500 → `413`) deletes all of them — cascade included — in **one** transaction. Motivation and measurement: `DELETE /objects/{id}` costs ~0,4–0,6 s per request while its statements run in 80–400 µs, so a 3 000-object cleanup spent ~20–27 min in call overhead; batched it is **12 ms/object** at 100 ids per call (measured: 591 ms → 12 ms, the demo cleanup dropped to 0,9 min). The cascade union is computed from **one** composition-edge query (`references::composition_children` + the pure `subtree_keys_in`; `subtree_keys` is now the same two steps) instead of one traversal per root; unknown ids are returned in `missing` (a cascade may already have removed them) and an audit row `objects_deleted` (`to: {deleted, cascaded}`) plus **one outbox `object.deleted` event per deleted root** are written in the same transaction, so event consumers see the same messages as before.
- **Batch upsert (`objects.rs`, endpoint `POST /objects/batch-upsert`, `object.create` or the machine key, `?emit_events`):** the import worker's write path — body `{match_by, key?, objects: [{…object fields…}]}`, `MAX_BATCH_UPSERT_ROWS` = 500 → `413`. `match_by` is `source` (default) or `id`; `key` names the business-key attribute when the batch matches by key **and** the entries carry different keys (matching normally uses the type's `key_attributes`, so the worker omits it). `parent` (optional, `object:<key>` or a bare key) is the **composition parent of a new object**: the entry is then created under that parent in the same transaction instead of on the universal root, the parent must be a live object (else the entry fails with `parent object \`object:<key>\` not found` — no object is written) and the composition definition's type restriction is enforced (`check_type_restriction`, one parent-type query for the whole batch via `live_object_types`). For entries that **update** an existing object `parent` is ignored (moving is `PATCH /objects/{id}/parent` or a `depends_on` reference). Rationale (measured 2026-09-17): creating such an object on the root left it in the wrong place in the structure tree while the caller only saw a failed reference afterwards — an object whose intended parent is missing must not exist at all. Matching order mirrors the single write path: business key → `id` (only with `match_by: "id"` and a `source_id` of the form `object:<key>`) → source reference (`source` + `source_id`, source default `api`). Response: per entry `{index, id, action: created|updated|failed, error?}` plus `{created, updated, failed, results}` — **one bad entry never fails the batch**, it is reported and the rest is written. Flow: prepare (no DB) → register types and read `key_attributes` **once per type** → lock all key values (`AppState::key_locks`) → in-batch duplicate detection → `key_values_in_use` grouped per (type, key) → source/id lookup → parent types (one query) → per entry the same rules the single path runs (`validate_attribute_values`, `save`, plus `transition` when the status changes) → **one transaction** (`FOR … CREATE`, the composition edges — `LET $parent = IF $c.parent IS NONE THEN object:object_root ELSE type::record('object', $c.parent) END` — , `FOR … UPDATE … MERGE`, `FOR … UPDATE … SET version = version + 1`, `FOR … CREATE outbox_event`) → `audit::record_many_best_effort` plus one inherited-cascade queue per updated object. Motivation and measurement: the per-request overhead dominates like it does for batch-delete — single-write import 11–25 objects/s vs **~73 writes/s** through the batch path (measured live: 1 456 writes / 20 s; worker `BATCH_UPSERT_SIZE` = 200), and the per-entry payload matches the single endpoints so the worker's retry pass works unchanged. **Report mode (2026-10-16):** `upsert_objects(state, headers, params, body, dry_run = true)` runs everything up to and including the per-entry checks and stops before the transaction — no `CREATE`/`UPDATE`, no `outbox_event`, no audit row, no cascade queue, no `ensure_registered` (an unknown type is only looked up), the record id an entry would create stays empty and the rule evaluations run as `WriteEvaluation::as_dry_run` (no failure counter moves, no rule log is written). Its only caller is `POST /imports/preview` — so a preview cannot drift from the write.
- **Composition edges are created with `RELATE`, never with `CREATE reference SET in/out` (`objects.rs::create_object`):** a new object hangs on the universal root through a `rel_depends_on` edge written as `LET $new = type::record('object', $key); RELATE $new->reference->object:object_root …` inside the transaction. `CREATE reference SET in = …, out = …` **parses and stores a row but is not a real `RELATION`** — the next traversal answers `Found record … which is not a relation, but expected a RELATION` and the failure surfaces as a masked `409 failed transaction`. `RELATE type::record('object', $key)->reference->…` is a **parse error** over the Rust SDK ("Unexpected token `::`", although the HTTP endpoint accepts it): bind the record with `LET` first. Consequence for imports: `PATCH /objects/{id}/parent` **re-parents**, so it needs an existing edge — a MEF `depends_on` entry for an object **without** a composition edge fails with `400 "object has no composition parent"` (reported per entry in `result.references`; the import continues). Objects written through `POST /objects`/`POST /objects/batch-upsert` always carry the root edge, so this only concerns restored/hand-made rows.
- **Batch references (`references.rs`, endpoint `POST /references/batch`, `reference.create`, `?emit_events`):** `{references: [{source, target, definition_id, attributes}], reparents: [{source, parent}]}`, `MAX_BATCH_REFERENCE_ROWS` = 500 for **both arrays together** → `413`. Motivation and measurement: `POST /references` costs a full write path (object + definition lookups, transaction, audit, outbox, HTTP) **per edge**, so the reference phase of a 7 992-object chunk ran at **11.5 edges/s** while the same chunk's objects went through `batch-upsert` at ~141 objects/s (`plan/detail/demodaten-generator.md` §4.3). The batch endpoint amortises exactly that: relation definitions and all involved objects are read in **one** query each, existing edges in **one** query per definition (reported as `existing`, so idempotency no longer depends on the `409` message), all edges are locked as one critical section (`crate::key_lock`, the same key `create_reference` uses) and written in **one** transaction. `references` follows `POST /references` (a `rel_depends_on` entry must find a source **without** a parent, else `"source object has already a composition parent"`); `reparents` follows `PATCH /objects/{id}/parent` (identical messages: `"object has no composition parent"`, `"would create a cycle"`, and a no-op move reports `existing`). Per entry it answers `{kind, index, source, target, action: created|existing|reparented|failed, error?}` — **one bad entry never fails the batch**; a failed transaction reports **all** its entries as `failed` (so a caller's retry pass re-applies exactly those rows). Unknown objects, unknown relation types, role violations, undeclared edge attributes, in-batch duplicates, cycles and self-edges (`source == target`, `object:<table>` prefix checked) are all per-entry failures. SurrealQL notes: creating edges inside a `FOR` body needs `LET $src = type::record('object', $row.source); RELATE $src->reference->$tgt SET …`, and a re-parent in a loop is `DELETE reference WHERE in = $child AND definition_id = 'rel_depends_on'; RELATE $child->reference->$parent SET …;` — both verified against the running server (§4.4 Punkt 10 of the plan detail doc).
- **Bulk reference read (`references.rs`, endpoint `POST /references/query`, `reference.read`):** `{ids: [object:<key>…], limit?, start?}` → `{references: [raw edge rows], truncated}`, at most `MAX_QUERY_REFERENCE_IDS` = 500 ids per call and `MAX_REFERENCE_PAGE` = 50 000 rows per page (`ORDER BY id`, so `start` paging is stable). It answers **both directions** and returns the **raw** rows (`id, definition_id, in, out, attributes`) — `GET /objects/{id}/references` costs one request per object and enriches every row with both endpoint objects, which for the complete MEF export (11 632 objects) would be one round trip per object plus data the export discards. The ids are rendered as a record list literal (`keys::record_list_literal`, index scan), never as a bound list. Motivation: `plan/detail/datenexport-import-ui.md` §5.2, `docs/integration/mef-and-events.md` §1.6.
- **Classification standards (`src/api/classification_standards.rs`, table `classification_standard`, endpoints `GET /classification-standards` + `GET|POST|PATCH|DELETE /classification-standards/{id}`):** the registry of the external standards (ETIM, ECLASS…) this catalogue was **loaded** with — one row per `code` + `version` (`etim`, `10.0`, deterministic record key `etim-10-0`), with `name`, `source` (the artefact the package was built from), `node_type` (the object type of the class nodes, must be a taxonomy type ⇒ else `400`), `notes`. Reads take `viewer+`/`X-Api-Key` (the export worker needs it), writes are admin. The list is assembled in Rust (a handful of rows) and adds the derived `feature_system_name` (`ETIM-10.0`) and `current` (newest version per `code`, compared **numerically**: `10.0.1` > `10.0` > `9.1`; `version_key` is pure and unit-tested); `?counts=true` adds the live `class_count`/`feature_count` of the node type (two extra queries: the class ids via `VALUE type::string(id)`, then `SELECT type::string(category_id) AS class_id, count() AS total FROM category_attribute GROUP BY class_id` summed in Rust — the grouped scan is **linear**, while the earlier `WHERE category_id IN array::map($keys, type::record($k))` shape needed a lookup per table row and did not return within 300 s once the full ETIM bundle (5640 classes) was installed; record ids are normalised without backticks before comparing). **Why:** the BMEcat export used to take the reference feature system version from a free-text profile field, so a catalogue could claim a version it never installed; `{id}` accepts `code@version` or the record key, and the record key is always derived from the row's own `code`/`version` — SurrealDB serialises a quoted id back as ``classification_standard:`etim-10-0` ``, and splitting that string would carry the backticks into the key. Deleting a row removes **no data** (classes/features/attributes are catalogue data). Details: `plan/detail/kategorisierung.md`.
- **Class features (`src/class_features.rs`, `src/api/category_attributes.rs`, Stage B):** `category_attribute` attaches attribute definitions to a taxonomy node (`category_id` record + `attribute` **name**, `required`, `position`, unique `(category_id, attribute)`). An object assigned to a class (any `role: category` relation) gets the class's features **plus** its ancestors' (`depends_on` chain, `ancestor_chain`/`ancestor_chain_live`). Two paths: per-object (`resolved_features`, few small indexed queries) and batch (`class_required_names_batch`, reusing the `depends_on` map of `completeness::compute_batch`). `class_required_names` feeds `completeness` (single + batch, same semantics as the API), so mandatory class features count into the percentage and `?missing_required`; `rules::missing_class_features` puts them into `ctx.missing_features`. Endpoints: `GET /objects/{id}/category-attributes` (resolved + `missing` + **`classes`** — the taxonomy nodes the object is assigned to, so a consumer can name the classification block itself (the BMEcat export writes one `PRODUCT_FEATURES` per class); editor+/`X-Api-Key`), `GET|POST /categories/{id}/attributes`, `PATCH|DELETE /categories/{id}/attributes/{attribute}` (admin; unknown attribute or non-taxonomy node ⇒ `400`, duplicate ⇒ `409`). Deletes of attribute definitions, class nodes and objects clean up the rows (renames are carried over). `ancestor_chain`, `merge_names` and `own_attributes` are unit-tested. **Own attribute as a carrier (`standard_codes`, 2026-09-13):** `attribute_definition.standard_codes` (`option<object>`, `{standard: code}`, e.g. `{"etim": "EF000040"}`) binds an **own** attribute to a standard's feature code, so a maintained product can be classified without adopting the standard's attributes. `feature_bindings` (now **cached** in `MetaCache::feature_bindings`, invalidated with the attribute definitions — measured: 17 397 definitions / **~0.3 s per call** with ETIM 10.0 installed, which every per-object `completeness::compute` paid, so `GET /objects?ids=1&locale=` went 332 ms → 69 ms, `?limit=20&locale=` 5.7 s → 0.5 s and a picker hit with badge 289 ms → 39 ms) and `resolve_attribute` (pure, unit-tested) picks the **binding** first, then the attribute named like the code, then the code itself. `ResolvedFeature` therefore carries both `name` (the code an export transmits) and `attribute` (the attribute that holds the value): `required`/`missing`/completeness count the **attribute**, `FNAME` is the **code**. **Reference data:** an attribute definition flagged `reference_data` is a standard's vocabulary, not the customer's own attribute set — the frontend keeps it out of the form (unless the object carries a value), the export field selection (behind a switch), the bulk wizard and find/replace, while the class-feature resolution and the export keep working with it unchanged.
- Relation usages (`role`) & taxonomy types (2026-09-11/12): `relation_definition.role` (`schema.rs`, `option<string>`) classifies a type's **usage** – `composition` | `category` | `collection` | `link` (Default). The seed (`src/seed.rs`) sets the four built-in roles, marks exactly `object_type:category` as the system **taxonomy** (`object_type.taxonomy`, `object_types.rs::PRIMARY_TAXONOMY_TYPE`; other system types are asserted `false`, existing rows without the field are backfilled) and migrates rows without a role to `link`; `POST /relation-definitions` accepts `role` for custom types (`link`/`category` only, `400` for the reserved roles), validates an explicit `target_types` list of a `category` role against the registered taxonomy types (`check_taxonomy_targets`, `400` naming the allowed types) and `PATCH` rejects a role change for `system: true` types; a role change to `category` drops non-taxonomy targets. `create_reference` enforces the role: a categorisation may only point at a taxonomy type (`is_taxonomy_type`, error lists `category_target_types(db)`), a collection only at `collection`. `?count_members=true` (`references.rs`) adds `memberCount` for every taxonomy-typed child, and `GET /objects?uncategorized=true` (`objects.rs`) excludes all taxonomy types plus `root` (`$taxonomy_types`). `POST`/`PATCH /object-types` carry `taxonomy` (custom types only, `system` types ⇒ `400`). `references::PRIMARY_CATEGORY_DEFINITION` (`rel_category_member`) and `resolve_category_definition(db, requested)` centralise the categorisation relation types; `role_of`, `custom_role`, `role_target_types` and `check_taxonomy_targets` are unit-tested.
- **Seed semantics (`src/seed.rs`): create-if-missing.** All seeded records (relation-definition identities, universal root, object types, units, languages) are written with `INSERT INTO … VALUES … ON DUPLICATE KEY UPDATE id = id` (SurrealDB ≥ 3.2), so a core restart **never** overwrites runtime edits (labels, `source_types`, `target_types`); only the structural identity of the built-in relation types (`kind`, `system`, `role`) is asserted with a follow-up `UPDATE`. Before this change an `UPSERT … CONTENT` on every start silently reverted those edits.
- Bulk operations (`objects.rs`, endpoint `POST /objects/bulk`, `object.update`): queues a `bulk_operation` `job_run` for a mass operation. Payload `BulkObjectRequest {op, object_ids, parameters}`; `BULK_OPS` = `set_attribute|clear_attribute|change_status|send_for_approval|add_category|remove_category|add_relation|remove_relation|change_parent|replace_text|consolidate_inheritance|delete`. Validates the editor role, a known `op`, and a non-empty `object_ids`, then calls `jobs::queue_run(..., "bulk_operation", parameters, "manual", &claims.sub)` with `parameters = {op, object_ids, parameters}` and returns `202` with the `job_run`. The worker (`meadow/worker/bulk.py`) applies the operation per object and stores `{op, processed, succeeded, skipped, failed, replacements, approvals, results[]}` in `job_run.result` (`skipped` counts objects without a match for `replace_text`, `approvals` the successful workflow transitions; `consolidate_inheritance` adds its own report keys, see `plan/detail/vererbung-konsolidierung.md`).
- Rule recompute (`src/api/rules.rs::recompute_rule`, `POST /rules/{id}/recompute`, admin/superadmin): queues a `business_rule` `job_run` (no definition) whose parameters embed the rule `{name, type, script}`, `applies_to`, and optional `object_ids`. The worker executes and reports per object.
- Computed write-back (`src/api/objects.rs::update_computed`, `PATCH /objects/{id}/computed`, `object.update` or the machine key): machine-to-machine path that merges only declared-`computed` values (`rules.rs::resolve_computed`) into an object without re-running rules (used by the recompute worker).
- Cron scheduler (`src/scheduler.rs`): a background task (`tokio::spawn` in `run()`) keeps `tokio_cron_scheduler` in sync with enabled scheduled `job_definition` records (6-field seconds-first cron) and, on each fire, creates a `job_run` (`trigger: schedule`) and publishes it to JetStream via `queue_run`. Sync interval from `SCHEDULER_INTERVAL_S` (default 60). `validate_schedule()` parses an expression with the same parser the scheduler uses (`Job::new_async`) and is called by every write path that stores one — `POST /jobs`, `PATCH /jobs/{id}` (empty string = clear), and a collection's `refresh_interval` — so an unusable schedule fails with `400` instead of becoming a definition that only logs a warning every minute (`tokio-cron-scheduler` needs **six** fields: `0 3 * * *` parses to `ParseSchedule`, `0 0 3 * * *` fires at 03:00). A definition that still cannot be registered is skipped with a warning, not by aborting the tick: one legacy row must not stall every other cron job.
- Dead-letter monitor (`src/jobqueue.rs::monitor_dlq`, background task): ensures the `JOBS_DLQ` stream (`jobs.dlq.*`, Limits retention, manual cleanup) and, for each dead-lettered message, marks the corresponding `job_run` as finally `failed` via `jobs::fail_run` („dead lettered after N attempts“).
- Log-retention cleanup (`src/log_cleanup.rs`, background task): deletes `log_entry` rows older than `log_retention_days` (resolved from system settings via `system::resolve_retention_days`; default 30, validated 7–90) every `LOG_CLEANUP_INTERVAL_S` seconds (default 3600). The ingest rate-limit (`log_rate_limit`) is not yet enforced (deferred per api-design).
- Request limits (`src/app.rs` + `src/rate_limit.rs` + config fields `max_body_bytes`/`rate_limit_per_minute`): a global axum `DefaultBodyLimit` (env `PIM_MAX_BODY_BYTES`, default 10 MiB) caps request bodies; routes with a larger need re-declare their own `DefaultBodyLimit` (e.g. `/imports` and `/config/import` at 100 MiB — a complete MCF of the demo instance is 15 MB, 17 462 attribute definitions, so a restore used to fail with `413`), which — as the innermost layer — overrides the global one. `RateLimiter` (env `PIM_RATE_LIMIT_PER_MINUTE`, default **0 = disabled**) is a per-IP fixed-window limiter (in-memory `HashMap<IpAddr, (Instant, u64)>`, 60 s window) applied as the outermost router layer and returns `429` when exceeded. It reads the peer IP from `ConnectInfo<SocketAddr>`, so the server is served via `into_make_service_with_connect_info::<SocketAddr>()`; it does **not** honor `X-Forwarded-For`, so behind a reverse proxy all clients share the proxy IP (acceptable for direct/LAN deployments; revisit if a proxy terminator is introduced). Defaults keep dev unaffected (2 MiB body, no rate limit).
- **Read-path performance rules (2026-09-14, all figures measured against the dev DB: 17 379 attribute definitions, 5 640 classes, 76 625 `category_attribute` rows):** id lists are rendered as **record literals** (`[object:a, object:b]` via `api::keys::record_list_literal`, which drops keys that are not `[A-Za-z0-9_-]` — such keys cannot exist — and **quotes** a key containing a dash: `object:ok-1` would be parsed as the subtraction `object:ok - 1` and answered with `500 Cannot perform subtraction with 'record' and 'none'`, found 2026-09-16 through a variable id in `POST /references/batch`; the trap existed for `?ids=` and `POST /objects/batch-delete` as well) instead of `id IN array::map($keys, |$k| type::record('object', $k))`, because SurrealDB evaluates that expression **per candidate row**: 100 keys 1.9 s, 1 000 keys 16.6 s, 5 640 keys 110 s, while the literal list uses the id index (100 keys 49 ms, 1 000 keys 178 ms). `MetaCache::required_names` caches the per-type required names (cleared by attribute-definition **and** object-type writes, `invalidate_object_types`), `completeness::compute_batch` resolves the whole page in one pass (including `load_ancestor_attributes` for the objects' ancestor chains, so a batch resolves inheritance exactly like the per-row path) and `GET /objects` computes completeness **once per page** instead of once per row; `class_required_names_batch` loads `category_attribute` only for the contributing classes (assigned nodes + ancestor chains) instead of the whole table (6.8 MB), and `config/category_attributes` reads the class nodes with a type filter instead of an id list. Measured effect: `GET /objects?limit=1000&locale` 18.1 s → 0.24 s, `?missing_required` 17.8 s → 0.22 s, `GET /objects/stats` 3.0 s → 0.4 s, `GET /config/export` 81 s → 8.4 s. `GET /attribute-definitions/vocabulary` serves the projection of **all** definitions from `MetaCache::attribute_vocabulary_json` (a **serialized** body — 7.41 MB; cloning and re-serializing it per request cost more than the query it saves): the `/export` wizard's field selection needs every definition, and paging `GET /attribute-definitions` cost 18 requests / 4.5 s — it is also capped at 1000 rows, so with an imported standard (17 377 `EF…` features, ordered by codepoint) the late-sorted own attributes were unreachable; today **five** consumers load the vocabulary projection (`/export` wizard, `/attribute-definitions` catalog page, `/products` grid — which turns it into picker rows and **columns only for the own catalogue plus standard attributes that carry data**, `grid.offered_definitions`, 17 377 standard columns would be unusable — the `/products/{id}` product form and the pickers on `/object-types`, `/relation-definitions`, `/categories`, `/import` and `/connectors`, 2026-09-17: the form rendered **no field** for an own attribute the grid could edit, because its paged list stopped inside the standard's vocabulary). The projection carries `computed`, `enum_set_id` and `constraints` besides the selection fields — three fields the grid and the form render (a **computed** attribute must not be editable inline, an `enum` cell needs its set to show labels, a reference field its `target_types`); **measured 2026-09-17 (17 463 definitions): 6.49 MB without and 7.41 MB with those three fields** (`computed` false and `enum_set_id` null for every standard row, `constraints` set on **5** rows — `min`/`max`/`target_types` only, the legacy inline `enum_values` on none, which is why the option list itself stays out of the projection; the `enum` type requires an `enum_set_id`). The vocabulary call served the selection-only body in **1.5 s cold / 9 ms warm**; measured 2026-09-17 with the three added fields (**fresh core, debug build**): **8.2 s cold / 25 ms warm** — a cold body is re-serialized once, a warm one is handed out verbatim; page build 12.0 s → 2.2 s (grid), and the cache is cleared by the definition writes **and** by the MCF import (`POST /config/import`, which writes definitions directly and left every metadata cache stale before). Remaining known bulk cost (payload-bound): `GET /config/export` ≈ 10–13 s / 14.3 MB (`attribute_definitions` 7.8 s/9.5 MB + `category_attributes` 7.5 s/4.7 MB) — a click-triggered admin action, not a page build. **Measurement note:** `Invoke-WebRequest` inflates multi-megabyte responses by roughly 1.4 MB/s (it showed 25 s where a Python client measures 10 s); measure payload-bound paths with a Python client or the browser's page timing, and never compare a PowerShell timing against a Python one.
- **Bound record vs record literal (2026-09-16, measured on the `perf` dataset: 70 379 objects, 275 961 `reference` rows, 70 314 of them `rel_depends_on`):** a **bound** record (`WHERE out = $parent`) is planned as a plain `Filter` on top of an `IndexScan` over the *definition* column — i.e. a scan of the whole definition partition, plus a sort when the page is ordered. `GET /objects/{id}/children?limit=100` therefore needed **245–305 ms** for a **childless** object (load-test outlier 940 ms). A record **literal** in the query text (`out = object:`<key>``, `api::keys::record_literal` — same charset rule and dash quoting as `record_list_literal`) is constant-folded and drives `idx_ref_out_def` (`access: [object:…, 'rel_depends_on']`): **3.3 ms** mean over 100 targets, and the read load test went from 41.6 to **310.7 req/s** (`children` 940 → 25 ms, 0 errors). A **bound `definition_id`** stays fine (filter on the index scan) and `WITH INDEX` does **not** help while the record is bound (falls back to `TableScan`, 441 ms measured). Used by `list_object_children`, `edge_exists`, the reference cascade of `GET /objects/{id}/references` (`UnionIndexScan` instead of `TableScan`) and `class_features::assigned_node_keys`. **Rule: never bind a record filter — render it as a literal, for single values as well as for lists.**
- **Cycle check of `POST /references/batch` (2026-09-16):** it walks **up from the new parent** (`load_parent_chain` over the batch's new parents + `creates_cycle(&chain, &batch_parents, source, target)`, batch assignment before stored parent, self-edge = cycle). The first version compared the *source* against a set that also contained the new parents **themselves**, so every source that was a parent elsewhere in the same batch came back as `"would create a cycle"` — the perf model import lost 10 category edges that way. The single-write endpoints (`POST /references`, `PATCH /objects/{id}/parent`) were correct, which is why the `demo` profile never showed it: a data change must be checked against **every** write path. Regression tests: `batch_cycle_check_walks_up_from_the_new_parent`, `batch_cycle_check_sees_assignments_of_the_same_batch`.
- **A correlated subquery in the projection costs ~11 ms per row; an `IN` list costs the list length per scanned row (2026-09-22, measured on the products grid, 1000-row page):** the products page asked for `?releases=true&locale=en&resolve_inheritance=true` and needed **19.5–22 s**. Split: plain list 0.7–0.8 s, `+locale` (completeness) +1.0–1.2 s, **`+releases` +11–13 s** (the projection's `(SELECT … WHERE object_id = $parent.id)` runs once per candidate row, i.e. per row of the page — SurrealDB does not hoist it into one pass; the plan for the equivalent standalone query is a `Filter` over a scan), **`+resolve_inheritance` +6–7 s** (one `reference … WHERE in IN [<1000 page keys>]` query per level, and an `INSIDE` list is evaluated **per scanned row**: 10 ids 168 ms, 100 ids 262 ms, **1000 ids 2.6 s** — the level loop then re-sent all 1000 keys (with duplicates) per level). Fixes: releases are one bulk query for the page + grouping in Rust (`objects::attach_releases`), inheritance is `load_parent_map` + `load_ancestor_attributes` + an in-memory walk (see the inheritance bullet). Result: **19.5–20.3 s → 2.1–2.3 s** for the grid query, page TTFB 22.3 s → ~4 s, identical response bodies (checked against the previous binary). The lesson for a new read path: a literal list is only cheap while it is **small** (the id-index win in the bullet above applies to *lookups*), a page-sized list on a big table wants a whole-map query plus in-memory work, and no list at all beats any list — `attach_releases` renders exactly the page's ids, and would still be fine as a full `release` scan (65 ms / 2603 rows). **What is left on that page (2026-09-22):** the page-proportional part of the list plus the page build (see the frontend note); the fixed batch cost is gone with the two caches below. The read path logs its phases at `debug` level — `RUST_LOG=info,pim_core::api::objects=debug,pim_core::inheritance=debug,pim_core::completeness=debug` prints `composition loaded keys=… ms=…`, `completeness batch computed class_features_ms=… total_ms=…` and `inheritance batch resolved walk_ms=…`; exactly that located the next cost.
- **Version-bound reference caches (2026-09-22, `MetaCache::composition_map` / `MetaCache::category_edges`):** the composition map and the categorisation edges are read on **every** page load, and only edge writes can change them, so both are cached bound to `stats_version` — the same trigger `cached_composition_types` uses (reference/object/type/class-feature writes bump it, `references.rs` does so in nine places). Measured on a 1000-row grid page: the composition was loaded **twice** (871–1309 ms each) and the categorisation edges cost **~690–960 ms** per completeness call; warm they are **33–44 ms once** and **0–3 ms**, so the whole batch work of a page is ~100 ms. `inheritance::Composition` is the single preparation a request builds and hands to both batches — it also carries the **page's own attributes**, so the in-memory walk no longer depends on where an object and its parent sit in the page (the list orders by `created_at DESC`, and 217 edges in the demo data have a child *older* than its parent, i.e. re-parented objects; `lookup_maps` is pure and unit-tested).
- **List contract for a pager (`src/api/objects.rs`, 2026-09-23): `?sort=`, `/objects/count`, `/objects/attribute-usage`.** `GET /objects` sorts server-side with `?sort=<field>&order=asc|desc` — the field must be a **sortable** field of the search catalog (`search_schema::sanitize_field` + `catalog.field(..).sortable`: `type`, `status`, `created_at`, `updated_at`, `attributes.<name>[.<lang>]`), `id` stays the tiebreaker (a paging client must not skip or repeat rows), and everything else is `400` (unknown field, non-sortable `id`/`source`/booleans, a bad `order` — `?order` is validated even without `?sort`). `GET /objects/count` counts **the same filter chain** (the filter builder is shared: `ObjectFilter` + `build_object_filter`, the paging parameters are ignored) so a page and its total can never disagree; without a completeness filter it is one `count() … GROUP ALL`. `GET /objects/attribute-usage?sample=<n>` (default 1000, max 5000) answers which attribute names carry data among the first `sample` objects of the view (`{names, sampled}`; `carries_value` mirrors the frontend's `reference_data.has_value`) — the grid decides its **column set once per view** with it instead of per loaded chunk.
- **A completeness-filtered view is walked in Rust and its keys are cached (`MetaCache::view_keys` + `objects::completeness_view_keys`, 2026-09-23).** Completeness is the one filter SurrealQL cannot express (required names per type **and** inherited values), so its members are only known after resolving completeness for **every** candidate — narrowed to the types that can be incomplete at all (`completeness::incomplete_candidates`). The walk reads **lean** rows (`id, type, attributes, created_at`: ~1,4 MB where the full objects of the 4 614 candidates are ~7 MB), caches the ordered keys per `(filter, sort)` bound to `stats_version` (single-flight like `/objects/stats`), and the page is then fetched by id (`SELECT * … WHERE id IN [<page keys>] ORDER BY <order>`, 1000 keys → 0,18 s) so the rows stay complete (`status`, timestamps, `version`). Measured: page 1–3 of `?missing_required` 158/95/26 ms (the first request of a data version pays the completeness caches and costs seconds), `count` 1–14 ms warm, and the old "scan a 1000-row window, filter, slice" was **wrong** from page 2 on (the newest 1000 objects of a filtered set are not its first matches).
- **An id-subquery inside an id filter is the same trap as the per-row expression (2026-09-23, measured):** `uncategorized` and `released_for` resolve their id list in Rust and render a **record literal** (`references::categorised_object_keys` is the flat counterpart of `category_member_keys`; `objects::released_object_keys` reads the `release` index). `SELECT * FROM object WHERE … AND id NOT IN (SELECT VALUE in FROM reference WHERE definition_id = 'rel_category_member') ORDER BY created_at DESC, id LIMIT 1` took **159 s** against **1,4 s** with the literal list — with `SELECT id` the same subquery stayed at 0,36 s, so the projection decides whether the subquery runs per candidate row.
- **The search catalog carries the conventional label field `attributes.name` (2026-09-23, `search_schema.rs`).** Every object's display label is resolved from it (`language.rs::resolve_object_label`, `code` as the taxonomy fallback) and the grid's first column is that name, so it belongs to the field vocabulary even though no `attribute_definition` has to exist for it — before, neither the search form nor `?sort=` could reach a name without a registered definition. It is declared `multilingual` (all active data languages), which is what makes the per-language spellings usable: **sort** a multilingual column by its language (`attributes.name.de` — the base key orders by the stored map instead), and filter it through the language too (the base key of a multilingual field is the "all languages" form `search_form.language_base`, which compares the stored value and therefore matches nothing for a text operator). The catalog is cache-backed (`MetaCache::search_catalog`, `search_fields_json`; the document is ~5,9 MB and serializing it costs seconds in a debug build) — `GET /objects?where=` and every saved-search execution used to rebuild it per request (measured 4,5 s / 5,5 s).
- **Clearing optional text fields on `PATCH /attribute-definitions/{id}` (2026-09-15):** `computed_rule`, `unit_id`, `display_unit_id` and `enum_set_id` are `option<string>` fields, and `UPDATE … MERGE` cannot write the distinct `NONE` — so a clear is collected in `clear_fields` and applied as **one** `UPDATE $obj UNSET a, b;` statement (which shifts the index of the trailing `SELECT`). The trigger is `patch_text` (`deserialize_with`): a **present `null`** becomes `Some(None)` = "clear", an **omitted** field stays `None` = "leave it as it is", and an empty/whitespace string clears as well. A plain `Option<Option<String>>` cannot tell those apart (serde maps JSON `null` to the *outer* `None`), which is why `{"computed_rule": null}` silently kept the old rule — found while wiring the dialog to clear fields that lost their meaning. On `POST` an empty string simply means "no value" (`text_change`), so a client may send the same payload for create and update.
- SurrealDB `option<T>` fields reject JSON `null` (the distinct `NULL` value, not `NONE`): omit `None` option fields when building `CREATE ... CONTENT`, and clear them with `UPDATE ... SET field = NONE;`.
- **SurrealDB quotes a record key that needs it** (`` classification_standard:`etim-10-0` ``, `` export_profile:`meadow-bmecat` `` — any key with a dash). A serialised `id` therefore carries the **backticks as part of the string**: `id_of()` (`api/config.rs`) strips the table prefix **and** the quoting, because `type::record(table, key)` with the backticks addresses a *different* (non-existent) record — an `UPDATE` changes nothing and a `DELETE` reports a removal that never happened. Every endpoint that resolves a reference (record key, `id`, or name) must accept all three spellings, so a caller can pass back the `id` it just received.
- The SurrealDB `Surreal<Client>` is shared behind `Arc` (`db.rs`): cloning `Db` (once per request via `AppState`) must reuse the **same** session, because cloning `Surreal<Client>` directly creates a fresh session whose namespace/database replay is asynchronous and intermittently fails with "Specify a namespace to use" under concurrency.
