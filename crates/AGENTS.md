# crates — Rust Source Code

## Purpose

Owns the Rust workspace (root `Cargo.toml`) and all Rust crates. The core service `pim-core` is the headless REST API (Axum + utoipa OpenAPI): sole write access to SurrealDB, JWT authentication/authorization, scheduler, and CRUD-event publishing to NATS JetStream.

## Ownership

- Root `Cargo.toml` (workspace) and every crate under `crates/`.
- `crates/pim-core/` — the PIM core service.

## Local Contracts

- Implementation stays consistent with `plan/meadow-pim-architektur.md` (sections 4–7, 9) and its detail documents; otherwise the plan is updated in the same change.
- Rust Edition 2024; MSRV 1.90 (`surrealdb` → `roaring`). `jsonwebtoken` requires a crypto backend feature (`rust_crypto` is used; `aws_lc_rs` is faster but needs NASM + CMake on Windows).
- `pim-core` module layout: `src/lib.rs` + `src/main.rs` (thin entry); top-level modules `config`, `db`, `error`, `event`, `audit`, `auth`, `cache`, `language`, `log_cleanup`, `inheritance`, `completeness`, `jobqueue`, `rate_limit`, `rules`, `scheduler`, `schema`, `seed`, `attribute_values`, `attribute_definition_types`; API handlers in `src/api/{health, auth, config, exports, export_profiles, objects, object_types, channels, attribute_definitions, attribute_groups, jobs, keys, languages, references, rules, search, system, users, groups, imports, connectors, connector_schema, units, saved_searches, search_schema, enum_sets}`.
- **Channels & channel-specific releases** (`src/api/channels.rs`, `schema.rs`, Phase 9): `channel` is a configuration catalog keyed by its stable **`code`** (record key, immutable; multilingual `label`, `description`, `active`, `position`); `release` holds the channel state of an object as **one row per `(object_id, channel)`** (unique index, `object_id` is a native `record<object>`, `channel` is the code, `status` uses the object-status vocabulary). Endpoints: `GET /channels` (editor+), `GET/POST/PATCH/DELETE /channels…` (admin; delete → 409 while releases use the channel), `GET/PUT /objects/{id}/releases` and `DELETE /objects/{id}/releases/{channel}` (`api_key_or_role` ROLE_EDITOR, so the bulk worker can write them like every other object write). `PUT` replaces the row (delete + create in one transaction) and both release writes run the **`workflow_guard` rules in `transition` mode** with `EvaluationContext { channel, release_status }` (`RulesClient::evaluate` sends them as `channel`/`release_status`; the Python contract exposes `ctx.channel`/`ctx.release_status`, `withdrawn` marks a withdrawal, `obj.status` stays the *global* status, the rule view carries own + **inherited** values, no language resolution). Audit `object_released`/`object_release_withdrawn`, outbox `object.released`/`object.unreleased`; `DELETE /objects/{id}` deletes the releases of the cascade with the object (per record via `FOR … DELETE release WHERE object_id = $r` — `object_id IN $recs` does **not** match the typed record field). `GET /objects` gained `released_for=<code>` (+ `release_status`, default `published`), `releases=true` (correlated subquery `(SELECT VALUE {channel, status} FROM release WHERE object_id = $parent.id …)`) and the bulk ops `release_for_channel`/`withdraw_from_channel`. MCF: section `channels` directly after `languages` (releases are data, not configuration); the `json_export` profile gained `channel`, which fills a `channel` export source without a code.
- `cache::MetaCache` (in-memory) caches the multilingual/inheritable attribute names, the `url` attributes (`name` + `multilingual`), the language fallback chains, the per-type required names, the feature-code bindings and the serialized attribute vocabulary; attribute-definition writes and object-type writes invalidate it, the MCF import clears it. The vocabulary projection (`VOCABULARY_FIELDS`) carries exactly what its consumers render — since the attribute catalog joined the export wizard that is 11 fields (`id, name, label, type, group_ids, multilingual, applicable_types, reference_data, is_key, inheritable, required_types`; body 5.83 MB → ~6 MB). **Decision (2026-09-15, do not re-open without a trigger):** this in-process cache with explicit invalidation **is** our caching strategy — no HTTP cache layer (`ETag`/`Cache-Control`/conditional requests), no shared/proxy cache, no Redis while a single core instance runs. Redis becomes relevant only with **more than one** core instance (each instance would otherwise warm its own vocabulary and queries and invalidation would have to cross instances); the cheapest real upgrade then is a **generation counter in `MetaCache` served as `ETag`** on the bulk endpoints, not a general cache layer. Measured reasons: bulk reads are milliseconds warm (vocabulary 9 ms), the core↔frontend link is an internal Docker network, every data answer is authenticated and user/locale dependent, and the frontend renders server-side. See `plan/meadow-pim-architektur.md`, Nachtrag 15.
- JWT auth (`auth.rs`): HS256 via `jsonwebtoken`; config through `JWT_SECRET`/`JWT_TTL_SECONDS`. Roles: `superadmin`, `admin`, `editor`, `viewer`. A default `superadmin` (`admin`/`admin`) is seeded in dev when no `user:admin` exists. `Claims` carries an optional `impersonator: Option<Impersonator>` (`{sub, username}`) set for impersonation sessions. `auth::validate_new_password(current, new)` enforces the password policy (`MIN_PASSWORD_LENGTH` = 8 characters, must differ from `current`; `current` empty skips the comparison for admin paths) and is used by `POST /auth/password`, `POST /users` and `PATCH /users/{id}`.
- **Self-service password change** (`src/api/auth.rs`, `POST /auth/password`, any authenticated role): body `{current_password, new_password}`; verifies the current password against the stored argon2 hash (400 on mismatch), applies the password policy (400), stores a new hash, sets `password_changed_at`, clears `must_change_password`, bumps `token_version` and returns `200 {token, token_type}` — a **fresh JWT** so the caller's session continues (the token version is not enforced per request yet, see the plan). Rejected with 403 for impersonated sessions (`impersonator` claim). Audited as `password_changed`. `GET /auth/me` returns `must_change_password` (whether the UI should ask the user to set their own password; a **missing field counts as `true`**) plus `password_changed_at` (informational). `POST /users` takes `must_change_password` (default `true`) and validates the password; `PATCH /users/{id}` accepts `must_change_password` **independently** of `password` (clear/re-arm the hint) and, when it sets a password, defaults the flag to `true` (an explicit value wins), **unsets** `password_changed_at` (`UPDATE … UNSET` — `MERGE` cannot write `null` into an `option<datetime>`) and bumps `token_version`, audited as `user_password_reset`.
- **Impersonation** (`src/api/auth.rs`, `POST /auth/impersonate/{user_id}`, **superadmin only**): issues a normal JWT for the target `user` (`sub`, `username`, `roles`, `token_version`, `exp`) plus an `impersonator` claim (acting superadmin). Rejects self-impersonation (400) and non-active targets (400); `GET /auth/me` returns the `impersonator` claim so the UI can show a banner. Audited as `user_impersonated`. This is a test/support aid, not a privilege-escalation path — the token adopts the target's roles.
- `POST /system/logs` accepts a machine-to-machine `X-Api-Key` (`LOG_INGEST_API_KEY`) or, as a dev fallback, an admin JWT. Full-text search (`POST /search`) uses analyzer `meadow_std` and index `idx_object_attributes_fulltext` over `object.attributes`. `GET /system/settings` also accepts the API key (machine-to-machine config read for the worker). Curated log categories are `app|job|rule|auth|integration`; the core's own rule logs use `rule` (singular). `GET /system/settings` returns a flat `{key: value}` map; with **`?include_source=true`** it returns `{key: {value, source}}` (`default`|`env`|`db`) for the admin UI (the worker keeps using the flat form). Settings: `log_persist_level` (DEBUG|INFO|WARN|ERROR|CRITICAL), `log_persist_categories` (array), `log_retention_days` (7–90), `log_rate_limit` (>0), plus **rule knobs** `rules_degrade` (bool), `rules_breaker_threshold` (>0), `rules_timeout_ms` (100–60000); `PUT /system/settings/{key}` persists + audits, `DELETE /system/settings/{key}` resets to default. A resolved settings snapshot lives in **`AppState.settings`** (`Arc<RwLock<Map>>`, precedence default < env < db, seeded by `system::initial_settings` + `refresh_settings_snapshot`); `RulesClient` reads `degrade`/`breaker_threshold`/`timeout` from it at runtime, so the rule settings take effect on the settings page **without a restart**.
- Synchronous rule evaluation (`rules.rs`): the core loads `active` `business_rule` records, builds the candidate view, and calls the Python worker over NATS request/reply (subject `rules.evaluate`) in the object write path. Fail-closed: validation errors reject with 400, a rule that fails (exception/timeout) rejects with 500, an unreachable worker rejects with 503; `RULES_DEGRADE=true` degrades to "skip rules" on transport failure. Circuit breaker: a `failure_count` on the rule auto-disables it after `RULES_BREAKER_THRESHOLD` (default 3) consecutive failures and writes an audit entry + system log; success resets the counter. Config: `RULES_NATS_URL`, `RULES_SUBJECT`, `RULES_COMPILE_SUBJECT`, `RULES_TIMEOUT_MS`, `RULES_DEGRADE`, `RULES_BREAKER_THRESHOLD`.
- Business-rule CRUD (`src/api/rules.rs`, endpoints `/rules`): list/get are open to all authenticated roles; create/update/activate/disable **and `DELETE /rules/{id}`** require `admin`/`superadmin`. Create/update/activate compile-check the script via the worker (subject `rules.compile`); invalid scripts reject with 400, an unreachable worker with 503. New rules start as `draft`; `name` is unique (409); every change bumps `version` and is audited. `DELETE /rules/{id}` returns 204 and is audited `rule_deleted` (no cascade — deleting an `active` computed rule means the matching `attribute_definition` loses its rule, so the UI warns). `POST /rules/{id}/dry-run` (admin/superadmin) evaluates a single rule against a real object (`object_id`) or a constructed `object`, read-only and audited. `POST /rules/{id}/test-batch` (admin/superadmin, Rule Lab) evaluates a rule against a selection of real objects (`TestBatch { object_ids }`), read-only, one NATS evaluation per object, audited as `rule_test_batch`; `RuleSpec` is `Clone` so the spec can be reused across the batch. `POST /rules/{id}/recompute` (admin/superadmin) queues a `business_rule` recompute job over the rule's object set (only `active` `computed`/`bulk` rules; see job management).
- Computed-attribute enforcement (`rules.rs::resolve_computed`): the write path validates that every value a `computed` rule produces is declared as `computed: true` in `attribute_definition`; undeclared or non-computed writes reject the save with 400 (fail-closed).
- Attribute catalog (`src/api/attribute_definitions.rs` + `src/api/attribute_groups.rs`, tables `attribute_definition`/`attribute_group`): `attribute_definition.group_ids` is `TYPE option<array>` of full group record-ids (`attribute_group:<key>`), an inline many-to-many (no `attribute_group_member` join table) — **option** because records created before group enforcement may lack the field (the code guards with `group_ids ?? []`); the create handler always writes `[]` when none. `attribute_group.applicable_types` (`TYPE array`) restricts the object types a group shows (empty = derived from members). **Reading** `GET /attribute-groups` requires `editor+` (it is display metadata: the product form renders one section per group, the export wizard groups its field selection by group) while create/update/delete stay admin-only. `DELETE /attribute-definitions/{id}` (admin) loads the definition via `LET $obj = type::record('attribute_definition', $key)` (record-key, **not** `WHERE id = $id`), counts objects carrying a value with `attributes.<name> IS NOT NONE` (`IS DEFINED` is unreliable for the `object.attributes` map — it returns true for absent keys), rejects with 409 when in use unless `?force=true`, which deletes and queues a `bulk_operation` run with `op=clear_attribute`. `DELETE /attribute-groups/{id}` (admin) also strips the group id from matching definitions' `group_ids` via `array::difference(group_ids ?? [], [$gid])` (`??` guards `NONE`; `array::contains` is **not** a valid function in the embedded SurrealDB — use the `IN`/`CONTAINS` operator). **Enum option management (Phase 9):** `GET /attribute-definitions/{id}/enum-usage?value=` (editor+) returns `{value, count, items:[{id,type}]}` for a scalar enum value (multilingual enums matched via `array::contains(object::values(attributes[$name] ?? {}), $value)` — note `object::values()` throws on `NONE`, so the `?? {}` coalesce guards it). `PATCH /attribute-definitions/{id}` accepts `enum_remap: {old:new}`; when `constraints.enum_values` drops values, the core checks usage per removed value — a used value with no remap target is rejected with 409 (`enum value \`x\` is still used by N object(s); re-map it or keep it`), while a remap target migrates objects (`UPDATE object SET attributes[$name] = $target WHERE ... attributes[$name] = $old`) before applying the new `constraints`.
- **Enum sets (Phase 9, `src/api/enum_sets.rs`, tables `enum_set`/`enum_option`):** reusable, multilingual option lists. `enum_option` = stable `code` + multilingual `labels` (+ `position`/`active`); `enum_set` stores `options` as an **array of full `enum_option:<key>` record-id strings**. `attribute_definition.enum_set_id` (`option<string>`) references a set (full `enum_set:<key>` record id). Endpoints `GET/POST /enum-sets` + `GET/PATCH/DELETE /enum-sets/{id}`, `GET/POST /enum-options` + `PATCH/DELETE /enum-options/{id}` (read `editor+`, write `admin`). `PATCH /enum-sets/{id}` accepts `options` + `option_remap {old_code:new_code}` and runs `removed_usage_check` across the attributes referencing the set (set-level usage); a used code with no remap target → 409. `DELETE /enum-sets/{id}` → 409 while an attribute references it; `DELETE /enum-options/{id}` → 409 while a set references it. `create`/`update` `attribute_definition` validate `enum_set_id` (`validate_enum_set`, normalizes to `enum_set:<key>`) and clear it with a separate `UPDATE ... SET enum_set_id = NONE` (the `MERGE $changes` path cannot carry JSON `null`). When resolving a set's options the `LET $recs = ... SELECT ...` result must be read with `take(1)` (the LET statement is index 0). Objects store the option `code`.
- Resolved view in the write path: `create_object`/`update_object` evaluate rules against own + inherited (`resolve_inheritance`) + language-resolved (`resolve_attributes`) values via `?locale=`; only own + computed values are persisted (inherited values never become own values).
- Inheritance sources (2026-09-11): `inheritance::resolve_inheritance` now **returns** `{attribute: {from, label}}` for every inherited (non-null) value — the parent's `name` is resolved via the language chain, its type is the fallback label. `GET /objects/{id}?resolve_inheritance=true` exposes it as `inherited`; **`GET /objects` supports the same parameter** and fills the page with `inheritance::resolve_inheritance_batch` (one `WHERE in IN array::map($keys, …)` edge query per hierarchy level, results keyed by child key). `parent_with_attributes` reads `out.attributes` **and** `out.type`.
- `remove_attributes` in `UpdateObject` (2026-09-11): a PATCH/batch entry may list attribute names whose **keys are removed** ("back to inherited"), because `MERGE $changes` can only add/overwrite and `{attr: null}` merely interrupts inheritance. The update SQL appends `UPDATE $obj SET attributes = object::from_entries(array::filter(object::entries(attributes), |$e| !($e[0] IN $remove)))` inside the transaction (binds `$remove`); **the read-back index shifts** when that statement is active (SELECT is index 5 without events, 6 with). The removed keys are also dropped from the evaluation view (`own_attributes`) so rules/completeness see the inherited value again.
- Inherited-computed recompute cascade (`rules.rs::inherited_computed_rules` + `rules.rs::queue_inherited_cascade`): after an attribute update (`apply_object_update`), the write path schedules a `business_rule` recompute job per affected rule whose `attribute_definition` has `computed_reads_inherited: true` (query `attribute_definition WHERE computed AND computed_reads_inherited`, join to `business_rule` by `name` for `type='computed' AND state='active'`). Descendants are taken from `references::subtree_keys` (expects the **full** `object:` id), filtered by the rule's `applies_to`, and each `business_rule` job carries the affected objects as **full** `object:` ids (`object_ids`), `trigger: cascade`, and an optional `locale`. Best-effort — a queue hiccup never fails the save. The worker (`meadow/worker/business_rules.py`) loads these objects with `?resolve_inheritance=true[&locale=…]` so computed rules see inherited values.
- Object deletion (`src/api/objects.rs::delete_object`, `DELETE /objects/{id}`, editor+): **soft delete** with cascade over the composition subtree (`subtree_keys`, BFS over `rel_depends_on`). Sets `deleted_at`/`deleted_by` on the object and every `depends_on` descendant, removes all reference edges touching a deleted object (`DELETE reference WHERE in IN $recs OR out IN $recs`), writes one `object.deleted` outbox event (`changes.cascade`/`object_ids`), and audits `object_deleted`. The universal root (`object:object_root`) is undeletable (400). Soft-deleted objects are hidden by the `deleted_at IS NONE` filter added to the object queries (`GET /objects`, `GET /objects/{id}`, `GET /objects/by-source`, `GET /objects/picker`, `GET /objects/by-key`, `GET /objects/{id}/children`). Aggregation edges never cascade — they are removed for the deleted objects, but the connected objects stay intact.
- Saved searches & collections (`src/api/saved_searches.rs`, Phase 9): `saved_search`/`collection` are generic objects (`object` table) — **not** attached to the composition tree. **Saved searches**: `GET/POST /saved-searches` + `GET/PATCH/DELETE /saved-searches/{id}` (CRUD; read editor+, write admin) and `POST /saved-searches/{id}/execute` which runs the query DSL (stored in `attributes.query`) and returns `{count, ids}`. The DSL is a **recursive condition tree**: `where = {op: and|or, conditions: [<group>|<leaf>]}` with leaves `{field, operator, value}` (the flat `filters` list is gone; a stored legacy `filters` is rejected with a clear message), plus `fulltext` (`attributes @@ $q`; `fields`/`language` accepted but unused), `references` (`rel_<type>`, `out` container, `incoming`/`outgoing`), `sort`, `start`, `limit`. `execute_query(db, query, catalog)` loads the catalog, normalizes/validates the query and renders it through `search_schema::render_query` (shared with `GET /objects?where=…`), then projects every sort field (`<field> AS _sort_N`, `ORDER BY _sort_N`) — SurrealDB rejects `ORDER BY` idioms that are missing from the selection (`Missing order idiom`). Sanitized field refs: `type`/`status`/`id`/`created_at`/`updated_at`/`source`/`attributes.<name>[.<lang>]`. **Collections**: `GET/POST /collections` + `GET/PATCH/DELETE /collections/{id}` (write admin) and `POST /collections/{id}/refresh` (editor+ or `X-Api-Key`) which re-runs the saved search and atomically replaces `collection_member` edges (`in`=member, `out`=collection, `attributes={rank, added_at}`; ranks assigned in Rust as `{key,rank}` objects iterated in a single SurrealDB `FOR` loop — SurrealDB `LET` does **not** accumulate in a `FOR`, and `0..<$n` is rejected; use `FOR $item IN $members`), and `GET /collections/{id}/members` (list, editor+) and **`POST /collections/{id}/members`** (bulk-add, editor+, idempotent): `add_collection_members` accepts `CollectionMembersRequest {object_ids}`, normalises/dedupes the object keys (bare or `object:`), skips already-membered ids, RELATEs the rest in a `FOR` loop (`rank` continuing after the current members, `added_at`), returns `{added, skipped}`, and is audited `collection_members_added`. `GET /objects?collection=<id>` (editor+) lists a collection's members (flat, via `references::collection_member_keys`) for the grid's Collections view. A non-empty collection `refresh_interval` cron auto-syncs a `job_definition` (`name = collection_refresh:<key>`, `type = collection_refresh`, `parameters={collection_id}`); clearing it (send the empty string, since `null` maps to the outer `None` for `Option<Option<String>>` and is indistinguishable from "absent") removes the definition. `job_definition.type = collection_refresh` is now in `VALID_JOB_TYPES`; the worker handler calls `POST /collections/{id}/refresh`.
- Object type registry (`src/api/object_types.rs`, Phase 9): `saved_search`/`collection` are generic objects; **object types** are the managed business types (`object_type` table, STIBO STEP / Akeneo family model, **flat** — no type inheritance). `GET/POST /object-types` + `GET/PATCH/DELETE /object-types/{name}` (read editor+, write admin). Each type has `name` (unique code), `label` (multilingual), `description`, `key_attributes` (the unique + **mandatory** business-key attribute names for that type; empty = no key), optional `label_attribute` (display-name attribute), and a **`system`** flag (`bool`, default `false`; the seeded/default types are `system: true`). `key_attributes`/`label_attribute` must reference `text` + non-multilingual attribute definitions (forward references allowed). Deletion is rejected with **400** for `system` types and **409** while objects use the type. `ensure_registered` auto-registers unknown types on `POST /objects` (best-effort, `system: false`). **Business-key enforcement moved per type:** `keys.rs::normalize_key_attributes` now reads the type's `key_attributes` from the registry (was a global `is_key` scan — which also enforced keys for types the attribute did not apply to); the duplicate check filters `deleted_at IS NONE` (soft-deleted objects no longer block). **Completeness (`completeness.rs::required_names`) now includes the type's `key_attributes`** in addition to `required_types`, so a declared key counts as mandatory.
- Rule warnings and `log()` output from evaluations are persisted as curated `log_entry` rows (`service: pim-core`, `category: rule`; warnings as WARN, `log()` with its script-provided level), best-effort.
- Eventsystem (`event.rs`, table `outbox_event`): CRUD operations write an event **atomically** with the change into the outbox (`CREATE outbox_event CONTENT $outbox;` inside the CRUD transaction; `object_id` via `type::string($obj.id)` for newly-created records) and a background relay (`event.rs::run_relay`) publishes `pending` events to NATS JetStream `events.crud` (stream `EVENTS`, WorkQueue retention with `max_age`/`max_bytes`), marking each `published` (`published_at`). Event types `object.created|updated`, `reference.created|deleted`, `attribute_definition.created|updated`; `object.deleted` follows with soft delete (Phase 7). Config: `EVENTS_NATS_URL`, `EVENTS_STREAM_MAX_AGE_DAYS`, `EVENTS_STREAM_MAX_BYTES`, `EVENT_RELAY_INTERVAL_S`. **Outage behavior (verified Phase 8):** if NATS is unreachable the relay logs `WARN ... event relay cycle failed` and events stay `pending`; writes still succeed (transactional outbox — the outbox is the source, NATS only the transport) and events are re-delivered once NATS returns.
- Job management (`src/api/jobs.rs`, tables `job_definition`/`job_run`): admin-only CRUD for definitions (`GET/POST /jobs`, `GET/PATCH /jobs/{id}`), editor+ read of runs (`GET /jobs/{id}/runs`, `GET /jobs/runs?ids=&status=`), and `PATCH /jobs/runs/{run_id}` (worker status update; `X-Api-Key` or admin). **`DELETE /jobs/{id}`** (admin) deletes a definition **and** its runs (cascade via `DELETE FROM job_run WHERE job_definition_id = $id` — no orphans); **`DELETE /jobs/runs/{run_id}`** (admin) deletes a single run. Both return `204` and are audited (`job_definition_deleted`/`job_run_deleted`). Job types `outbound_export|inbound_import|business_rule|bulk_operation`; run statuses `pending|running|success|failed|retry`. `job_run.job_definition_id` is `option<string>`: `None` for ad-hoc jobs (rule recompute). `running`/`retry` clear a stale `error`/`result`; `success` clears `error`.
- Manual job run (`src/api/jobs.rs::run_job`, `POST /jobs/{id}/run`, editor+): creates a `pending` `job_run` (`trigger: manual`) and publishes it to NATS JetStream via `src/jobqueue.rs` (`JOBS` stream, subjects `jobs.*`, WorkQueue retention, `max_age` from `JOBS_STREAM_MAX_AGE_MINUTES`). On queue failure the run is marked `failed` and the call returns 503. Config: `JOBS_NATS_URL`, `JOBS_STREAM_MAX_AGE_MINUTES`.
- MEF import (`src/api/imports.rs`, table `import_document`, endpoints `POST /imports` + `GET /imports/{document_id}` + `POST /imports/{document_id}/complete`): `POST /imports` accepts the MEF document as a JSON body **or** as a `multipart/form-data` file upload (field `file`, parsed via `multer` in `extract_mef_document`), validates it superficially (`objects`/`references` array), stores it in `import_document` (`document`, `format_version`, `source`, `created_by`), and queues an ad-hoc `inbound_import` `job_run` via `queue_run`; the response is `202 { job_run_id }`. Query params `?match_by_key=` (business key), `?match_by_id=` (match the MEF `id` against existing core object ids — Meadow's own MEF export puts the record id in `id`), `?source=` (overrides the document `source`), `?emit_events=`. The route is capped by `DefaultBodyLimit::max(100 * 1024 * 1024)` (100 MB). `GET /imports/{document_id}` returns the stored document to the worker (X-Api-Key or admin). `POST /imports/{document_id}/complete` writes the `import.completed` summary event (`event.rs::EVENT_IMPORT_COMPLETED`) to the outbox.
- **Saved export profiles (`src/api/export_profiles.rs`, table `export_profile`, endpoints `GET /export-profiles` + `GET|POST|PATCH|DELETE /export-profiles/{id}`, Phase 9):** the reusable configuration of the export wizard — the `ExportRequest` **without `source`** (`format` plus `parameters` with only the keys `fields`/`locales`/`options`/`bmecat`). `name` is the record key (`record_key()` lower-cases and replaces non-alphanumerics with `-`: `Meadow BMEcat 1.2` → `meadow-bmecat-1-2`), immutable, max 80 characters; a profile is addressed by record key, record `id` **or** name. Reads take `editor+` (the wizard fills its select), writes are admin, audited `export_profile_created|updated|deleted`. Validation is **closed**: an unknown format (`csv|xlsx|json|bmecat`) or an unknown parameter key is a `400` rather than a silently dropped setting, `fields`/`locales` must be arrays of strings (empty entries and duplicates removed), `options`/`bmecat` must be objects, a duplicate name is a `409`. `notes: ""` **clears** the field with an explicit `UNSET` (an `option<string>` rejects JSON `null`; the `MERGE` cannot carry `NONE`), and the update writes `updated_at`/`updated_by` in the same statement. The MCF section `export_profiles` (`src/api/config/export_profiles.rs`) makes them portable: `merge` creates/updates, `replace` deletes the profiles the document does not list (`record_in_use` → `false`, a profile is never referenced by data), an entry with a bad format or parameters is reported as an **error** and skipped while the rest applies. Frontend: the admin page `/export-profiles` and the wizard card on `/export`. Details: `plan/detail/bmecat-export.md` §5 + §11.13, `plan/detail/datenexport-import-ui.md` §5.7.
- **Configuration export/import (MCF, `src/api/config.rs`, Phase 9):** `GET /config/export` (admin/superadmin) serialises the data model & reference data as an **Meadow Configuration Format (MCF)** document — `sections` for `languages`, `channels`, `units`, `attribute_groups`, `enum_sets`, `object_types`, `classification_standards`, `attribute_definitions`, `relation_definitions`, `business_rules`, `export_profiles`, `category_attributes` — using **stable keys** (name/code/symbol) instead of local ULIDs so it can be imported into another environment. Query params `?sections=` (comma list, empty/`all` = all) and `?include_system=` (default false; includes `system`-flagged object types/relation definitions and `system=default` units). References are resolved to stable keys: `attribute_definition.group_ids` → group names, `unit_id`/`display_unit_id` → unit symbols, `enum_set_id` → set name; `language_tree.parent` → parent language code; `unit.canonical_unit_id` → canonical symbol; `enum_set.options` → `{code, labels, position, active}`. Helper maps (`unit_symbol_maps`, `group_name_map`, `enum_set_name_map`) resolve record-id references. `created_at` is a Rust-side UTC RFC3339 string (`utc_now_iso`, no chrono). Detail: `plan/detail/konfiguration-export-import.md`.** Import-side detail: `normalise_entry_maps()` runs once per section before the apply functions and turns `null` in the map fields `label`/`labels` into `{}` — the export writes `null` for an empty label map, but the object-typed fields reject `NULL` (`plan/detail/bmecat-export.md` §11.4, found in the ETIM spike).**Import** is `POST /config/import` (admin/superadmin): `?mode=dry_run|merge|replace` (default merge). It applies each section in dependency order (`languages` → `channels` → `units` → `attribute_groups` → `enum_sets` → `object_types` → `classification_standards` → `attribute_definitions` → `relation_definitions` → `business_rules` → `export_profiles` → `category_attributes`), resolving references to existing target records via a preloaded `Resolve` map (stable key → target record key) and falling back to creating missing referenced records. `system`-flagged entries and `system=default` units are skipped (seeded rows must already exist, existence is required). Existing records are merged with `UPDATE ... MERGE`; `would_change(existing, content, VOLATILE)` reports re-imports of an unchanged document as `skipped` (idempotent report) instead of `updated` — `VOLATILE` ignores `version|updated_by|updated_at|created_at|failure_count`. Response is a `ConfigReport` (`mode`, `summary {created,updated,skipped,deleted,errors}`, per-section lists). **`replace`** first deletes target-only (non-system) records per section present in the document (reverse dependency order; `system` records and records still in use are kept, the latter reported as errors), then applies the document — so the applied section matches the document exactly; absent sections are left untouched and a full round-trip replace is a no-op. **Async import (`?async=true`):** stores the document in `import_document` (with `kind = "mcf"`) and queues a `config_import` job (`VALID_JOB_TYPES`), returning `202 {job_run_id}`; the worker (`meadow/worker/config_import.py`) fetches it via `GET /imports/{document_id}` and re-applies it through the sync endpoint, storing the report in `job_run.result`. Both the sync and async paths accept `X-Api-Key` (worker machine-to-machine) or an admin JWT via `api_key_or_role(..., ROLE_ADMIN)`. **SurrealDB quirks:** `option<T>` fields reject JSON `null` so nullable fields are omitted from `CONTENT`/`MERGE`; `array::contains` is invalid (use `array::distinct(array::append(...))`); a trailing `SELECT * FROM $r` after `UPDATE` returns no rows (so `update_keyed` runs only the UPDATE); `response.take(idx)` depends on the statement count (`take(2)` after `LET $r = …; CREATE/UPDATE …`); `enum_option.code` is globally unique (options are found by code then re-linked).

- Attribute value validation (`src/attribute_values.rs`, Phase 9): the **only** value-level check of the core so far, for the `url` data type. `is_valid_url()` accepts an absolute `http(s)` URL with a host only (WHATWG parser via the `url` crate, surrounding whitespace tolerated) — `example.com`, `ftp:`/`mailto:`/`javascript:`/`data:` and `https://` are rejected; `validate_attribute_values()` is called by `create_object` and `apply_object_update` (hence also by `batch_update_objects` and every worker write path) and returns `400` with one message per offending value, naming the attribute (`` `attributes.homepage`: must be an absolute http(s) URL ``, multilingual per language: `` `attributes.homepage.de`: … ``). `null` and empty/whitespace strings mean "no value" and stay valid; non-string values (numbers, arrays, a language map for a scalar attribute) are rejected. The attribute list comes from `MetaCache::url_attributes` (no query per write). **Rule:** a new data type that needs validation gets its check here, not in the handlers. The `range` type (two numeric bounds `{"from", "to"}`, added Phase 9 for ETIM/BMEcat range features) is checked nowhere on write, like `number`; its rules live in `attribute_definition_types.rs` (`is_range`, `is_numeric`, `range_value` orders the bounds, `parse_range`/`format_range` for the canonical `from..to` text form) and are applied on the type-change path — units are kept when moving between the numeric types.
- Attribute definitions (`src/api/attribute_definitions.rs`, Phase 9): `DELETE /attribute-definitions/{id}` counts the objects that carry a value for the attribute (409 with `?force=true` to remove the values as a bulk job) — the check filters `deleted_at IS NONE`, like every other usage/visibility query (`count_enum_usage`, object lists, `object_types` deletion), so **soft-deleted objects never block** a deletion. **Data-type change (`POST /attribute-definitions/{id}/type-change`, admin):** the type is mutable through a dedicated endpoint because every existing value must be migrated. Preconditions: not `computed` (the rule owns the value), a business key may only stay `text` (`409` each), the target must be allowed by the compatibility matrix and a target `enum` needs an existing `enum_set_id` (`400`). `?dry_run=true` returns the report (`{name, from, to, checked, convertible, incompatible, samples[], dropped, dry_run}`) without writing; applying converts each value (a value that does not fit blocks the change with `409`, `drop_incompatible: true` removes those values instead), updates the definition (leaving `enum` clears `enum_set_id`/`constraints`, leaving `number` clears the units) and writes both in **one transaction** (`FOR $row IN $rows { UPDATE … SET attributes[$name] = $row.value; }`). Audited as `attribute_definition_type_changed`, event `attribute_definition.updated`, caches invalidated. `PATCH /attribute-definitions/{id}` rejects a `type` field with a pointer to this endpoint (silently ignoring it would look like a successful type change). `standard_codes` is normalised and validated by `validate_standard_codes`: an object of `{standard: code}` with non-empty codes, and a code may be claimed by exactly one definition (a second claim is `409` naming the other attribute). Clearing goes through `SET standard_codes = NONE`, **not** an empty `{}` — the update runs `UPDATE … MERGE`, and SurrealDB `MERGE` merges nested objects key-wise, so `{}` would silently keep the old binding. The same reason drives the `enum_set_id` clear. **`reference_data` (bool, 2026-09-13)** marks an attribute as the vocabulary of a classification standard (set by the standard import, 380 definitions in the shipped ETIM 10.0 bundle): the frontend hides it wherever an attribute is *chosen* and shows a **Standard** column/filter plus an adopt action that clears the flag. Accepted in `POST` (default `false`) and `PATCH`; both `standard_codes` and `reference_data` travel in the MCF `attribute_definitions` section, so an exported configuration keeps the binding and the adopted state (`plan/detail/kategorisierung.md`, "Referenzdaten").
- Search field catalog, validation & filter rendering (`src/api/search_schema.rs`, Phase 9): the **server contract** behind `GET /search-fields`, the validation of every saved-search query (write, execute, preview, collection refresh) **and** the SurrealQL rendering shared by saved searches and the grid: `Catalog {groups, operators, fields, languages, references, limits}` is built by `load(db)` from `attribute_definition`/`object_type`/`object`-status/`enum_set`+`enum_option`/`unit`/`language_tree`/`relation_definition`, where `build_catalog(&CatalogSources)` is the pure, unit-tested part. Fields carry `value_type` (`string|number|boolean|date|datetime|enum|url`), `widget`, `options`/`options_source`, `multilingual`+`languages`, `unit`, the **allowed** `operators`, `sortable` and `computed`; `reference` attributes are not filterable (relation types are, via `query.references`). A field also carries **`reference_data`** (from `attribute_definition.reference_data`, part of the catalog query since 2026-09-13): such a field stays **filterable** — a stored search must keep validating — and only tells the client to keep the standard's vocabulary out of the *offered* field/sort lists (the search form has a switch for that, `meadow/frontend/search_form.py`). A **`range` attribute** (value `{from, to}`) is not offered as one field: each **bound** becomes its own numeric field (`attributes.<name>.from` / `.to`, property `range_bound`), so every numeric operator keeps its documented meaning and validation/sorting/`unit` work unchanged; `sanitize_field` already accepts the two-segment path. `url` fields are text filters with `in`/`not_in` and the cell value must be a string (`value_type_hint` → "a URL"). `OPERATORS` declares `arity` (0 = no value, 1, 2 for `between`/`not_between`) and `multi` (`in`/`not_in`) — the client renders its value widget from exactly these two properties; `not_between` is offered for numeric/date fields only. `MAX_DEPTH` is **6**, `MAX_CONDITIONS` 50. `validate_query()` returns messages naming the path inside the condition tree (`query.where.conditions[1].operator: `gt` is not allowed for …`), enforces the depth/condition/limit bounds plus the reference/sort shapes, and accepts `eq null`/`ne null` as the “has no value” spellings. `normalize_query()` folds the documented operator aliases (`neq`/`ge`/`le`/`is_empty`), always sets the group `op` and prunes empty groups (an empty root means “no restriction”); the handler stores that canonical form. **Shared renderer** (`RenderedFilter {clauses, params}`, `sanitize_field`, `render_condition`, `render_filter`, `render_query`): groups become parenthesized `AND`/`OR` clauses, parameters are numbered recursively (`f0`, `f1`, …), composite clauses are parenthesized (`AND` binds tighter), `created_at`/`updated_at` operands are wrapped in `type::datetime(…)`, sort fields are projected as `_sort_N`, and **ordering/negative operators are guarded with `field IS NOT NONE AND field != NULL`** — in SurrealDB `NONE < 0` is true (missing values sort before numbers) and `NONE != 'x'` is true as well, so without the guard `not_between [0, 200]` matched every object without a value; “has no value” is expressed with `is_null` only. `render_query` also emits the `fulltext` (`attributes @@ $q`) and reference clauses. **Rule:** every field/operator pair offered by the catalog is executed, and every executed operator is declared here. Consumers: `POST`/`PATCH /saved-searches`, `POST /saved-searches/{id}/execute`, `POST /saved-searches/preview` (read-only `{count, ids}`), collection refresh and **`GET /objects?where=<Query-DSL-JSON>`** (grid / advanced search: same catalog, `400` with the same path messages, combined with `AND` to `type`/`q`/`missing_required`/…). Contract: `plan/detail/suche-formular.md`.

- Composition tree & children (`references.rs`, editor+): `GET /objects/tree` returns the composition tree rooted at the Universal-Root as nested `{ id, children: [...] }` nodes in one call (query `SELECT in AS child, out AS parent FROM reference WHERE definition_id = 'rel_depends_on'`, then a recursive build with cycle protection); used by the grid's structure navigation, names resolved client-side. `GET /objects/{id}/ancestors` returns the path from the outermost composition ancestor down to the object (root-most first, the object last; each entry = object document + `hasChildren`, the universal root is not part of the path) — the tree panels use it to show a **search hit in its hierarchy** instead of a flat hit list; the walk is one query per level (taxonomy depth) plus two batched queries and refuses to loop on broken data. `GET /objects/{id}/children` (paginated `?limit`/`?offset`, `ChildrenListParams`) returns the direct `rel_depends_on` children **paginated**, each as its object plus a **`hasChildren`** flag (so the tree shows the expand arrow without loading the whole subtree, for lazy loading); it fetches the child objects in one `SELECT * FROM object WHERE id IN $recs` and **skips children whose object record is missing** (broken/dangling `depends_on` references stay out of the tree). **`?scope=all|composition|taxonomy` (default `all`) and `?type=<object type>` filter in the core** — `composition` excludes the taxonomy types (`object_type.taxonomy`), `taxonomy` keeps only them; an unknown scope is a `400`. Why it must be server-side: with a classification standard installed the universal root carries **5648 taxonomy nodes** next to 46 structure objects, so a client-side filter silently truncates a `LIMIT`ed page and makes `count_members` count subtrees nobody renders. **The filter must use the record-link traversal `in.type`, never `in IN (SELECT VALUE id FROM object WHERE …)`**: measured at the root the subquery shape needs **31.7 s** (evaluated per candidate row), `in.type …` answers the same page in **0.12 s** (still driven by `idx_ref_out_def`). `?count_members=true` adds a `memberCount` to every taxonomy child (`?definition_id=` selects the category relation type, default: the primary one; unknown/non-category ⇒ `400`), computed for the whole page in **one pass** by `category_member_counts` (reads the composition edges and the assignments once, then `subtree_member_counts` — pure and unit-tested — sums the subtrees in memory; the earlier per-child variant re-read every edge per node: ~8 s for 100 children). The endpoint authorizes via `api_key_or_role(..., ROLE_EDITOR)`, so the bulk worker (service account, `X-Api-Key`) can walk the tree for `consolidate_inheritance`. `subtree_keys(db, root_id)` (BFS over `rel_depends_on`, returns **bare object keys**, with cycle protection) backs the server-side subtree filter in `GET /objects?ancestor=<id>` (`objects.rs::list_objects`): the condition is `id IN array::map($ancestor_ids, |$k| type::record('object', $k))`, replacing the former client-side `collect_subtree` traversal once the structure tree is lazy-loaded. `category_member_keys(db, category_id, definition)` (also in `references.rs`) backs `GET /objects?category=<id>[&definition_id=<rel_…>]`: it computes the category's composition subtree keys (`subtree_keys`) and returns the bare keys of every object assigned via `category_member` (`rel_category_member`, aggregation) to that subtree — used by the grid's category tree (selection filters via aggregation, not composition). `collection_member_keys(db, collection_id)` (also in `references.rs`) backs `GET /objects?collection=<id>`: it returns the bare keys of every object assigned via `collection_member` (`rel_collection_member`, aggregation) to that collection — used by the grid's flat **Collections** view (selection filters via aggregation, no hierarchy). It binds `$col` to `key_of(collection_id)` and reads the result with `take(0)` (a single-statement query, unlike `category_member_keys` which has a `LET` prefix and uses `take(1)`). `GET /objects?uncategorized=true` (`objects.rs::list_objects`) filters `id NOT IN (SELECT VALUE in FROM reference WHERE definition_id = 'rel_category_member') AND type NOT IN ['category', 'root']` — the grid's „Nicht kategorisiert“ entry.
- Reference picker & relation definitions (`references.rs`, editor+): `GET /objects/picker?q=&types=&locale=&limit=` (compact full-text object search for the reference picker, returning `{id, type, label, status}` with the label resolved via `language::resolve_object_label` — `name` first, then `code`, then the object type, so a taxonomy class shows `EC012373` instead of `etim_class`; with `?locale=` each hit also carries **`completeness: {"<locale>": <0–100>}`** so the form's pickers can badge the target — computed per hit via `completeness::compute`, because the picker's hit list has no ancestors for `compute_batch`). **Two opt-in parameters (2026-09-14, additive — the taxonomy tree's search uses them):** `?code_prefix=true` adds a **second** query for a partial `code` (`EC0123` → every class `EC0123…`) as the range `attributes.code >= <prefix> AND < <prefix+1>` (`prefix_upper_bound`, pure + 2 unit tests; matched as typed *and* upper-cased, since the full-text search is case-insensitive), its hits merged into the result (prefix hits first, then the full-text hits by `score`, deduped by id); `?completeness=false` skips the per-hit badge, which costs **~0.3 s per hit** (measured: 5 hits with `?locale=` = 1.4 s, without = 9 ms). Two traps forced the **separate** query: `attributes @@ $q` matches **whole tokens only** (`EC0123` finds 0 of the 61 matching classes but `EC012373` finds one), and combining it with another condition via `OR` **degenerates** in SurrealDB 3.2 — `(attributes @@ 'EC0123' OR string::starts_with(attributes.code, 'EC0123'))` returns all **5640** classes instead of 61 (`… OR false` is fine, it is constant-folded); `string::starts_with` also fails on objects without a `code` (`Expected string but found NONE`), the range comparison does not; `GET /objects/{id}/references?locale=` (list an object's references with resolved `in_object`/`out_object` summaries; authorizes via `api_key_or_role(..., ROLE_EDITOR)`, so the bulk worker can use the service-account key); `DELETE /references/{id}` (editor+ **or `X-Api-Key`**, 204); `GET /relation-definitions` (editor+ **or `X-Api-Key`** so the worker can resolve relation roles, all `relation_definition` rows for the picker's relation-type dropdown). `create_reference` expects the relation definition's **short record key** (e.g. `rel_category_member`, derived from `relation_definition:rel_category_member`) as `definition_id` — not the full record id nor the display `name` (e.g. `category_member`). `list_object_references`/`picker` resolve labels against the locale fallback chain via `language::resolve_label`. **Relation-type CRUD (Phase 9, `POST`/`PATCH`/`DELETE /relation-definitions`, admin):** custom types (`system: false`) are **always `kind: aggregation`** (the backend forces it; `name` may only contain `[A-Za-z0-9_-]` and derives the record key `rel_<name>`), carry optional `source_types`/`target_types` (allowed object types, enforced at reference creation) and an **`attributes`** array (edge-metadata names referencing `attribute_definition`, forward references allowed). `PATCH` updates label/restrictions/attributes; `DELETE` is rejected with 400 for `system: true` types and 409 while references use the definition. **Edge metadata (`PATCH /references/{id}`, editor+):** updates a reference's `attributes`; keys must be declared in the definition's `attributes` template when non-empty (`validate_edge_attributes`), and `create_reference` applies the same check. A SurrealDB RELATION-table quirk: a trailing `SELECT * FROM $r` in the same statement as `UPDATE $r SET …` returns no rows, so `update_reference` re-fetches in a separate statement.
- Completeness (`src/completeness.rs`): computes an object's **Vollständigkeit** as the percentage of its type's required attributes (`required_types` on `attribute_definition`) that are set. `compute(cache, db, object_id, object_type, locale, own_attributes)` resolves inheritance (`inheritance::resolve_inheritance`) and splits required names into set/missing via `split_set` (pure, unit-tested): a name is *set* when its key is present in `own` attributes (even an explicit empty/null value, which breaks inheritance) or when it was inherited as a non-null value; 100 when the type has no required attributes. `compute_with_required` has a **fast path**: if every required name is already present in `own` it returns 100% without resolving inheritance. The `required_names`/`compute_with_required` are `pub(crate)` so aggregators can reuse required names per type. **`compute_batch`** (Phase 8, used by `GET /objects/stats`) resolves completeness for many objects in one pass: a single `load_parent_map` edge query (`SELECT in, out FROM reference WHERE definition_id='rel_depends_on'`) builds a child→parent map, `inheritable_names` from the cache gates which required names may be inherited, and the chain walk (`resolve_missing_in_memory`, pure + unit-tested) fills values in-memory — avoiding one DB query per ancestor per object. Wired into `objects.rs`: `GET /objects?locale=<code>` adds `completeness: { "<code>": <0–100> }` per object; `GET /objects/{id}?locale=<code>` adds `completeness` and `missing_required` (list of missing required attribute names, for the form widget); `GET /objects/stats?locale=<code>` returns the dashboard aggregation `{total, by_type, by_status, incomplete_by_type}` (object counts by type/status via a single `GROUP`-free scan plus per-type incomplete counts via `compute_batch`). **`GET /objects` completeness filters (Phase 9):** `?completeness_lt=<n>` (keep objects strictly below `n` %) and `?missing_required=true` (keep objects that still miss a required attribute) — applied in `list_objects` via the pure helper `passes_completeness_filter` (unit-tested) after the per-object `compute` (which resolves inheritance, so a page is filtered correctly even when the ancestors are not part of the page; `compute_batch` is only exact over a whole dataset). The filter cannot be expressed in SQL, so it is applied to a scanned window of up to 1000 rows and `start`/`limit` then slice the **filtered** result; `locale` may be omitted (default values).
- Batch update (`objects.rs`, endpoint `POST /objects/batch-update`, editor+): applies a list of partial changes (`[{id, attributes, status, …}]`) in one call; shared per-object logic with `PATCH /objects/{id}` via `apply_object_update` (rules/computed/workflow guard, outbox event, audit). Capped (verbindlich) at `MAX_BATCH_UPDATE_ROWS` (500) per call, returning `413 Payload Too Large` (`error::payload_too_large`) above the limit. The result is a per-item list (`{id, success, status?, error?}`); an invalid/expired JWT is reported per item as `error: "invalid or expired token"` (HTTP 200, `success: false`).
- **Classification standards (`src/api/classification_standards.rs`, table `classification_standard`, endpoints `GET /classification-standards` + `GET|POST|PATCH|DELETE /classification-standards/{id}`):** the registry of the external standards (ETIM, ECLASS…) this catalogue was **loaded** with — one row per `code` + `version` (`etim`, `10.0`, deterministic record key `etim-10-0`), with `name`, `source` (the artefact the package was built from), `node_type` (the object type of the class nodes, must be a taxonomy type ⇒ else `400`), `notes`. Reads take `viewer+`/`X-Api-Key` (the export worker needs it), writes are admin. The list is assembled in Rust (a handful of rows) and adds the derived `feature_system_name` (`ETIM-10.0`) and `current` (newest version per `code`, compared **numerically**: `10.0.1` > `10.0` > `9.1`; `version_key` is pure and unit-tested); `?counts=true` adds the live `class_count`/`feature_count` of the node type (two extra queries: the class ids via `VALUE type::string(id)`, then `SELECT type::string(category_id) AS class_id, count() AS total FROM category_attribute GROUP BY class_id` summed in Rust — the grouped scan is **linear**, while the earlier `WHERE category_id IN array::map($keys, type::record($k))` shape needed a lookup per table row and did not return within 300 s once the full ETIM bundle (5640 classes) was installed; record ids are normalised without backticks before comparing). **Why:** the BMEcat export used to take the reference feature system version from a free-text profile field, so a catalogue could claim a version it never installed; `{id}` accepts `code@version` or the record key, and the record key is always derived from the row's own `code`/`version` — SurrealDB serialises a quoted id back as ``classification_standard:`etim-10-0` ``, and splitting that string would carry the backticks into the key. Deleting a row removes **no data** (classes/features/attributes are catalogue data). Details: `plan/detail/kategorisierung.md`.
- **Class features (`src/class_features.rs`, `src/api/category_attributes.rs`, Stage B):** `category_attribute` attaches attribute definitions to a taxonomy node (`category_id` record + `attribute` **name**, `required`, `position`, unique `(category_id, attribute)`). An object assigned to a class (any `role: category` relation) gets the class's features **plus** its ancestors' (`depends_on` chain, `ancestor_chain`/`ancestor_chain_live`). Two paths: per-object (`resolved_features`, few small indexed queries) and batch (`class_required_names_batch`, reusing the `depends_on` map of `completeness::compute_batch`). `class_required_names` feeds `completeness` (single + batch, same semantics as the API), so mandatory class features count into the percentage and `?missing_required`; `rules::missing_class_features` puts them into `ctx.missing_features`. Endpoints: `GET /objects/{id}/category-attributes` (resolved + `missing` + **`classes`** — the taxonomy nodes the object is assigned to, so a consumer can name the classification block itself (the BMEcat export writes one `PRODUCT_FEATURES` per class); editor+/`X-Api-Key`), `GET|POST /categories/{id}/attributes`, `PATCH|DELETE /categories/{id}/attributes/{attribute}` (admin; unknown attribute or non-taxonomy node ⇒ `400`, duplicate ⇒ `409`). Deletes of attribute definitions, class nodes and objects clean up the rows (renames are carried over). `ancestor_chain`, `merge_names` and `own_attributes` are unit-tested. **Own attribute as a carrier (`standard_codes`, 2026-09-13):** `attribute_definition.standard_codes` (`option<object>`, `{standard: code}`, e.g. `{"etim": "EF000040"}`) binds an **own** attribute to a standard's feature code, so a maintained product can be classified without adopting the standard's attributes. `feature_bindings` (now **cached** in `MetaCache::feature_bindings`, invalidated with the attribute definitions — measured: 17 397 definitions / **~0.3 s per call** with ETIM 10.0 installed, which every per-object `completeness::compute` paid, so `GET /objects?ids=1&locale=` went 332 ms → 69 ms, `?limit=20&locale=` 5.7 s → 0.5 s and a picker hit with badge 289 ms → 39 ms) and `resolve_attribute` (pure, unit-tested) picks the **binding** first, then the attribute named like the code, then the code itself. `ResolvedFeature` therefore carries both `name` (the code an export transmits) and `attribute` (the attribute that holds the value): `required`/`missing`/completeness count the **attribute**, `FNAME` is the **code**. **Reference data:** an attribute definition flagged `reference_data` is a standard's vocabulary, not the customer's own attribute set — the frontend keeps it out of the form (unless the object carries a value), the export field selection (behind a switch), the bulk wizard and find/replace, while the class-feature resolution and the export keep working with it unchanged.
- Relation usages (`role`) & taxonomy types (2026-09-11/12): `relation_definition.role` (`schema.rs`, `option<string>`) classifies a type's **usage** – `composition` | `category` | `collection` | `link` (Default). The seed (`src/seed.rs`) sets the four built-in roles, marks exactly `object_type:category` as the system **taxonomy** (`object_type.taxonomy`, `object_types.rs::PRIMARY_TAXONOMY_TYPE`; other system types are asserted `false`, existing rows without the field are backfilled) and migrates rows without a role to `link`; `POST /relation-definitions` accepts `role` for custom types (`link`/`category` only, `400` for the reserved roles), validates an explicit `target_types` list of a `category` role against the registered taxonomy types (`check_taxonomy_targets`, `400` naming the allowed types) and `PATCH` rejects a role change for `system: true` types; a role change to `category` drops non-taxonomy targets. `create_reference` enforces the role: a categorisation may only point at a taxonomy type (`is_taxonomy_type`, error lists `category_target_types(db)`), a collection only at `collection`. `?count_members=true` (`references.rs`) adds `memberCount` for every taxonomy-typed child, and `GET /objects?uncategorized=true` (`objects.rs`) excludes all taxonomy types plus `root` (`$taxonomy_types`). `POST`/`PATCH /object-types` carry `taxonomy` (custom types only, `system` types ⇒ `400`). `references::PRIMARY_CATEGORY_DEFINITION` (`rel_category_member`) and `resolve_category_definition(db, requested)` centralise the categorisation relation types; `role_of`, `custom_role`, `role_target_types` and `check_taxonomy_targets` are unit-tested.
- **Seed semantics (`src/seed.rs`): create-if-missing.** All seeded records (relation-definition identities, universal root, object types, units, languages) are written with `INSERT INTO … VALUES … ON DUPLICATE KEY UPDATE id = id` (SurrealDB ≥ 3.2), so a core restart **never** overwrites runtime edits (labels, `source_types`, `target_types`); only the structural identity of the built-in relation types (`kind`, `system`, `role`) is asserted with a follow-up `UPDATE`. Before this change an `UPSERT … CONTENT` on every start silently reverted those edits.
- Bulk operations (`objects.rs`, endpoint `POST /objects/bulk`, editor+): queues a `bulk_operation` `job_run` for a mass operation. Payload `BulkObjectRequest {op, object_ids, parameters}`; `BULK_OPS` = `set_attribute|clear_attribute|change_status|send_for_approval|add_category|remove_category|add_relation|remove_relation|change_parent|replace_text|consolidate_inheritance|delete`. Validates the editor role, a known `op`, and a non-empty `object_ids`, then calls `jobs::queue_run(..., "bulk_operation", parameters, "manual", &claims.sub)` with `parameters = {op, object_ids, parameters}` and returns `202` with the `job_run`. The worker (`meadow/worker/bulk.py`) applies the operation per object and stores `{op, processed, succeeded, skipped, failed, replacements, approvals, results[]}` in `job_run.result` (`skipped` counts objects without a match for `replace_text`, `approvals` the successful workflow transitions; `consolidate_inheritance` adds its own report keys, see `plan/detail/vererbung-konsolidierung.md`).
- Rule recompute (`src/api/rules.rs::recompute_rule`, `POST /rules/{id}/recompute`, admin/superadmin): queues a `business_rule` `job_run` (no definition) whose parameters embed the rule `{name, type, script}`, `applies_to`, and optional `object_ids`. The worker executes and reports per object.
- Computed write-back (`src/api/objects.rs::update_computed`, `PATCH /objects/{id}/computed`, `X-Api-Key` or admin): machine-to-machine path that merges only declared-`computed` values (`rules.rs::resolve_computed`) into an object without re-running rules (used by the recompute worker).
- Cron scheduler (`src/scheduler.rs`): a background task (`tokio::spawn` in `run()`) keeps `tokio_cron_scheduler` in sync with enabled scheduled `job_definition` records (6-field seconds-first cron) and, on each fire, creates a `job_run` (`trigger: schedule`) and publishes it to JetStream via `queue_run`. Sync interval from `SCHEDULER_INTERVAL_S` (default 60).
- Dead-letter monitor (`src/jobqueue.rs::monitor_dlq`, background task): ensures the `JOBS_DLQ` stream (`jobs.dlq.*`, Limits retention, manual cleanup) and, for each dead-lettered message, marks the corresponding `job_run` as finally `failed` via `jobs::fail_run` („dead lettered after N attempts“).
- Log-retention cleanup (`src/log_cleanup.rs`, background task): deletes `log_entry` rows older than `log_retention_days` (resolved from system settings via `system::resolve_retention_days`; default 30, validated 7–90) every `LOG_CLEANUP_INTERVAL_S` seconds (default 3600). The ingest rate-limit (`log_rate_limit`) is not yet enforced (deferred per api-design).
- Request limits (`src/app.rs` + `src/rate_limit.rs` + config fields `max_body_bytes`/`rate_limit_per_minute`): a global axum `DefaultBodyLimit` (env `PIM_MAX_BODY_BYTES`, default 10 MiB) caps request bodies; routes with a larger need re-declare their own `DefaultBodyLimit` (e.g. `/imports` at 100 MiB), which — as the innermost layer — overrides the global one. `RateLimiter` (env `PIM_RATE_LIMIT_PER_MINUTE`, default **0 = disabled**) is a per-IP fixed-window limiter (in-memory `HashMap<IpAddr, (Instant, u64)>`, 60 s window) applied as the outermost router layer and returns `429` when exceeded. It reads the peer IP from `ConnectInfo<SocketAddr>`, so the server is served via `into_make_service_with_connect_info::<SocketAddr>()`; it does **not** honor `X-Forwarded-For`, so behind a reverse proxy all clients share the proxy IP (acceptable for direct/LAN deployments; revisit if a proxy terminator is introduced). Defaults keep dev unaffected (2 MiB body, no rate limit).
- **Read-path performance rules (2026-09-14, all figures measured against the dev DB: 17 379 attribute definitions, 5 640 classes, 76 625 `category_attribute` rows):** id lists are rendered as **record literals** (`[object:a, object:b]` via `api::keys::record_list_literal`, which drops keys that are not `[A-Za-z0-9_-]` — such keys cannot exist) instead of `id IN array::map($keys, |$k| type::record('object', $k))`, because SurrealDB evaluates that expression **per candidate row**: 100 keys 1.9 s, 1 000 keys 16.6 s, 5 640 keys 110 s, while the literal list uses the id index (100 keys 49 ms, 1 000 keys 178 ms). `MetaCache::required_names` caches the per-type required names (cleared by attribute-definition **and** object-type writes, `invalidate_object_types`), `completeness::compute_batch` resolves the whole page in one pass (including `load_ancestor_attributes` for the objects' ancestor chains, so a batch resolves inheritance exactly like the per-row path) and `GET /objects` computes completeness **once per page** instead of once per row; `class_required_names_batch` loads `category_attribute` only for the contributing classes (assigned nodes + ancestor chains) instead of the whole table (6.8 MB), and `config/category_attributes` reads the class nodes with a type filter instead of an id list. Measured effect: `GET /objects?limit=1000&locale` 18.1 s → 0.24 s, `?missing_required` 17.8 s → 0.22 s, `GET /objects/stats` 3.0 s → 0.4 s, `GET /config/export` 81 s → 8.4 s. `GET /attribute-definitions/vocabulary` serves the slim projection of **all** definitions from `MetaCache::attribute_vocabulary_json` (a **serialized** body — 5.83 MB; cloning and re-serializing it per request cost more than the query it saves): the `/export` wizard's field selection needs every definition, and paging `GET /attribute-definitions` cost 18 requests / 4.5 s — it is also capped at 1000 rows, so with an imported standard (17 377 `EF…` features, ordered by codepoint) the late-sorted own attributes were unreachable; today both consumers load the vocabulary projection (`/export` wizard and the `/attribute-definitions` catalog page), while the vocabulary call takes **1.5 s cold / 9 ms warm** (page build 12.0 s → 2.2 s) — the cache is cleared by the definition writes **and** by the MCF import (`POST /config/import`, which writes definitions directly and left every metadata cache stale before). Remaining known bulk cost (payload-bound): `GET /config/export` ≈ 10–13 s / 14.3 MB (`attribute_definitions` 7.8 s/9.5 MB + `category_attributes` 7.5 s/4.7 MB) — a click-triggered admin action, not a page build. **Measurement note:** `Invoke-WebRequest` inflates multi-megabyte responses by roughly 1.4 MB/s (it showed 25 s where a Python client measures 10 s); measure payload-bound paths with a Python client or the browser's page timing, and never compare a PowerShell timing against a Python one.
- **Clearing optional text fields on `PATCH /attribute-definitions/{id}` (2026-09-15):** `computed_rule`, `unit_id`, `display_unit_id` and `enum_set_id` are `option<string>` fields, and `UPDATE … MERGE` cannot write the distinct `NONE` — so a clear is collected in `clear_fields` and applied as **one** `UPDATE $obj UNSET a, b;` statement (which shifts the index of the trailing `SELECT`). The trigger is `patch_text` (`deserialize_with`): a **present `null`** becomes `Some(None)` = "clear", an **omitted** field stays `None` = "leave it as it is", and an empty/whitespace string clears as well. A plain `Option<Option<String>>` cannot tell those apart (serde maps JSON `null` to the *outer* `None`), which is why `{"computed_rule": null}` silently kept the old rule — found while wiring the dialog to clear fields that lost their meaning. On `POST` an empty string simply means "no value" (`text_change`), so a client may send the same payload for create and update.
- SurrealDB `option<T>` fields reject JSON `null` (the distinct `NULL` value, not `NONE`): omit `None` option fields when building `CREATE ... CONTENT`, and clear them with `UPDATE ... SET field = NONE;`.
- **SurrealDB quotes a record key that needs it** (`` classification_standard:`etim-10-0` ``, `` export_profile:`meadow-bmecat` `` — any key with a dash). A serialised `id` therefore carries the **backticks as part of the string**: `id_of()` (`api/config.rs`) strips the table prefix **and** the quoting, because `type::record(table, key)` with the backticks addresses a *different* (non-existent) record — an `UPDATE` changes nothing and a `DELETE` reports a removal that never happened. Every endpoint that resolves a reference (record key, `id`, or name) must accept all three spellings, so a caller can pass back the `id` it just received.
- The SurrealDB `Surreal<Client>` is shared behind `Arc` (`db.rs`): cloning `Db` (once per request via `AppState`) must reuse the **same** session, because cloning `Surreal<Client>` directly creates a fresh session whose namespace/database replay is asynchronous and intermittently fails with "Specify a namespace to use" under concurrency.
